# 多实体、多跳关系图谱抽取改进方案

> 文档状态：设计建议，尚未实施  
> 复核日期：2026-07-20  
> 复核范围：`backend/app/services/extraction`、抽取 API、OntologyEngine 以及当前部署容器  
> 约束：本方案仅描述后续改造方向，不代表本文编写时已修改业务代码

## 1. 结论摘要

当前项目已经具备一条可工作的三阶段实体与属性抽取链，以及一条独立的、由本体 schema 驱动的关系抽取链。GLiNER 和 Sentence Transformer 均已在实际后端容器中正常运行，因此后续工作的重点不是“接入 GLiNER”，而是把现有能力组合成一条以父实体为作用域、以证据为中心、可审核并可落入 ABox 的图谱抽取流水线。

综合代码和运行结果，当前方案对单实体、结构化表格及 CMC 特化关系已有较好覆盖；对一篇文档内存在多个同类型实体、每个实体各自拥有不同子关系的场景，仍容易发生父子错绑、子实体笛卡尔积和跨章节串联。按目标能力估算，整体完成度约为 **55%～60%**，其中“通用多实体、多跳绑定”和“关系审核后落库”是主要缺口。

建议的目标链路如下：

```text
文档结构解析
  → 证据单元（段落/句组/表格行/章节）
  → 按“父实体 + 谓词 + range 类”执行 BM25 + 向量混合检索
  → GLiNER 定界候选实体和属性值
  → LLM 在候选与证据内完成 subject-predicate-object 绑定或拒答
  → TTL domain/range/datatype/cardinality 校验
  → GraphCandidate 节点/边审核
  → 创建或复用 ABox individual，并持久化 object/data property
```

核心接口需要从无父实体上下文的：

```python
find_endpoints(ctx, edge)
```

演进为：

```python
find_endpoints(ctx, edge, parent_endpoint, evidence_scope)
```

这项改变比单纯增加更多正则或扩大 LLM 上下文更关键：每一跳都必须知道“正在为哪个父实体寻找哪一种子实体”，并且只能在与父实体相关的证据范围内建立边。

## 2. 当前实现与实测基线

### 2.1 GLiNER 与语义模型复核

此前若只检查宿主机 `backend/.venv`，可能会得到依赖不存在的结论；但项目实际运行环境是 Docker 后端容器。对实际容器复核后确认：

| 项目 | 实测结果 |
|---|---|
| GLiNER | `0.2.27`，可正常加载和推理 |
| GLiNER 模型 | `models/gliner_multi-v2.1` 已存在 |
| Sentence Transformers | `5.6.0` |
| 中文向量模型 | `models/bge-small-zh-v1.5` 已存在 |
| 向量维度 | 512 |
| `GlinerExtractor.is_available()` | `True` |

中文零样本推理样例也已通过：

| 文本 | 标签 | 分数 |
|---|---|---:|
| 苹果公司 | 公司 | 0.7097 |
| 史蒂夫·乔布斯 | 人物 | 0.6843 |
| 加利福尼亚州 | 地点 | 0.7754 |

因此，GLiNER 的当前定位应明确为“已经可用的 span 候选生成器”，无需重新证明模型是否存在。后续应解决其调用方式、长文本切分、候选约束和与关系抽取的融合。

运行时仍有两项技术债：

1. `batch_predict_entities` 在当前 GLiNER 版本中已标记为 deprecated，后续应迁移至 `GLiNER.inference`，并做结果兼容回归。
2. 实测出现 616、689、729 token 的片段被截断到 384 token。当前“一个结构段直接送模型”的方式可能漏掉片段后半部分实体，需要按模型 tokenizer 做受控切分与偏移回映射。

### 2.2 当前三阶段实体与属性抽取

[`document_annotator.py`](../backend/app/services/extraction/document_annotator.py) 已实现：

1. **实体定界**：从本体生成通用种子标签，使用 GLiNER 批量召回 span。
2. **本体归类**：丢弃 GLiNER 的临时类型，以 span 原文或局部上下文的 embedding 与本体类向量做余弦匹配；文档分类成功时，先用相关类子图缩小候选空间。
3. **属性抽取**：按实体最终本体类读取 data property 标签，再用 GLiNER 从实体周围上下文中抽取属性值，形成实体—属性—值三元组。

这条链路的设计方向是合理的：GLiNER 擅长边界召回，Sentence Transformer 负责本体类语义对齐，本体定义负责限制可抽取的属性，而不是要求单一模型同时完成所有任务。

当前局限主要是：

- 属性上下文固定为实体前后 200 个字符，未优先使用表格行、句组、章节等结构边界。
- 每个属性标签只保留第一个结果，不适合多值属性。
- 属性值虽在某个实体的窗口内找到，但没有显式输出“该值为何属于该实体”的绑定证据。
- 三元组以实体文本作为 `group_key` 的一部分；同名实体在不同章节、批次或工艺步骤出现时，缺少稳定 mention/individual 标识。

### 2.3 当前关系抽取

[`relation_extractor.py`](../backend/app/services/extraction/relation_extractor.py) 已具备以下能力：

- 对文档进行本体类分类。
- 调用 `get_relation_schema(doc_class, max_hops=4)` 获取最多四跳的 object property schema。
- 按 extraction profile、method、specialized finder 和 generic finder 分派抽取策略。
- 输出根关系及嵌套 `sub_relationships`。
- 对表格、章节 KV、章节段落和 CMC 领域中的设备、合成路线、风险、残留、存放条件、共线评估、备样生产计划等内容进行抽取。

当前 CMC schema 共发现 47 条边：一跳 12 条、二跳 17 条、三跳 17 条、四跳 1 条。静态复核 `_resolve_strategy` 可直接处理的边为 22 条：一跳 12 条、二跳 5 条、三跳 4 条、四跳 1 条。其余边并不等价于一定抽不到，因为 composite finder 可能内部手工构造部分子关系；但这说明“schema 中存在一条边”尚不能保证通用递归器能够独立抽取它。

最近一次真实 CMC 标注缓存结果如下：

| 指标 | 数量 |
|---|---:|
| 实体三元组 | 36 |
| 带属性实体 | 7 |
| 属性值 | 10 |
| 根关系 | 40 |
| 一级嵌套关系 | 7 |
| 二级嵌套关系 | 16 |
| 文档分类 | CMC Report |

已出现的根关系族包括：使用设备、含质量风险评估、含清洗残留物、含安全风险评估、存放条件、含合成路线、含共线评估数据、含备样生产计划。最新结果中仍未出现 `describes`、`hasCleaningMethod`、`hasDegradationPathway`。

### 2.4 当前完成度判断

下表是面向“文档中某实体类型具有多条、多跳关系，并且需要识别各跳关系实体”这一目标的工程完成度估算，不是单一模型准确率：

| 能力 | 完成度 | 判断 |
|---|---:|---|
| GLiNER 模型供给与推理 | 90% | 模型和依赖正常；主要剩 API 迁移、长文本切分和指标标定 |
| Sentence Embedding 语义归类 | 80% | 已用于本体类型匹配和候选缩窄；尚未成为证据检索器 |
| 三阶段实体/属性抽取 | 65%～70% | 主链可运行；属性归属、多值和精确证据仍弱 |
| CMC 特定关系抽取 | 65%～70% | 已覆盖主要关系族；有明显领域特化和手工组合痕迹 |
| 通用多实体、多跳绑定 | 35%～45% | 已能生成嵌套结构，但缺父实体作用域，复杂文档易错绑 |
| 审核与 ABox 持久化闭环 | 25%～35% | NER 属性候选可进入审核；关系边缺少通用候选、审核和落库语义 |
| **总体目标** | **55%～60%** | 可展示、有实测结果，但尚未形成稳定的通用图谱生产链 |

## 3. 关键问题与根因

### 3.1 实体属性链与关系链弱耦合

三阶段标注链已经得到带类型 span 和属性三元组，关系抽取链却主要重新扫描 `DocStructure`，很少复用前者得到的 mention、类型置信度和精确位置。这会造成：

- 同一个实体被两套逻辑重复识别，文本、类型和位置可能不一致。
- 关系 finder 无法直接从“文档内所有已识别实体”中挑选 range 候选。
- 属性抽取无法利用父关系约束，例如“设备 A 的清洗方法”与“设备 B 的清洗方法”无法天然分开。
- 调试时难以判断错误来自实体召回、类型归类、证据检索还是关系绑定。

### 3.2 递归抽取缺少父实体作用域

当前策略接口只有 `ctx` 和 `edge`，递归到下一跳时，finder 往往再次扫描整篇文档。假设文档内有两条合成路线，每条路线各有三个工艺步骤，每个步骤各使用不同设备，若每一跳都全局搜索，则容易形成：

```text
路线 A → 步骤 A1/A2/A3/B1/B2/B3
路线 B → 步骤 A1/A2/A3/B1/B2/B3
每个步骤 → 文档中所有设备
```

这不是实体识别召回率问题，而是关系绑定缺少条件变量。父实体的 source span、表格行、章节、编号和局部邻域必须成为下一跳检索的过滤条件。

### 3.3 正则和 extraction pattern 被当成最终抽取器

TTL 中的正则、anchor 和 extraction profile 对格式稳定的表格/KV 文档很有效，但其本质应是：

- schema 约束；
- 检索 query 的关键词来源；
- 高精度候选生成器；
- LLM/GLiNER 结果的校验条件。

如果将其作为唯一抽取器，表头变化、同义改写、跨句表达、代词指代和顺序变化都会显著降低召回率。改进方向不是删除正则，而是把正则从“唯一判定”降为“高精度证据和约束”。

### 3.4 Sentence Embedding 尚未用于文档证据检索

当前 embedding 主要用于：

- span 到本体类的类型匹配；
- 文档类型相关类缩窄；
- 部分语义对齐或主题分组。

它还没有回答关系抽取最需要的问题：**对于父实体 P 和谓词 R，文档中哪几条证据最可能描述 range 实体 O？** 因而即使已经加载 `bge-small-zh-v1.5`，关系 finder 仍以全局扫描或 anchor 命中为主。

### 3.5 LLM 未进入实体—关系主链

项目中虽然存在 LLM 相关服务，但当前三阶段标注和多跳关系抽取没有使用 LLM 做以下判定：

- 候选子实体是否确实属于给定父实体；
- 一个句组内哪个属性值属于哪个实体；
- 跨句代词或编号是否指向同一实体；
- 证据不足时应拒答而不是构造关系。

LLM 最适合承担“受约束的绑定与消歧”，不适合直接读取整篇文档后自由生成完整图谱。

### 3.6 关系审核和 ABox 持久化未闭环

当前关系主要保存在 annotation JSON 的 `relationships/sub_relationships` 中，用于展示或报告消费；NER 属性三元组可以转为 `ExtractionCandidate`，但关系边没有等价的通用候选模型和审核流程。

普通候选确认时，`_commit_candidate` 把 `extracted_properties` 直接传给 `project_entities`；而 `OntologyEngine.project_entities` 需要 `kind` 来区分 `class`、`link_type`、`data_property`，并不负责创建普通 ontology individual。因此当前“审核确认”通常没有完整地创建实例及其 object property。

## 4. 目标数据模型：EvidenceUnit、EntityMention 与 GraphCandidate

在调用任何模型前，先建立统一的中间表示。建议最少包含以下对象。

### 4.1 EvidenceUnit

```json
{
  "evidence_id": "doc1:table3:row5",
  "document_id": "doc1",
  "kind": "table_row",
  "text": "步骤 S2；反应釜 R-201；温度 20~25℃",
  "section_path": ["3 工艺", "3.2 合成步骤"],
  "page": 6,
  "table_id": "table3",
  "row": 5,
  "char_start": 4210,
  "char_end": 4240,
  "parent_evidence_id": "doc1:section:3.2",
  "metadata": {}
}
```

建议的 evidence 粒度：

- 普通正文：1～3 个相邻句子组成 sentence group，并保留重叠。
- KV 段落：key 与 value 作为一个单元。
- 表格：一行作为主单元，同时附带多级表头和表题。
- 列表：列表项与其最近标题组成一个单元。
- 章节：作为粗粒度父单元，用于过滤和回退，不直接作为默认 LLM 长上下文。

所有 GLiNER span、属性和关系都应引用 `evidence_id + start/end`，而不是只写“表 X”或“§ 某章节”。

### 4.2 EntityMention

```json
{
  "mention_id": "m-123",
  "text": "R-201",
  "class_iri": "...#Reactor",
  "evidence_id": "doc1:table3:row5",
  "start": 7,
  "end": 12,
  "gliner_score": 0.82,
  "typing_score": 0.91,
  "normalization_key": "reactor:r-201"
}
```

`mention_id` 表示一次文本出现，`normalization_key` 或后续 `individual_id` 表示可能的同一真实对象。必须保留这一区分，不能仅凭相同字符串把所有 mention 合并。

### 4.3 GraphCandidate

建议用统一节点和边候选替代只适合显示的递归 JSON：

```json
{
  "nodes": [
    {"candidate_id": "n1", "mention_id": "m-123", "class_iri": "...#Reactor"}
  ],
  "edges": [
    {
      "candidate_id": "e1",
      "subject_candidate_id": "n0",
      "predicate_iri": "...#usesEquipment",
      "object_candidate_id": "n1",
      "evidence_ids": ["doc1:table3:row5"],
      "evidence_quote": "步骤 S2 使用反应釜 R-201",
      "confidence": 0.87,
      "status": "pending"
    }
  ]
}
```

前端仍可把边投影成 `sub_relationships` 树展示，但数据库和审核层应保持显式 node/edge ID，才能表达共享节点、环、同名实体和非树形图。

## 5. 混合语义检索：把 Sentence Embedding 用在证据定位

### 5.1 检索 query 生成

每一条 schema edge 都可生成一个面向当前父实体的查询：

```text
父实体名称/编号
+ 父实体类标签及同义词
+ predicate label、comment、同义词
+ range class label、父类标签、同义词
+ range extraction anchors
+ 关键 data property 标签
```

例如，正在为“工艺步骤 S2”抽取 `usesEquipment → Equipment` 时，query 可包含：

```text
S2 工艺步骤 使用设备 生产设备 设备名称 设备编号 型号
```

查询不是整篇文档级固定文本，而是随父实体和 schema edge 改变。

### 5.2 候选过滤与排序

先做结构过滤，再做混合召回：

1. 若父 mention 位于表格行，优先当前行、同一行组、同表相邻行。
2. 若父 mention 位于章节，优先同一小节、子小节和相邻句组。
3. 若有稳定编号或交叉引用，加入引用目标 evidence。
4. 在结构候选内同时计算 BM25 和 dense embedding 分数。
5. 使用 RRF 或归一化加权融合，取 top-K 交给 GLiNER/LLM。

推荐初始值：结构强匹配 evidence 全保留，BM25 top-10、dense top-10，融合后最多保留 6～8 个单元。对证据不足的 edge 再扩大到父章节，而不是第一次就搜索全文。

向量库不是 P0 的硬前提。单文档通常只有数百至数千 evidence，可先在进程内批量编码和余弦检索，复用现有 `SentenceTransformerEmbedder`；当需要跨文档检索、持久化缓存或百万级 evidence 时，再按《引入向量数据库的优化方案》引入外部索引。

### 5.3 向量内容与缓存

embedding 输入不应只有正文，建议规范为：

```text
[章节路径] [表题/表头] [Evidence 原文]
```

缓存键至少包含：

```text
document_hash + evidence_id + evidence_text_hash + embedding_model_version
```

本体 schema query 的向量可按 `ontology_version + edge_iri + query_template_version` 缓存。TTL 变化时只需失效 query 侧缓存，不必重新编码未变化的文档 evidence。

## 6. GLiNER 在目标方案中的使用方式

GLiNER 保留两层用途，但不单独负责建立关系。

### 6.1 第一层：文档级广召回

沿用当前三阶段第一步：

- 标签使用“设备、药物、人员、地点、工艺步骤、风险”等通用类标签。
- 一次批量处理 evidence/chunk，召回实体 mention。
- GLiNER 标签仅作弱先验，最终 class 仍由本体语义归类和 TTL 范围约束决定。
- 输出必须保留原文字符偏移并回映射到 evidence。

这一层追求 recall，生成全局 mention inventory，供后续各条 edge 复用。

### 6.2 第二层：edge 定向补召回

当某个父实体的某条 schema edge 没有足够 range 候选时，只在混合检索得到的 top-K evidence 中再次调用 GLiNER：

- 实体标签：range class label、父类/子类标签、TTL 同义词。
- 属性标签：该 range class 的 data property label。
- 不再把数十个无关类标签一起送入模型。
- 与第一层已存在 mention 做 span 去重和类型合并。

例如 `Step --usesEquipment→ Equipment` 的定向标签只包含设备及其子类、设备名称、设备编号、型号等，而不是整套本体类。这样既利用零样本泛化，又用 schema 控制误召回。

### 6.3 GLiNER 不应承担的职责

- 不以 GLiNER 返回的 label 直接决定最终本体类。
- 不仅凭两个实体在同一窗口出现就建立关系。
- 不让 GLiNER 自由生成 TTL 中不存在的 predicate。
- 不用超出模型 token 上限的整章节输入换取“更多上下文”。

### 6.4 长文本切分和 API 迁移

切分必须以模型 tokenizer 的 token 数为准，而不是字符数。建议：

1. Evidence 小于安全阈值时直接推理。
2. 超长正文按句子切成不超过约 320 token 的 chunk，保留 32～64 token 重叠。
3. 超宽表格按逻辑列组拆分，但每个 chunk 重复表题、表头和父实体标识。
4. 推理后将 chunk 内偏移映射回 evidence/document 偏移。
5. 对重叠区结果按位置、类型和分数去重。

同时封装 GLiNER 新旧 API 的兼容适配层，用固定回归样本确认 `GLiNER.inference` 迁移前后 span、score 和 batch 顺序没有非预期变化。

## 7. 父实体约束的多跳递归抽取

### 7.1 递归状态

每次展开一条 edge，至少携带：

```python
ExtractionState(
    parent_node,          # 当前 subject candidate
    parent_mention,       # subject 的文本位置
    edge,                 # 当前 TTL object property schema
    evidence_scope,       # 当前允许检索的 evidence 范围
    path,                 # 已走过的 class/predicate，防环
    hop,                  # 当前跳数
    confidence,           # 路径累计置信度
)
```

递归逻辑建议为：

```python
def expand(state):
    evidence = retrieve(state.parent_mention, state.edge, state.evidence_scope)
    mentions = find_or_recall_range_mentions(state.edge, evidence)
    bindings = bind_subject_object(state.parent_node, state.edge, mentions, evidence)
    valid_edges = validate_and_rank(bindings, ttl_schema=state.edge)

    for graph_edge in valid_edges:
        yield graph_edge
        child_scope = derive_child_scope(graph_edge.object, graph_edge.evidence)
        for next_edge in outgoing_schema(graph_edge.object.class_iri):
            yield from expand(next_state(graph_edge, next_edge, child_scope))
```

### 7.2 evidence scope 的继承规则

不同结构使用不同绑定强度：

| 场景 | 子跳默认作用域 | 绑定强度 |
|---|---|---|
| 同一表格行 | 当前行及合并单元格继承内容 | 最强 |
| 编号列表 | 当前列表项及其子项 | 强 |
| 明确小节 | 当前小节及子小节 | 强 |
| 相邻句组 | 父 mention 所在句组及前后各一组 | 中 |
| 交叉引用 | 当前证据 + 被引用目标 | 中 |
| 仅全文同现 | 不直接建边，只作回退候选 | 弱 |

子节点可以扩大作用域，但必须记录触发原因。例如当前行无设备信息且文本出现“设备见表 4”，才跟随引用进入表 4。不能因为局部证据为空就无条件把同类型的全文实体全部挂到当前父节点。

### 7.3 composite finder 的处理

现有 CMC specialized/composite finder 不必一次性删除。建议把它们逐步改造成统一接口的高精度 provider：

- 输入父节点和 evidence scope。
- 输出标准 EntityMention/GraphCandidate，不直接拼最终展示树。
- 手工构造的子关系也通过同一 TTL validator。
- generic retrieval + GLiNER + LLM 作为兜底，而不是与 specialized finder 形成第二套结果模型。

## 8. LLM：只做有证据、受约束的关系绑定

### 8.1 触发条件

LLM 不应默认处理所有 entity pair。优先通过下列低成本路径确认：

- 同一结构化表格行且列语义明确；
- TTL 正则/profile 唯一命中；
- 父子编号或引用关系唯一；
- 高置信 specialized finder 命中。

仅在以下情况调用 LLM：

- 一个 evidence 中有多个同类型父/子实体，需要消歧。
- 关系跨句表达或存在代词、简称、步骤编号。
- 正则/GLiNER/检索结果相互冲突。
- top-2 绑定分数接近。
- 需要判断“未提及/不适用/否定”而非正向关系。

### 8.2 输入约束

每次请求只提供：

- 当前父实体及其 mention。
- TTL 允许的一个或少量 predicate。
- 每个 predicate 的 domain、range、label、comment 和 cardinality。
- GLiNER 已找到的候选 object/属性值及 ID。
- top-K evidence 原文及 ID。

禁止把整篇文档和全部本体一次性交给 LLM。输入范围越明确，成本、幻觉和跨实体串联越容易控制。

### 8.3 结构化输出

LLM 只能选择已有 ID 或拒答，例如：

```json
{
  "subject_id": "n-step-s2",
  "predicate_iri": "...#usesEquipment",
  "object_id": "m-r201",
  "decision": "entailed",
  "evidence_id": "doc1:table3:row5",
  "quote": "步骤 S2 使用反应釜 R-201",
  "reason": "同一表格行且动词明确",
  "confidence": 0.92
}
```

约束规则：

- `subject_id`、`object_id`、`predicate_iri` 必须来自输入枚举。
- `quote` 必须是 evidence 的连续原文子串，并由程序二次校验。
- 没有直接证据时返回 `not_enough_evidence`。
- 否定陈述返回 `contradicted`，不创建正向边。
- 不允许补写原文不存在的属性值、设备编号或实体名称。

若确有必要发现 GLiNER 漏掉的新 object，可单独提供 `proposed_span` 模式，但 start/end 和原文必须可校验，且其置信等级低于“选择已有候选”。

### 8.4 本地与云端模型

当前配置已经具有本地 LLM 与云端门控能力。关系绑定建议优先走本地模型，并设置独立 feature flag、超时、并发数和最大证据数；不可用时降级到结构规则 + GLiNER + embedding，不应阻塞整篇抽取。涉及受控或敏感文档时，默认禁止将原始 evidence 发往云端。

## 9. TTL 校验与置信度融合

### 9.1 硬校验

模型输出后必须由确定性代码验证：

- predicate 是否存在于当前 schema。
- subject class 是否满足 domain。
- object class 是否满足 range，包含子类闭包。
- data property 值是否能转换为 TTL datatype。
- functional/max cardinality 是否冲突。
- 路径是否超过最大 hop 或形成无意义循环。
- evidence quote 是否真实存在且偏移有效。

硬校验失败的候选不得自动提交；可标记为 rejected 或进入“schema/类型冲突”专项审核。

### 9.2 软分数

建议保存分项分数，不只保存一个最终 score：

```text
S = 0.20 × GLiNER span
  + 0.20 × ontology typing
  + 0.20 × hybrid retrieval
  + 0.25 × relation binding
  + 0.15 × structure proximity
```

这只是初始权重，应通过标注集校准。规则/profile 唯一命中可以作为额外强特征，LLM 自报 confidence 不能直接等同于概率。多跳路径置信度建议取边分数的几何平均或最小值，并同时显示最弱边，避免跳数越多简单相乘导致分数不可解释。

建议分级：

- 高置信且无约束冲突：可进入快速审核队列。
- 中置信：必须人工确认。
- 低置信或证据不足：仅保留诊断，不创建图边候选。

## 10. 审核、实体消歧与 ABox 落库

### 10.1 审核单元

审核界面应以“父节点及其局部子图”为单元，而不是把每条边完全孤立展示。至少同时呈现：

- subject 和 object 的类型、原文位置及标准化名称。
- predicate 的中英文标签。
- 精确证据 quote，并可跳转原文。
- 该节点的属性值。
- 当前路径的上游父节点。
- 各阶段置信度和校验告警。

审核动作应支持：确认边、拒绝边、换绑 object、合并节点、拆分同名节点、编辑属性。

### 10.2 实体消歧

候选合并依次使用：

1. 本体类兼容性。
2. 领域唯一标识，如设备编号、物料编码、批号、步骤编号。
3. 标准化名称和同义词。
4. 结构与关系邻域。
5. embedding 相似度。

只有名称相同而编号、章节关系不同的 mention 不应自动合并。反之，同一设备的全称、简称和编号可在证据充分时映射到同一 individual。

### 10.3 提交顺序

审核通过后的事务建议按以下顺序执行：

1. 根据 normalization key 查找已有 individual。
2. 不存在时创建 individual，并设置 `rdf:type` 和 label。
3. 写入 data property，处理 datatype 和 cardinality。
4. 所有端点均存在后写入 object property。
5. 写入 `extractedFrom`、evidence ID、job ID、模型/规则版本等 provenance。
6. 提交 shadow/搜索索引和 ontology store；失败时整体回滚或进入可重试 outbox。

需要为普通实例提供明确的 create/upsert individual 服务；不能继续把缺少 `kind` 的属性字典传给面向 TBox 投影的 `project_entities`，并假定其已经创建实例。

## 11. 分阶段实施计划

### P0：统一证据和修正现有链路

目标：不引入 LLM，也能显著降低父子错绑并建立可量化基线。

- 建立 EvidenceUnit 和 EntityMention 中间表示，统一段落、句组、表格行的 source ref 和字符偏移。
- 让关系抽取复用三阶段标注得到的 typed spans，而不是全量重复识别。
- 为 strategy/finder 增加 `parent_endpoint` 与 `evidence_scope`。
- specialized finder 先按表格行、章节、编号约束，不再无条件全局扫描。
- 属性抽取从固定 ±200 字符改为“同表格行/同句组优先，字符窗口回退”，支持同属性多值。
- 迁移 deprecated GLiNER batch API；实现 tokenizer 感知切分和偏移回映射。
- 将当前 CMC 实测文档固化为回归基线，逐条标记 47 条 schema edge 的 supported/unsupported/delegated 状态。

P0 完成后应先验证交叉绑定错误明显下降，再引入 LLM，否则 LLM 会掩盖中间表示和作用域设计问题。

### P1：混合检索与受约束 LLM 绑定

目标：提升自然语言改写、跨句关系和无固定模板文档的泛化能力。

- 基于现有 BGE 模型建立文档内 evidence 向量索引。
- 加入 BM25 + dense + 结构邻近的混合检索。
- 实现 edge-directed GLiNER 补召回。
- 实现只选择候选 ID 的结构化 LLM binder 和严格拒答。
- 实现 TTL domain/range/datatype/cardinality validator。
- 保存分项置信度、检索候选和 LLM 原始结构化响应，支持回放。
- 所有新能力均使用 feature flag；LLM 不可用时保持确定性链路可运行。

### P2：图候选审核和 ABox 闭环

目标：让抽取结果从“报告展示数据”变为“可治理的知识图谱数据”。

- 建立 GraphCandidate node/edge 数据结构或表。
- 提供局部子图审核、换绑、合并、拆分能力。
- 实现 individual upsert、object property 提交和事务/重试机制。
- 建立跨文档实体消歧和 provenance 查询。
- 数据规模达到阈值后，再决定是否引入持久化向量数据库。

## 12. 验收指标与回归测试

### 12.1 标注集设计

不能只用“每类只有一个实体”的文档验收。至少覆盖：

- 同一文档 2～5 个同类型父实体，各自具有不同子实体。
- 三跳和四跳路径。
- 同名但不同对象，以及异名但同一对象。
- 表格、正文、列表、跨句和交叉引用。
- 正向、否定、未提及、不适用。
- 表头改写、同义表达、字段顺序变化和少量 OCR 噪声。

标注对象应包含 mention span、class、data property、object property、精确 evidence、实体共指和完整 path。

### 12.2 核心指标

| 层级 | 指标 |
|---|---|
| 实体 | span precision/recall/F1，按类统计 |
| 类型 | ontology class accuracy、macro-F1、top-k recall |
| 属性 | value exact/normalized match、subject-binding accuracy、多值召回 |
| 单边关系 | predicate precision/recall/F1、subject-object binding accuracy |
| 多跳关系 | 2/3/4-hop path exact match、路径完整率 |
| 证据 | quote exact match、evidence recall@K |
| 图质量 | cross-parent binding error、重复节点率、约束冲突率 |
| 工程 | 单文档耗时、GLiNER/embedding/LLM 分阶段耗时、降级成功率、人工修改率 |

建议把 **cross-parent binding error** 设为发布阻断指标。即使实体和单边 F1 较高，只要同类型父实体之间经常互相挂错子节点，就不能认为多跳抽取达标。

可作为首轮目标的建议值：

- evidence recall@8 ≥ 95%。
- subject-object binding accuracy ≥ 90%。
- cross-parent binding error ≤ 3%。
- 二跳 path exact match ≥ 85%，三跳 ≥ 75%。
- 所有自动确认关系均有可定位的精确原文证据。

这些值需在完成首批人工金标后重新校准，不应直接作为模型宣传指标。

### 12.3 消融测试

每次发布应分别评估：

1. 仅正则/profile。
2. 正则/profile + GLiNER。
3. 再加 embedding retrieval。
4. 再加 LLM binder。
5. 完整 TTL validator 与父实体 scope。

这样才能确认泛化提升来自哪一层，并避免 LLM 提高召回的同时引入更多错误边。

## 13. 可观测性与降级

每个 job 至少记录：

- 文档/evidence 数量及超长 chunk 数。
- GLiNER 调用批次、标签数、截断数、候选数和耗时。
- embedding 模型版本、缓存命中率、检索 recall 诊断。
- 每条 schema edge 的检索 top-K、策略来源和最终候选数。
- LLM 调用数、拒答率、JSON 校验失败率、超时率和 token 数。
- TTL 硬校验拒绝原因。
- 每一跳展开前后的候选数量，识别笛卡尔积异常。
- 审核确认、换绑、拒绝、合并的比例。

推荐降级顺序：

```text
LLM 不可用
  → 结构规则 + profile/regex + GLiNER + embedding
embedding 不可用
  → 结构过滤 + BM25 + profile/regex + GLiNER
GLiNER 不可用
  → 结构规则 + profile/regex，并明确标记 degraded
```

任何降级都应写入 job 结果，避免把“模型未运行”误认为“文档没有实体或关系”。

- [word 报告内容识别导致的关系图谱识别问题](word报告内容识别导致的关系图谱识别问题.md)：Word 结构和关系识别问题。

本方案新增的核心不是某一个模型，而是四项组合原则：

1. **结构先行**：先把文档变成可寻址的 evidence。
2. **父实体约束**：每一跳只在父实体相关证据内寻找子实体。
3. **模型分工**：GLiNER 找边界，embedding 找证据和类型，LLM 做受约束绑定，TTL 做最终校验。
4. **图式闭环**：抽取结果以节点/边候选审核，并最终创建 ABox individual 和 object property。

只有这四项同时成立，系统才能从“模板和正则驱动的关系展示”演进为对多实体、多跳、自然语言改写具有稳定泛化能力的知识图谱抽取系统。
