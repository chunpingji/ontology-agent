# 引入向量数据库的优化方案

> 状态：方案讨论稿（未涉及编码）
> 协作：本方案由架构分析 + Codex CLI（`codex exec`）双向审辩形成
> 适用范围：SLPRA 临床药物共线生产风险评估知识工程平台

---

## 0. 核心结论（TL;DR）

向量数据库应作为 SLPRA 的**语义检索层和持久化向量层**，**不能替代** OntologyEngine、OWL 推理、精确 ID 索引或现有规则引擎。

核心设计原则：**「向量召回，知识图谱裁决」**

- 向量库负责从十万级对象中快速找出几十个候选；
- OntologyEngine 负责类别层级、关系合法性、规则约束和最终事实确认；
- IRI / ID / 规范编码等强标识仍走精确索引；
- ANN 结果**绝不**直接作为实体合并或知识事实。

技术选型双路线：

| 突出痛点 | 推荐方案 |
|----------|---------|
| 给现有实体加向量相似检索（对齐加速、类型推断、跨进程缓存） | **pgvector**（复用 PostgreSQL，与本体表可 JOIN，最低风险） |
| 文档证据检索质量、精确术语+语义融合、离线索引迭代、自然语言查询 | **LanceDB 作文档检索侧车**（hybrid search 是关键差异） |

两者**不互斥，可混合分层**：PostgreSQL/pgvector 是事实源与 KG 相邻向量层，LanceDB 是可重建的文档证据检索投影。

## 3. 各模块改进点与收益

| 模块 | 向量数据库带来的改进 | 收益 |
|------|-------------------|------|
| **semantic.py** | 拆三层：Embedder(推理) + EmbeddingCache(持久化) + VectorStore(索引)；`model_fingerprint + text_hash` 作缓存键 | 冷启动分钟级→秒级；跨进程共享 |
| **aligner.py** | ANN top-K 检索(附 class_iri 过滤) + 重排；O(N)→O(log N)+O(K) | 十万个体时秒级→毫秒级 |
| **ontology_typer.py** | 类向量预计算+持久化；类文本扩展(label+定义+父类路径+典型属性) | 歧义类区分度↑；跨进程复用 |
| **sentence_grouping.py** | 句向量按 `doc_id + content_hash` 持久化 | 重跑场景~零编码开销 |
| **document_classifier.py** | 混合分类：规则分 + 文档类型 prototype cosine 分 | 召回无关键词但语义相近文档 |
| **关系抽取** | 向量检索定位证据段落/表格行，缩小 finder 作用域 | 减少无效扫描，同义召回↑ |
| **语义查询（新能力）** | 自然语言→本体术语链接→受约束查询→KG 事实→向量证据回溯 | 完全新增 |

### 3.1 aligner.py 改造流程

```text
候选 ID
   ├─ 精确 ID 索引命中 ───────────────► 直接裁决
   └─ 未命中
        ├─ 规范化标签精确/倒排检索
        └─ 向量 ANN 检索 top 20~100
                 │
                 ▼
        类层级过滤 + 字面重排 + 语义重排
                 │
                 ▼
        merge / review / new
```

要点：
- ID 属性走普通唯一/哈希索引，**不用**向量检索；
- ANN 查询附带类别过滤（`class_iri == target` / `in descendants` / `in ancestors`）；
- ANN 只缩小候选集，对召回结果继续算精确 cosine + SequenceMatcher；
- 保留现有 subclass→same→parent 裁决与等分歧义逻辑（FR-017）；
- 自动合并保留硬门槛：仅语义高通常进 review，top1/top2 接近进 review。

推荐评分示意（可调）：

```text
final_score = 0.55*semantic + 0.25*lexical + 0.15*attr_consistency + 0.05*source_reliability
```

风险：ANN 有召回误差。**实体自动合并必须优先保证召回率**，用离线标注集评估 Recall@K，K 不宜过小；ANN 召回不到应退化为 `new/review`，绝不能错误合并。

### 3.2 自然语言知识图谱查询链

例："哪些设备有清洗验证问题？"

```text
自然语言
  → 本体术语链接（"设备"→Equipment 及子类；"清洗验证问题"→相关 E1/E2/E3）
  → 查询意图/关系路径
  → 受约束查询（OntologyEngine 方法调用 + 图遍历）
  → KG 精确结果
  → 向量证据补充（文档 chunk 溯源）
  → 返回设备、问题类型、关系路径、证据
```

> **注意**：本项目 OntologyEngine 基于 Owlready2/SQLite，**不暴露 SPARQL endpoint**。语义查询应构造为 OntologyEngine 的 Python 方法调用（`get_individuals(filter)` + 图遍历），而非生成 SPARQL 执行。

## 4. 统一索引策略

### 4.1 逻辑索引划分（不应混为一个集合）

| 索引 | 对象 | 更新频率 | 关键过滤字段 |
|------|------|---------|------------|
| `ontology_terms` | E1 class / E2 property / E3 data_prop / E11 / E12 | 随本体发布 | kind, module, snapshot_id |
| `individuals` | A-Box 个体标签 | 中高（抽取入库） | class_iris, ancestor_iris, status |
| `document_chunks` | 句子/段落/表格行 | 高（文档上传） | document_id, doc_type, section |
| `document_types` | 文档类型 prototype | 低 | snapshot_id |
| `embedding_cache` | text_hash→vector (KV) | 按需 | model_fingerprint |

### 4.2 向量文本构造（不能只存 label）

```text
# 类向量文本示例
名称：反应釜
英文：Reactor
定义：用于进行化学反应的工艺设备
父类路径：设备 > 工艺设备 > 反应设备
典型属性：材质、容积、设备编号

# 个体向量文本示例
名称：R-101
别名：一号反应釜
类型：反应釜
关键属性：材质 316L；容积 1000L
```

每类对象应有独立的 `text_builder_version`。结构字段既可入嵌入文本（用于语义），也必须单独存 metadata（用于精确过滤）。

### 4.3 元数据设计（通用字段）

```json
{
  "object_id": "稳定唯一业务 ID/IRI",
  "kind": "class|object_property|data_property|individual|rule|chunk",
  "ontology_snapshot_id": "sha256:...",
  "model_fingerprint": "bge-small-zh-v1.5:...",
  "embedding_dim": 512,
  "normalized": true,
  "text_hash": "sha256:...",
  "text_builder_version": 2,
  "active": true
}
```

### 4.4 混合检索

实体对齐与自然语言查询都适合：

```text
精确 ID / keyword / lexical + dense vector + KG filter + rerank
```

向量数据库**不能替代**：IRI/ID 精确索引、中文名称规范化匹配、字符串编辑距离、类层级约束、domain/range 约束。

## 5. 技术选型（离线 / 空气隔离）

### 5.1 通用向量库对比

| 方案 | 优点 | 缺点 | 建议 |
|------|------|------|------|
| **pgvector** | 复用现有 PostgreSQL；SQL/事务/备份/metadata join 简单；air-gap 易部署 | 极大规模与高级向量功能弱于专用引擎 | **当前项目首选** |
| Qdrant | 单机部署简单；过滤强；HNSW 成熟；named/sparse vector | 新增独立服务与一致性运维 | 十万→千万级、检索压力高时 |
| Milvus | 大规模分布式 | 组件多、air-gap 镜像管理重 | 当前规模过度设计 |
| ChromaDB | 原型开发快、可嵌入 | 生产并发/运维/演进有限 | 仅开发验证 |
| **LanceDB** | 嵌入式无服务；hybrid search 原生；多模态列式；版本化 | 与 PG 事务不共享；多进程并发写弱 | **文档证据检索侧车** |

### 5.2 空气隔离要点

- 固化 Python wheel、数据库扩展包、容器镜像；
- 模型目录只用本地路径并记录 SHA-256，禁止运行期自动下载；
- 建立离线升级包与 SBOM；
- 备份需同时覆盖 PostgreSQL、向量索引配置、索引 manifest；
- 向量数据可重建但耗时，应保留快照。

> 符合空气隔离原则 VI：仅阻断公网/云，pgvector 作为 PG 扩展、LanceDB 作为嵌入式库均为内网/进程内组件，在合规范围内。

## 6. LanceDB 专题：文档处理能力的加强作用

### 6.1 先厘清误区

LanceDB **不解析文档**——不做 docx/excel 版面解析、表格还原、OCR、中文分词或 chunk 切分。这些仍由现有流水线（`docx_structure.py`、`sentence_grouping.py`）完成。

LanceDB「文档处理能力」的真正含义：**解析后的证据 chunk 如何被统一存储、混合检索、版本切换和离线部署**。它是「文档证据检索层」，不是「文档解析器」。

### 6.2 加强作用最显著的三个场景

| 场景 | LanceDB 独特价值 | 对应模块 |
|------|----------------|---------|
| **① 监管证据检索（最大价值）** | 原生 hybrid search：BM25 + 向量 + reranking 同表/SDK 内完成 | 关系抽取证据定位、自然语言查询 |
| **② 关系抽取证据溯源** | chunk 原文 + 向量 + 文档坐标（页码/sheet/cell）共表；结果记 `source_chunk_id` | endpoint-finder 缩小作用域 + 审计回溯 |
| **③ 离线索引迭代** | 嵌入式无独立服务；列式格式适合批量重算 embedding/评测 | 空气隔离部署 + 模型迭代 |

### 6.3 Hybrid Search 为何对中文监管文档关键

监管文本同时存在两类查询需求：

```text
词面必须精确        →  国药准字H2024xxxx、批号、标准号、CMC 缩写、化学名
语义相近但表述不同  →  "变更原料药供应商" ≈ "新增 API 生产场地"
```

纯向量检索失败模式：把格式相似的批准文号召回却没命中准确编号；罕见 CMC 缩写 embedding 不稳定；长 chunk 一般性语义掩盖关键限定词（「不得」「不适用」「未批准」）。

纯 BM25 又漏掉同义表达与上下位概念。

推荐检索链：

```text
结构化精确匹配/过滤
      ↓
BM25 词面召回 + 向量语义召回
      ↓
分数融合（如 RRF）
      ↓
领域 reranker
      ↓
返回带页码、sheet/cell、chunk_id 的证据
```

**动态加权**：编号查询偏词面+精确过滤，概念性问题偏向量，复杂问句再用 reranker。

> ⚠️ **警示**：Tantivy 有全文检索能力 ≠ 开箱即用的中文监管分词。中文/英文缩写/数字编号混排的 tokenizer 需实际验证甚至定制。批准文号/批号**不应依赖 BM25**——应在入库时抽取为规范化字段走精确等值过滤（与现有 `国药(准|试)字[HZSBTFJ]\d{8}` 正则思路一致）。

### 6.4 建议的 chunk 表结构

```text
chunk_id

ontology_snapshot_id
```

### 6.5 版本化与 ontology_snapshot 双索引切换

契合但**不等价**，应分层管理：

```text
ontology_snapshot_id   →  业务语义版本（必须显式保存，权威在 PostgreSQL registry）
Lance table version    →  物理提交版本（读一致性、回滚、审计辅助）
```

双索引切换模式：

```text
1. 当前快照 S1 保持在线读取
2. S2 写入独立表（或同表独立分区）
3. 为 S2 构建索引 + 离线评测
4. PostgreSQL registry 将 active 从 S1 切为 S2
5. 查询显式带 ontology_snapshot_id=S2
6. 出问题把 active 指针切回 S1
```

> **纠正**：不能把 Lance table version 当作 `ontology_snapshot_id`，也不能把 time-travel 当正式业务审计日志。zero-copy ≠ 免费——旧版本/索引/碎片仍需 compaction 与保留策略。

## 7. 混合架构：pgvector + LanceDB 分层

```text
┌─────────────────── PostgreSQL / SQLite（事实源）────────────────┐
│ A-Box 个体、实体主键与关系约束                                   │
│ 本体快照 registry + active 指针                                  │
│ 唯一性/外键/状态机/ACID 事务                                     │
│ 批准文号等主数据精确查询、人工审核、权限审计                     │
│ （可选）pgvector：KG 相邻的 class/property/individual 向量       │
└──────────────────────────┬──────────────────────────────────────┘
                           │  稳定 ID 关联（entity_id / chunk_id）
┌──────────────────────────▼──────────────────────────────────────┐
│ ──────────────── LanceDB（可重建的检索投影）────────────────    │
│ 原始 chunk + 检索文本 + 向量 + 文档定位（页码/sheet/cell）      │
│ BM25 / 向量 / hybrid retrieval + reranking                      │
│ 关系抽取证据候选、embedding 重算、快照对比、离线评测            │
└─────────────────────────────────────────────────────────────────┘
```

关系抽取流程改造示例：

```text
LanceDB 找证据 chunk → 模型生成关系候选 → PostgreSQL 校验快照/实体
    → 规则/人工审核 → 事务写入 A-Box → 保存 source_chunk_id 溯源
```

**关键约束**：LanceDB 永远是「可重建的检索投影」，绝不成为与 PostgreSQL 竞争的第二权威源。

## 8. VectorStore 抽象层设计

不让 `aligner.py`、`ontology_typer.py` 直接依赖 pgvector 或 LanceDB SDK。

```python
class VectorStore(Protocol):
    def ensure_index(self, spec: IndexSpec) -> None: ...
    def upsert(self, index: str, records: Sequence[VectorRecord]) -> None: ...
    def search(self, index: str, query: VectorQuery) -> list[SearchHit]: ...
    def fetch(self, index: str, ids: Sequence[str]) -> list[VectorRecord]: ...
    def delete(self, index: str, ids: Sequence[str]) -> None: ...
    def delete_by_filter(self, index: str, filters: dict) -> int: ...
    def health(self) -> dict: ...
```

层级结构：

```text
VectorStore (协议)           ← PgVectorStore / LanceDBStore
    ↑
EmbeddingService (协议)      ← 内存LRU → 持久化cache → SentenceTransformer
    ↑
OntologyVectorIndex (领域)   ← search_classes / search_individuals / search_chunks
    ↑
业务模块                     ← aligner / ontology_typer / document_classifier
```

业务模块调用示例（hierarchy/snapshot/model filter 集中管理）：

```python
hits = ontology_index.search_individuals(
    query_text=candidate_label,
    target_class_iri=target_class_iri,
    include_descendants=True,
    include_ancestors=True,
    top_k=50,
)
```

### 8.1 同步机制（架构分析对 Codex 的修正）

- Codex 建议 outbox + 异步 worker。**本方案倾向**：当前单体架构、个体写入并发低（手动确认入库），应优先用**同步事务写入**（个体入库时同事务 upsert 向量行），仅在写入量激增后才引入 outbox 异步。
- reconciliation 频率：优先用 **version 比对**（向量记录存 `entity_version`，查询结果校验版本，不一致则懒更新），而非定期全量对账。

## 9. 迁移路径

| 阶段 | 内容 | 对现有代码影响 | 依赖 |
|------|------|-------------|------|
| **0. 基线** | 记录 align 延迟/准确率、type_spans F1、embedding 重算耗时、实体对齐 P/R、各类与个体数量 | 零 | 无 |

| **2. T-Box 预计算** | 离线命令预计算 class/property 向量入 pgvector | 新增 CLI command | pgvector 扩展 |
| **3. type_spans 切换** | `VECTOR_CLASS_SEARCH_ENABLED` flag；向量 top-K + 现有 threshold/depth 逻辑 | ontology_typer.py 加 if/else | 阶段 2 |
| **4. individual 索引** | 全量 backfill + create/update 同步入向量 | 新增 index 写入逻辑 | 阶段 1 |
| **5. align_entity ANN** | 双跑对比→切换；ANN top-50 + 现有 hierarchy 重排 | aligner.py 加新路径 | 阶段 4 |
| **6. 混合文档分类** | 规则 + semantic prototype 融合 | document_classifier.py 扩展 | 阶段 2 |
| **7. chunk 索引 + 语义查询** | LanceDB 文档 chunk 索引 + NL→本体→KG 查询链 | 新模块 | 阶段 2+4 |

```python
class CachedEmbedder:

    def embed_many(self, texts: list[str]) -> None:

        # 2. 按 text_hash 批量查持久化缓存
        # 3. delegate 只编码 miss
        # 4. 批量写回持久化缓存 + LRU
        ...
```

现有 aligner、typer、sentence_grouping 与测试桩 `DeterministicEmbedder` **无需修改**。

### 9.2 关键兼容约束

- 现有 `Embedder` 协议 `embed_many() → None` 签名不变（阶段 1-5）；
- 测试桩继续注入无需修改；
- `is_available() → False` 时整条路径优雅降级到字面匹配；
- Feature flag 全程保护，向量库不可用时退化到现有行为。

## 10. 风险与代价

| 风险 | 严重度 | 缓解 |
|------|--------|------|
| **ANN 召回误差导致错误合并** | 🔴 高 | 自动合并优先 Recall；离线标注集评估 Recall@K；召回不到退化 new/review |
| **LanceDB 与 PostgreSQL 事务不共享** | 🔴 高 | 稳定 ID + 幂等写；快照状态机 `preparing→ready→active→retired`；LanceDB 为可重建投影 |
| **多进程并发写（LanceDB）** | 🟡 中 | 「多进程计算，单写入者批量提交」；文档 chunk 批量导入需压测文件锁/compaction |
| **双存储运维** | 🟡 中 | 两套备份/监控/一致性巡检；空气隔离依赖封装；灾备恢复到相互匹配快照 |
| **中文分词质量（Tantivy）** | 🟡 中 | 实际验证/定制 tokenizer；编号类走规范化字段精确过滤 |

## 11. 架构分析对 Codex 建议的质疑与补充

1. **多向量策略过早**：Codex 建议 name_vector + description_vector。对 201 类 + 数万个体规模，单向量（丰富化文本）够用。Named vectors 增加写入复杂度，仅在评估发现单向量 recall 不足时引入。
2. **SPARQL 不是当前主路径**：本项目 OntologyEngine 基于 Owlready2/SQLite 不暴露 SPARQL，语义查询应构造为 Python 方法调用 + 图遍历。
3. **reconciliation 频率**：outbox + 定期对账对当前规模过度设计，优先 version 比对懒更新。
4. **句组分割不需向量库**：`sentence_grouping.py` 相邻句 cosine 计算不应走远程向量库——需要的是缓存（减少重编码），不是 ANN 检索。
5. **类索引规模保护**：类小于 ~500（当前 201 类在线计算仅 ~0.3ms）时保留内存精确矩阵作稳定兜底，Feature flag 控制切换。
6. **embedding_cache 不进 ANN 索引**：纯 text_hash→vector 是 KV 查询，用 PostgreSQL 普通表，不占用 ANN 索引资源。

## 12. 最终推荐组合

| 决策项 | 推荐 |
|--------|------|
| 嵌入模型 | 继续本地 bge-small-zh-v1.5（512 维），air-gap 本地加载 |
| KG 相邻向量层 | PostgreSQL + pgvector（首选），预留 Qdrant 切换口 |
| 文档证据检索层 | LanceDB（当证据溯源/语义查询成为明确需求时引入） |
| 第一优先级 | 阶段 1（缓存持久化）— 最低风险、最直接收益 |
| 最大业务价值 | 阶段 5（align ANN）— 解决十万级个体扩展性 |
| 最大新能力 | 阶段 7（语义查询 + LanceDB hybrid）— 依赖前置阶段成熟 |
| 数据边界铁律 | PostgreSQL 是事实源，向量库是可重建的检索投影 |

**一句话总结**：
- pgvector 先解决「跨进程缓存」+「十万级实体对齐扩展性」（既有痛点，风险最低）；
- LanceDB 的文档处理能力集中在「解析后的证据 chunk 混合检索与溯源」，是 pgvector 的补充（文档证据层），不是替代（KG 相邻向量层）；
- 全程不破坏现有 `Embedder` 协议、测试桩与优雅降级行为。
