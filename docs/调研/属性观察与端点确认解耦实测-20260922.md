## 实现

- 发现协议将叙述字段放在各实体的 `source_fields` 中，明确原标签与单个完整原值；
  无法归属的字段放在 `unowned_fields`。所有有效引用先保存，不要求类型或关系成立。
- 没有专名的具体计划、步骤和事件用 `name=null` 加原文 anchor 定位。
  类型候选提出后先核对实体，避免把展示角色名误当作虚构专名。
- 属性观察通过原字段 ID 关联候选主体。公开响应和界面展示原值、候选主体及引用；
  未决或拒绝主体不删除原文观察。
- 确认主体后才提供范围的 lower/upper 组件；同一原字段可映射多个当前合法属性。
  程序仅拆分完整、明确且单位一致的区间，保留原值，不做单位换算。
  属性核验检查主体、区间边界和谓词定义，不要求关系路径先被采信。
- 同一原字段的不同范围组件不能同时写入同一谓词。冲突时保留完整原值与原因，
  不把一个区间变成同一泛化属性的两个独立值。
- 后续窗口确认主体后，直接复用已保存且未处理的字段继续对齐；不重新发现数值。

以上均在独立 `document_harness` 内实现，不修改权威本体，不引入领域 IRI 特判、
旧抽取协议、数据库表或执行历史快照。主服务尚未重启加载本次改动。

## 实测中发现的协议缺口

初次原文发现召回了相关卡，但 `source_fields=[]`，遗漏了叙述批量。
改成逐实体字段后，模型保存了整句，却用同一整句充当 label 和 value，仍不能
安全拆分数值。这两种结果都没有算作批量属性成功。

进一步进行无业务数据的小型传输对照：阶段 instructions 能正常送达；仅存在于
JSON Schema description 中的要求没有被执行，显式把同一 Schema 放入模型输入后
才被执行。隐式 Schema 对照返回 `9`，可读 Schema 对照返回要求的
`SCHEMA_VISIBLE_82741`。说明当前服务的解码约束不能代替模型可读协议。

因此所有新阶段显式传入 `{input, schema}`，同时保留相同的严格解码 Schema。
预算估计原本就包含该 Schema，修复未扩大输出上限、未截断原文或放宽事实采信。

后续还发现批量类型对齐会把“某个类型已被其他候选选择”作为当前候选返回 null
的理由。新增通用协议约束：每个指称独立判断，同一类型可供多个候选使用，
竞争解释保留到各自的证据核对。固定同一输入的对照中，明确计划指称从 null
变为生产计划候选；这仍不等于主体已采信，后续独立核验保持不变。

重复整批判断仍出现相互排斥，因此对“没有有效类型提议、原文 anchor 与其他
指称重叠”的对象，使用重叠指称已提出的合法类型菜单进行一次独立消歧。
这只补充检索候选，不借用他人的身份或判断；独立消歧可继续返回 null。
定向真实调用中，原来的计划 anchor 在独立输入下正确提出生产计划类型。

实体核验也复现了跨候选推断：“另一候选被拒绝，因此该候选也缺乏实体专名”。
对同一计划单独核验则通过。最终实现将实际 anchor 重叠的实体分入不同核验批次，
不改变判断标准；其余非重叠实体仍可合批。

## 深层对象结果与范围限制

实际发现输入保留层级支持与覆盖重排：第一物理窗口中 API、DrugProduct 分别为
前两张阅读卡；第二窗口在输入预算内选入 Purification、DrugProduct。类型对齐
仍检查可达类型目录，发现卡没有直接替实体定型。

第二窗口真实发现 9 个新提及。后续定向核对其中已有的“步骤三”候选
`c171a13bf8002e680b5b5fcd`，其余 8 个新候选未完成类型和事实核验。
定向选择只限制核对对象，没有增加发现候选或指定目标类型。

该主体独立确认成 `Crystallization`。本体最短路径为
`CMCReport —hasSynthesisRoute→ SynthesisRoute —hasStep→ Crystallization`，
即本体二跳类型；实际候选图和采信图中均未形成文档根到该实例的路径。
在此情况下，原文“内温”的完整值 `30~35℃` 仍保存，字段
`ce476a62fa377565dad47c44` 与主体关联、精确引用和对齐结果均可读取。
这验证了观察保存、主体确认和属性对齐不依赖已有关系路径；不表示上述实例
关系链已成立，也不表示真实报告的三跳链路已经验证。

修复前模型把这个范围的两端都映射到 `reactionConditions`，证据核验也错误放行。
新增通用冲突检查后，最终复核未创建这两条属性，保留完整范围及理由：
“同一属性不能同时承载范围的不同组件；保留完整原值，待按定义对齐”。
计划的上下限使用两个不同的合法谓词，因此仍通过。

最终截面共有 60 个原字段；实体 accepted 4（含文档根）、rejected 2、candidate 8；
属性 accepted 5、unresolved 9、rejected 3；关系 accepted 2、rejected 5。
深层步骤的 `stepOrder` 仍以原词“步骤三”保存，尚未规范为整数；其 accepted
状态不能用于宣称全部属性均已满足类型化值质量要求。整段步骤映射为
`reactionConditions` 的另一候选被拒绝，原文继续保留。

首窗口达到发现容量，另排补读窗口；第二窗口只定向核对一个主体。虽然阶段游标
已越过两个窗口，`scope_complete=false`，不能把游标或当前事实数当作全文完成度。
三跳及更深路径不阻塞属性的机制由合成回归验证，真实三跳仍未验证。
