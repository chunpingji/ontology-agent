# 类型对齐后二次 ID 复核可行性实测

日期：2026-09-28。状态：隔离真实模型试验完成；核心编号对齐目标未通过，未部署。
依据：[方案第 8 节](Mock身份键候选数组引导指称识别方案-20260928.md)、
[前轮发现阶段实测](Harness实体查询最小接线与可行性实测-20260928.md)。

**结论：类型对齐后增加 ID/指称复核，能把核心句拆成两个已接受车间（3/3），
但正确编号归属仍为 0/3。键数组确实到达模型，失败主要发生在成员字段绑定和后续属性核验。
当前版本不足以完成 H01/H02 的识别验收。**

## 1. 本轮验证范围

用户要求实测类型候选确定后、属性及关系对齐前进行 ID/指称二次复核的方案。
新增 [隔离评测入口](../../backend/app/evaluation/harness_key_realign_probe.py)，
实验步骤只在评测适配器生效，没有修改或部署线上 Harness。

先执行真实生产发现及类型对齐，把同一次结果作为以下分支的共同起点：

| 条件 | 行为 |
|---|---|
| A | 当前流程直接继续实体核验、属性/关系对齐、证据核验及共指 |
| B | 读取当前映射的真实 Mock 键值，按原文定位召回；增加一次 ID/指称复核，再执行后续生产阶段 |
| C | 同一额外复核协议及类型/键定义，但不提供新键值候选，明确标注未提供来源；用于区分额外调用与键值反馈 |

A 的共同前缀已经包含前轮实现的发现查询能力，不能把 A 写成完全无库。
B/C 的修订结果重新登记并重新执行类型对齐、实体核验，不继承整组实体的接受结论。
只有在生成属性和关系候选之前才允许替换当前分组；原字段观察保留，旧整组候选和端点退出活动集合。
旧关系线索不复制为成员关系，不回退已采信事实或改写历史运行。

键值来自隔离 Mock 表经既有映射查询服务返回的记录。读取范围由类型候选及其本体父类限定，
每映射最多返回 50 条，本试验来源只有 1–3 条；保留完整性和截断状态。
只把在当前原文实际出现的键值交给模型，保留重叠的整体/成员候选，字面边界仍标为未核验。
没有按斜杠切分，没有预填两成员作为模型金标，也没有人工指定模型的类型判断。
候选记录及来源实体分别使用短别名，来源身份仍保持 `not_checked`。

## 2. 固定条件与评分

复制当前完整 TTL，使用独立 World 和 SQLite Mock 表；复用本地模型服务、现有模型传输及语义阅读卡排序。
逐例原文沿用前轮的核心并列句、单个复合编号、缺记录及备选表达，根类型为 CMCReport。
模型配置、revision、温度及输入/输出预算以各试验 `manifest.json` 为准。
共享前缀只计费一次，分支消耗分别统计；不同核心重复使用新的真实发现和类型前缀。

两轮冻结配置均为 `Qwen3.6-35B-A3B`，revision
`0b21525e972670ed59e1812e170b27c26355381f0656ecc4e25617ece7dac58b`，温度 0.1。
复用传输设置 `reasoning.effort=none`、`enable_thinking=false`，本轮没有改变模型或开启思考模式。
每次输入使用 32,768 的 UTF-8 字节保守上界门槛（不是真实输入 token 计数），输出上限 16,384 token。
首轮预算为 50 次调用/1,800 秒；后续固定试验预算为 180 次调用/3,600 秒，计时从环境初始化和清单写入后开始。
已比对两轮评测脚本、Harness、查询实现、映射模板、10 份 TTL 的 SHA-256 及模型配置，全部一致。
重复使用相同原文及来源键集合；各轮隔离来源记录 UUID 新建，实际返回顺序可能不同，不预设 K1 必须对应某个编号。

评分参考只供输出评价，不进入排序、模型或键值检索。分别保留：

- ID 复核的解释、原文定位和全部成员候选。
- 最终实体状态、编号属性候选及接受/拒绝/未决结果。
- 按生产共指投影计算的已接受生产区域数量、逐主体已接受编号值及其引文归属。
- 所有关系及其极性、条件、核验状态；不以对象数代替生产关系成立。
- 调用、查询、预算、技术失败和实际 token/耗时。

此为单句合成文档的开发回归，不是完整原报告或专家金标评测。
正式来源身份确认和跨文档合并不在本轮范围。
`summary.json` 中沿用的 `count_ok`、`identifier_ownership_ok` 仅评价发现候选/原字段；
最终判定使用 `accepted_entity_count`、`accepted_identifier_groups`、`accepted_identifiers_ok`。
后者核对所有已接受编号值，且多成员用例要求编号引文归属对应 anchor，不能只检查参考值是否曾出现。

## 3. 实际结果

首轮 A/B/C、两次 A/B 核心重复及三个 A/B 边界案例均完成，共 13 个分支。
163 次真实模型调用均取得完整响应，无调用错误；备选案例有一次发现查询反馈因输入预算跳过，详见下文。

### 3.1 核心句结果

| 条件 | 次数 | 已接受车间数 | 最终逐主体编号 | 两成员及编号归属全部正确 |
|---|---:|---|---|---|
| A 当前流程 | 3 | 每次 1 | 每次均为 `644/642车间 → 644/642` | 0/3 |
| B 增加键值复核 | 3 | 每次 2 | 每次均错误接受 `644 → 644/642`；首轮接受 `642 → 642`，后两次拒绝 `642` 属性 | 0/3 |
| C 复核但不提供新键值 | 1 | 2 | `644 → 644/642`；`642 → 642` | 0/1 |

这七条核心分支均技术完成，无模型调用异常。B/C 的两个车间通过实体核验，并在共指阶段保持不同对象。
这表明该插入点能够改变原有分组，但仅拆成两个节点不能证明编号属性也正确。
C 同样能拆出两个成员，因此当前小样本不能证明 Mock 键数组是拆分改善的独立原因。
B 的三次 `interpretations.identifier_values` 均只返回 `["644/642"]`，
未满足逐独立编号表达输出数组的要求，虽然 `grouping` 均为 `multiple_objects`。

### 3.2 边界案例

| 案例 | 来源键集合 | A 最终结果 | B 最终结果 |
|---|---|---|---|
| 明确只有一个车间，完整编号 `644/642` | `644`、`642`、`644/642` | 1 个对象，编号正确 | 1 个对象，编号正确；未因命中三个键而拆分 |
| 核心句，但 Mock 缺少 `644` | 仅 `642` | 1 个整组对象，错误接受编号 `644/642车间` | 保留 2 个对象，但两者编号都错误接受为 `644/642` |
| `644车间或642车间之一`，尚未确定 | `644`、`642` | 2 个对象，但编号属性均被拒绝 | 2 个对象，但编号属性均被拒绝 |

复合编号 B 复核正确只关联完整编号记录；重新登记后有两条同值编号候选被接受，
属于一个主体的重复属性观察，不是两个车间。误提议给文档根的两条 documentNumber 候选被拒绝。
缺记录 B 正确保留了库外的 644 提及，并只为 642 提出来源建议；
但[最终证据核验](../../backend/data/evaluations/harness-key-realign-20260928-final-01/093-missing-1-B-evidence_review.json)
拒绝两个正确成员编号，接受两个错误整串值，因此该案例的编号对齐仍失败。

备选案例的[复核](../../backend/data/evaluations/harness-key-realign-20260928-final-01/106-alternative-1-B-key_realign.json)
正确识别独立编号 `644`、`642`，保留“计划生产车间选项之一”角色。
但 source_fields 仍保留 `644车间`、`642车间`；A/B 的属性阶段也都输出带后缀的编号候选。
[B 的证据核验](../../backend/data/evaluations/harness-key-realign-20260928-final-01/118-alternative-1-B-evidence_review.json)
及 [A 的证据核验](../../backend/data/evaluations/harness-key-realign-20260928-final-01/123-alternative-1-A-evidence_review.json)
以“尚未确定具体车间”为由拒绝属性，混淆了“是否选用该区域”与“该候选区域本身的编号”。
因此既有编号边界问题，也有条件修饰范围问题，不能把拒绝当作编号识别成功。

该例[共同前缀](../../backend/data/evaluations/harness-key-realign-20260928-final-01/alternative-1-prefix-state.json)
记有 `lookup.status=not_completed`、`lookup_feedback_budget_exceeded`：查询后反馈输入超过门槛，
系统保留发现初稿继续类型对齐，没有调用发现修订模型。B 的后续键值查询及复核完成。
分支 `completed=true` 仅说明当前 Harness 流程结束，不表示每个查询反馈步骤都已执行。

所有 13 个分支均未生成关系候选。没有观察到把备选车间写成共同生产关系，
但这也不能证明生产关系抽取、条件关系核验或完整生产路径已经通过。
所有来源建议仍为 `not_checked`，没有任何正式身份确认。

### 3.3 从原始产物定位失效点

1. **键值已正确到达模型。**
   [B 的复核输入及回答](../../backend/data/evaluations/harness-key-realign-20260928-smoke-01/009-members-1-B-key_realign.json)
   包含真实映射返回的 K1=`644`、K2=`642`，完整原文、ProductionArea 和 areaIdentifier 定义。
   模型判断 `multiple_objects`，提出两个独立 anchor，且分别关联正确来源候选。
   但 `interpretations.identifier_values` 仍只有整串 `644/642`，与逐编号判断的要求不一致。
2. **分组改变没有同步改变字段归属。**
   同一回答给两个成员都填写 `field_ids=[F1]` 和 `source_fields.value="644/642"`，
   还把 F1 分给文档根。适配器按模型回答登记，没有暗中修正为参考值。
   原始 F1 被保留是正确的；将它继续当作每个成员的编号字段是本轮错误。
3. **属性对齐没有修复 644 的整组值。**
   [644 的属性回答](../../backend/data/evaluations/harness-key-realign-20260928-smoke-01/018-members-1-B-assertion_alignment.json)
   选择 `span="644/642"`；
   [642 的属性回答](../../backend/data/evaluations/harness-key-realign-20260928-smoke-01/019-members-1-B-assertion_alignment.json)
   选择 `span="642"`。文档根的错误字段则未映射为报告属性。
4. **独立证据核验看到了冲突，但未拒绝错误属性。**
   [证据核验输入及回答](../../backend/data/evaluations/harness-key-realign-20260928-smoke-01/021-members-1-B-evidence_review.json)
   明确同时包含主体 anchor=`644`、候选 value=`644/642`、完整字段及原文。
   模型仍以置信度 1.0 接受，并用“644 作为该复合编号的一部分”解释。
   这不能证明整串属于 644；故评分按最终值和逐主体定位判失败，不能沿用模型自报置信度。
5. **即使提供了正确成员字段，旧整组字段仍会干扰。**
   [C 的复核回答](../../backend/data/evaluations/harness-key-realign-20260928-smoke-01/026-members-1-C-key_realign.json)
   已给两个成员分别生成 `644`、`642` 字段，但同时保留共享 F1。
   [最终核验](../../backend/data/evaluations/harness-key-realign-20260928-smoke-01/038-members-1-C-evidence_review.json)
   接受 `644 → 644/642`，反而以“割裂整体标识”为由拒绝 `644 → 644`，同时接受 `642 → 642`。
   对两个成员采用了不一致的整体/成员解释。

这里既有模型未遵守指令的问题，也有实验协议允许矛盾输出的问题：
`interpretations`、`entities.field_ids`、`source_fields` 是分开的输出，尚无逐成员绑定一致性约束。
后续属性/证据步骤收到原文、anchor 和字段，但不包含本次键值复核的结构化成员解释。
单靠增加上下文或“已接受实体”状态，没有使各步骤维持同一种编号解释。

### 3.4 后续最小修正方向

以下为实测支持的改进建议，本轮未实施或宣称模型验证通过：

- 复核输出直接表达每个成员的 `anchor + identifier_quote + candidate_ids`，让编号解释与成员绑定共用一份结构；
  不再让同一次响应独立重写三套容易冲突的归属。
- 原整组字段作为原文观察保留。模型决定为多个成员后，分别登记其逐字编号字段；
  未明确归属的整体值留在未分配观察，避免默认挂给所有成员及文档根。
- 编号属性对齐与核验携带同一成员绑定及整体/成员竞争解释，核验“此值属于此主体”；
  检出分组、引文、字段归属相互矛盾时保留未决或拒绝当前修订，不能自动以参考答案补值。
- 区分对象自身的编号与业务关系的条件；“尚未选用”不自动否定备选对象的编号属性。
- 不以命中两条记录或斜杠决定拆分。单个复合编号、别名/改号、缺记录及子串边界仍须依据原文区分；
  来源身份继续独立核验，Mock 记录不充当生产关系证据。
