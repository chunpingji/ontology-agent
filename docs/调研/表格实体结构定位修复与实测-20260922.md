# 表格实体结构定位修复与实测（2026-09-22）

指定文档 3.7「设备需求」的 5 条设备记录，在修复后的隔离真实模型实测中全部登记，
并通过实体指称和类型核验；名称来源分别定位到 `table:6` 的第 1–5 行、第 1 列
（索引从 0 起，表头为第 0 行）。这证明本次定位缺失导致的设备漏登记已在该样本中修复。

实测并非全部通过：删除数据行、仅保留标题和表头后，模型仍提出 12 个字段误候选，
其中 1 个被拒绝、11 个未决，0 个被采信。「仅表头不产生任何实体候选」的严格断言失败，
原答和失败断言均保留。本次未运行属性/关系核验、全文分析或部署主服务。

## 1. 原问题与修改

文档 IRI：`http://slpra.org/facts#upload-a255fd30-192c-4f81-92df-5f76a56b8383`。
页面所选原运行：`19e34873-feb3-41c7-af3d-79cc59743e88`；
3.7 对应 IR 的 `section:83` / `table:6`。

原运行的三次发现回答已提出全部 5 条设备，但均省略了可选的 `name` 和 `anchor`。
控制器因 `unnamed_entity_requires_source_anchor` 拒绝登记，因此 3.7 没有登记成功的设备；
图中两条反应釜提及来自 `section:80` 的设备清洗方法。原运行最终为
`coverage_status=partial`、`stop_reason=incomplete_scope`，部分登记失败窗口仍可能因
模型回答 `complete=true` 被当成完成。原发现请求和回答保存在
[baseline-calls.json](../../backend/data/evaluations/equipment-source-anchors-20260922-3baddcd4/baseline-calls.json)。

修复集中在既有独立 Harness：

- [protocols.py](../../backend/app/services/document_harness/protocols.py)：每个实体的
  `anchor` 必填非空，`source_id` 限定当前窗口来源。整来源可只给 `{source_id}`，
  局部指称再给逐字 `text` 和必要的 `occurrence`。`name` 仍是可选的独立名称引用；
  `name=null` 不表示原文没有名称，名称可以直接位于 anchor 中。
- [source.py](../../backend/app/services/document_harness/source.py)：新增来源定位解析，
  复用 DocumentIR 已有表格路径、行列和物理单元格信息。模型不重新数坐标；同格多段
  沿用各段来源 ID，合并单元格沿用解析器归属，不能扩张到窗口外、其他段落或整行。
- [controller.py](../../backend/app/services/document_harness/controller.py)：登记失败保留
  已解析证据和有效字段观察，并计入窗口未完成，沿既有有界拆分处理；不再直接相信
  模型的 `complete=true`。位置有效不代替实体类型、身份或字段归属核验。

没有新增位置存储、兼容层、开关或本体定义。代码加载后的新运行直接使用新契约。
