# 独立文档 Harness 重构与实测（2026-09-21）

## 范围与口径

对应 [035 规范](../../specs/035-independent-document-harness/spec.md)。在当前分支重建
`document-harness-v1`，新文档图谱运行默认采用新核心和阶段消息，旧非模板文档运行
保留历史读取、原件下载及取消/删除，不能恢复旧识别引擎。模板属于独立执行域。

复用物理 DocumentIR、原件存储、鉴权、运行租约/控制、模型传输；不复用旧
`ontology_guided` 的候选、执行卡、facet 证明、核验消息、恢复状态或图谱响应。
无领域 IRI/词表特判，无权威 TTL 修改，无旧运行转换。

## 当前实现

- 发现：预算内共同阅读相邻小节，保留真实章节、表格行和字符位置；原字段由程序
  提取，叙述字段允许模型补充原标签/原值。先保存提及和关系线索，不按名称合并角色。
  提及、文档字段归属、补充字段、关系线索均须显式回答，省略任务不能解释为无结果。
- 类型对齐：独立 RDF 类型目录，分批时没有符合原指称的类别就返回 null。
  按实体 ID 固定键返回，不允许重复某实体而漏掉另一实体。
- 属性/关系对齐：依据主体当前卡的合法 IRI，结合两端字段集合和谓词语义合批发现；
  跨窗口端点不要求先采信。非法谓词只保留观察；缺失标记不作为实值。
  属性按当前字段 ID 固定键逐项给出合法 IRI 或 null 及理由；关系数组同样必填。
  没有合法属性菜单时直接保留字段观察；超过 32 个字段分批，不静默裁剪。
- 原文核对：按候选 ID 固定键逐项判断，证据只引用本次短来源 ID，由程序保存真实
  原文；原字段值不重新生成。空证据、错来源、缺少指称/原值锚点不能采信。
  SHACL/datatype 不作为严格识别门。候选关系先虚线，采信后实线。
- 每调用输出上限 16,384 token；输入以指令、消息和 Schema 的 UTF-8 字节保守上界
  限制（不是实际 tokenizer 数）。发现先拆阅读范围，后续按目录/实体/对象/候选拆批；
  单个不可分输入仍超预算时明确失败，不裁断原值。
- 当前业务状态逐行更新，请求/原答和成本独立保存；暂停继续复用已保存回答。
  新图谱、来源接口独立，界面区分调用、候选和已采信事实。

阶段协议详见 [contracts/stages.md](../../specs/035-independent-document-harness/contracts/stages.md)。

## 首次实测暴露的协议问题

运行 `a29a5d68-79d0-4b16-957b-79d98ebaa1fb`：

- 发现调用 23.79 秒，输入 2,961 / 输出 551 token；运行创建后 25.21 秒出现 3 个提及，
  为研发项目、化合物/原料药、生产活动，分别组织 4、8、2 个原字段。
- 类型调用 33.41 秒，输入 5,817 / 输出 512 token。数组响应重复 E3、漏 E2，
  被 `type_alignment_entity_set_mismatch` 拒绝。没有错误采信，候选与原答保留。
- 修正为固定 ID 键对象，由动态 JSON Schema 要求所有当前 ID 且禁止额外键；
  JSON 解码拒绝重复对象键，不接受旧数组转换，不宽容重复以制造进展。
- 该失败截面的 58 处展示引用均与原文字符区间匹配。真实浏览器能展示候选及失败原因、
  来源定位高亮；刷新零写请求，未访问旧 target-graph/source-selection 接口。

此运行用于定位协议问题，不作为最终四阶段通过的证明。

第二次运行 `6a093156-34c6-4c2e-b1d2-5731f050be0e` 已通过固定键的四批类型对齐，
但发现阶段仍提出标题/单字段等低质量候选；有效名称的非 null 类型提议缺少来源，
被后置检查保留为未决，修改说明误作工艺实体则被原文核对拒绝，未产生采信事实。
据此进一步让非 null 类型在 Schema 中即必须有来源，并明确文档元数据归属文档根、
未归属字段保留观察，不为字段虚构“记录”实体。新模型传输显式使用并冻结服务已有的
`local_llm_temperature=0.1`，不再依赖模型服务默认温度。

第三次运行 `31351e2b-ce97-4bd8-b6bb-02b5976c7180` 首窗口完成四阶段，
采信 4 个实体提及和 1 条关系；发现耗时 40.46 秒，类型对齐四批 182.06 秒，
属性/关系对齐三批 37.80 秒，原文核对两批 50.05 秒。
但模型对已有 `property_field_ids` 仅返回空关系数组，跳过全部属性匹配结论。
最后将属性输出也改为必填的字段 ID 固定键对象；每个当前字段必须明确返回合法谓词
或 null 及不匹配理由。无匹配合法谓词不等于允许借用其他类型卡的属性。

第四次运行 `8e45609e-cbad-458b-a739-3ab10431f99a` 的 12 个模型响应全部符合各自
动态 Schema，20 个字段匹配任务均有明确决策，200 处展示引用逐项匹配原文。
但协议和引用正确不等于事实正确：类型分片分别为同一化学实体提出 CMCReport（0.95）
与原料药（0.90），原实现跨分片选最高自报置信度，错误覆盖了正确提议。
后续核对还以“缺乏更精确类型”为由错误接受 CMCReport。此截面界面显示的两个采信项
中有一个错误实体类型，另一个是文档编号；不能将该计数当成两个正确事实。

据此修正类型分片合并：分片只召回候选，多个类型提议在同一原指称上下文中联合比较，
不跨分片按自报置信度决定胜者。核对明确允许拒绝全部候选；没有替代类型不是接受
错误类型的理由。此修正不增加领域特判，不放宽合法 IRI、引用或采信条件。

上述开发验证运行均已停止（cancelled），保留全部原答、成本和当前候选，没有删除数据。
