2026-09-28 12:04 UTC 前，当前主机的后端已重建并运行：默认文档分析 Harness 使用 `gpt-6-sol` Responses 网关，模型请求调度容量与文档分析执行槽均为 **8**。网页代理的 `/api/health` 返回 200，数据库 revision `0042_mock_entity_query` 与代码 head 一致。此处的并行度是已生效的容量配置；本轮没有同时提交八份文档来测量峰值吞吐。

## 修改与部署配置

- [local_client.py](../../backend/app/services/llm/local_client.py) 从流式 `response.output_item.done` 收集完整消息。当网关的终止事件报告 completed 却给出空 `output` 时，按事件索引还原消息；终止事件已有输出时仍以其输出为准，失败或不完整状态不伪装成成功。
- [model.py](../../backend/app/services/document_harness/model.py) 将动态 Pydantic Schema 整理为网关接受的严格 JSON Schema：展开带说明的 `$ref`，显式要求对象字段及 nullable 类型。相同整理结果同时发送给模型作为可读契约和结构化输出约束，请求输入预算按实际发送内容计算。
- [docker-compose.yml](../../docker-compose.yml) 从仓库外的私有 env 文件注入网关凭据。主机被 Git 忽略的 `.env` 指定模型 `gpt-6-sol`、地址 `http://host.docker.internal:31080/v1`、`LOCAL_LLM_MAX_CONCURRENCY=8` 与 `DOCUMENT_ANALYSIS_DISPATCH_CONCURRENCY=8`，清除了旧 Qwen 权重 revision 与 tokenizer/server 路径。密钥不在 Compose、`.env`、源码或评测产物中；私有文件权限为 `0600`。

当前运行按本机默认 Compose 合并方式执行 `docker compose up -d --no-deps --no-build --force-recreate backend`，最终重建后容器处于 Up。此前核对数据库无 queued/running 模型请求。启动会执行迁移和本体投影，因此单独核查了实际数据库 revision，未仅凭健康接口判断。

## 发现并修正的生产兼容问题

直接调用此前独立评测脚本能获得 GPT 回答，但首次使用正式 `call_model` 测选择阶段时，网关 completed 的终止响应没有携带 `output`，客户端误报 `harness_model_invalid_json`。修正流式消息收集后，相同正式调用返回 `supported/P2`。

随后从空状态运行一条原句时，网关对发现阶段返回 HTTP 400：`invalid_json_schema`，指向带 `description` 的 `$ref`。将已在对照评测中验证的 Schema 整理规则接入正式 Harness 后，重新运行完成。评测脚本一度仍使用旧请求预算下的冻结精排缓存键，已改为调用部署环境的真实精排器；该脚本问题未进入生产代码。

## 适用范围

本轮替换的是当前默认的非模板文档分析 Harness 所用模型。网关仅给出模型别名，没有可冻结的权重 revision；历史 Qwen 运行不能按原模型身份在 GPT 上继续，应以当前配置新建运行。模板驱动的旧抽取协议还依赖本地权重 revision 与专用 tokenizer，本轮未将该协议改造成 GPT 网关执行路径；不能把本次 Harness 验收外推为它的验收。

密钥文件位于仓库外的 `/root/.config/ontology-agent/gpt-gateway.env`，由 Compose 读取。可复核部署配置而不输出凭据：`docker compose config -q`；查看当前容器配置时只查询必要的非敏感字段或凭据是否存在。
