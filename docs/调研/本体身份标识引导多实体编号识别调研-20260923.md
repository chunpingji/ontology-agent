# 本体身份标识引导多实体编号识别调研

日期：2026-09-23。初始状态：调查结论与建议方案。用户随后授权按本文实施验证；
当前实现及新评测结果见[验证记录](本体身份标识引导多实体编号识别验证-20260923.md)。
下文第 2 节及末段保留调研时点的事实，不代表修订后的当前状态。

## 1. 结论与纠正

上一版将具体编号、对象名称和拆分示例写入通用发现协议、核验协议及输出 Schema 描述，
违反领域无关原则。案例通过不代表这种实现方式可接受。此前
[实测记录](并列车间编号识别修复-20260923.md)保留为历史结果，不再作为推荐实施方案。

推荐复用现有本体卡，将**适用的标识属性及其语义提前提供给实体发现，并在核验时继续使用**。
通用指令只要求模型判断“哪些编号属于哪些具体对象”，不内置对象名称、编号、IRI、后缀词表
或分隔符拆分规则。具体类型、属性、身份约束来自当前冻结本体，值与对象归属来自原文。

这次问题有两个独立缺口：

1. 本体已识别出的身份信息，没有完整传到发现阶段。
2. 当前 `ProductionArea` 没有编号属性；仅接通已有身份信息不足以覆盖这个类型。

本体 ID 可以引导识别，却不能独自决定实体数量；不能将 `identityKey=true` 解释成
“遇到多个数字就拆分”，也不能把编号不同直接升级为全局不同实体。

## 2. 仓库核验结果

本次读取了当前工作区 10 份顶层 SLPRA TTL，并与指定运行此前保存的冻结本体核对。
合并 TTL 仅用于内存调查，没有修改本体、导入实例或下载外部 imports。

| 已核验事实 | 依据及影响 |
| --- | --- |
| 存在 `slpra-integ:identityKey` 注解 | [integration 定义](../../ontology/slpra/slpra-integration.ttl)：表示身份核对依据，明确不自动赋予全局唯一性。属于现有本体适配契约，通用流程可读取其结果。 |
| 目前只有两个数据属性显式标记为 true | `equipmentID` 与 `productIdentifier`；不是所有名字含 ID、Identifier、编号的属性都有这个标记。 |
| 当前 SLPRA TTL 没有 `owl:hasKey` 声明 | 程序支持复合键，不等于当前本体已提供复合键。不能把测试 fixture 的声明当作生产事实。 |
| `ProductionArea` 和父类 `Facility` 的有效数据属性均为 0 | 当前 TTL 编译结果与原运行冻结卡一致；没有可直接绑定的区域编号属性，也没有可继承的身份键。 |
| `intermediateIdentifier` 有明确作用域描述，未标 identityKey | 描述限定到项目或合成路线。卡上的默认 false 表示未识别为显式身份键，不能据此否定其作为局部编号的语义。 |
| 类卡已经保存身份信息 | [ontology.py](../../backend/app/services/document_harness/ontology.py) 的 `PropertyCard.identity_key`、属性定义/注解、`ClassCard.identity_key_groups` 已存在。 |
| 发现阅读卡丢弃了这些信息 | [reading_card](../../backend/app/services/document_harness/ranking.py) 只提供 `property_labels`，不提供属性定义、identity_key 或 identity_key_groups。 |
| 后面的部分阶段已有完整信息 | `model_menu` 将身份信息用于属性/关系对齐；[coreference.py](../../backend/app/services/document_harness/coreference.py) 已给共指模型提供身份属性及复合键。发现阶段合并错对象后，这些信息来得太晚。 |
| 实体核验也缺少清晰的标识属性上下文 | [controller.py](../../backend/app/services/document_harness/controller.py) 的实体核验主要提供类定义、提及及原字段；没有明确交付该类型的身份属性定义。 |

需要区分三种 ID：类型/属性 IRI 标识本体术语；`local_id` 和系统生成的实体 ID 标识程序记录；
原文编号才是待解释的业务属性值。前两者不能证明原文有几个对象或某编号全局唯一。

## 3. 标准语义与适用边界

本次直接查阅了 W3C 原始规范，以下是对设计有实际影响的结论。

| 声明 | 可以提供什么 | 不能据此做什么 |
| --- | --- | --- |
| 项目 `identityKey` 注解 | 提示某属性可作为身份核对依据，并使用其定义中的作用域限制 | 自动断言唯一性、赋予实例身份或拆字符串 |
| OWL `HasKey` | 在规定类及键条件下，用共同键值判断命名个体同一；复合键必须保留组合 | 推定每个属性单独唯一、键必填、键只有一个值，或由“不同键值”反推必然不同对象 |
| OWL 数据属性 functional / 最大基数 | 约束一个主体关联的不同数据值数量 | 判断原文列举数量；发现冲突时自动创造新主体 |
| SHACL `sh:maxCount` | 检查数据图中的值节点数量 | 将一个字符串内部的若干片段计算成多个值节点 |
| 字符串数据类型、`sh:pattern` | 约束已有值的类型或词法格式；前提是本体/形状确有声明 | 根据属性名字自行生成格式规则，或直接证明编号归属 |

尤其是，一个包含分隔符的 `xsd:string` 仍然是一个字面量；`sh:maxCount=1` 本身无法发现
该字符串是否错误地包裹了多个实体编号。不同对象也可能暂时同号，同一对象可能有多个系统编号
或改号前后的编号。作用域、时间、对象层级及原文说明必须参与解释。

官方依据：

- [OWL 2 Structural Specification §9.5 Keys](https://www.w3.org/TR/owl2-syntax/#Keys)
- [OWL 2 Direct Semantics §2.3.5 Keys](https://www.w3.org/TR/owl2-direct-semantics/#Keys)
- [OWL 2 Functional Data Properties](https://www.w3.org/TR/owl2-syntax/#Functional_Data_Properties)
- [SHACL sh:maxCount](https://www.w3.org/TR/shacl/#MaxCountConstraintComponent)
- [SHACL sh:pattern](https://www.w3.org/TR/shacl/#PatternConstraintComponent)

首期不需要新增推理器或 SHACL 管线。当前 `PropertyCard` 没有完整表达属性 functional 等约束，
也不能在新阅读卡里假装已有；复用已经保存的身份标记、完整键组及定义即可。

## 4. 建议的最小流程

### 4.1 从冻结本体编译阅读指引

在现有 `reading_card` 中补充 `identity_properties` 和 `identity_key_groups`，复用现有字段：

- 属性 IRI、标签、别名、定义、数据类型、适用 domain 和必要的已有注解。
- 身份标记及其声明依据；保留完整复合键组，不能将组内成员扁平化为独立身份键。
- 键组含对象属性时保留对应合法关系定义的引用；缺少组件解释时不能当成完整身份依据。
- 身份注解的解释沿现有适配器和 `annotation_contracts`，不扫描 IRI 后缀或中文关键词猜测。
- 没有显式身份键时列表为空；其他编号语义仍可从现有属性定义和原文识别，但不能虚构身份键。

身份属性的作用域若仅存在于本体描述中，就保留原描述给模型阅读；不为本次任务建立新的
作用域管理系统。缺少声明时明确未知，不默认全局唯一，也不默认一份文档只有一个编号空间。

这些字段同时送入实体核验。发现阅读卡仍是候选语义提示，不是类型确认；若后续选择了
另一合法类型，核验必须使用实际候选类型的标识定义重新检查归属。保持现有输入预算与分批，
不能为了塞入更多卡片而静默删除键组成员或身份语义。

### 4.2 让模型建立“指称—编号”对应

通用发现指令可收敛为以下规则，不含业务名称或样例答案：

> 结合当前类型卡的标识属性定义和原文，判断编号表达属于一个完整标识、一个对象的多个标识、
> 多个对象各自的标识，还是复合键的不同组成。分别登记有原文支持的对象提及，将对应编号
> 作为该提及的原字段保存。每个成员必须能独立定位；共享上下文不能替代成员定位。
> 不以标点、数字数量或属性名称决定对象数量。不补造省略的字符，不把别名或改号拆成新对象。
> 无法确定归属的原值保留观察，不伪装成已确定编号或身份。

建议继续使用 `Mention.anchor`、`evidence`、`source_fields` / `field_ids`：每项原编号用精确
引文保存，共用名词、表头或句子作为上下文。发现阶段仍不输出已采信的本体属性事实；
随后由现有属性对齐选择合法谓词，再核验编号及归属。

不需要新增枚举状态表、额外身份实体、第二套抽取流程或默认多一次模型调用。
无法归属的编号复用 `unowned_fields`；`complete` 仍只表达阅读范围是否完成，不能用来
冒充编号消歧成功。字段保存也不应以已形成完整关系路径为前提。

上一版 `name_parts` 的“编号＋同来源后缀”限制服务于显示名拼接，不能承担编号归属与身份语义。
建议在替代实施时移除该专门约束，直接复用原文编号作为提及标签，并显示本体类型标签。
用户本次要求是正确区分实体，不必为了拼接完整显示名再扩展协议。

### 4.3 独立核对数量、属性和身份

实体核验接收原文、候选类型及身份属性定义、当前成员定位和相邻候选的有界上下文，检查：

1. 当前候选指一个对象，还是误将多个对象打包；编号确实属于该对象层级。
2. 多项编号是否为不同成员、同一对象的不同编号、复合键组件或未决表达。
3. 属性值与其来源逐项对应；范围、缺失、备选、否定和条件没有被拆分操作丢弃。

程序负责合法 IRI、来源范围、精确引文、端点引用及已有声明约束，不负责猜测编号语义。
候选整组打包或归属不清时不得采信；保留未决/拒绝和原因，不自动将旧属性、旧边复制到新对象。
首期仍让发现阶段产生正确成员，不为修复失败候选引入自动拆点、无限重试或运行历史回放。

后续共指沿用现有流程。同一编号要结合命名空间/有效范围核对；未证明全局身份不妨碍保留
原文明确列举的独立局部提及。实体数量、编号属性成立及共指归并是三个不同判断。

### 4.4 本案例需要的本体补充

`ProductionArea` 当前没有编号属性，不能借用 `equipmentID`，也不能在代码中动态造谓词。
如要按本体标识引导这个类型，建议按本体维护流程增加一个**生产区域的管理编号属性**，
声明正确 domain、字符串 range、定义及已有 `identityKey` 注解。其名称和 IRI 由本体维护确定。
定义应说明编号用于指称什么层级、唯一性的适用范围及范围不明时的处理，不规定某份文档的
编号值、位数、分隔符或示例答案。

这属于领域知识进入本体，而非进入通用引擎。不要扩展到所有类统一加 ID，不增加未经需求
确认的全局唯一性、单值性或 `owl:hasKey`。特别是当前类定义允许区域包含多个房间，
编号属性不能顺带把生产区域改成生产房间。

本体补充前，仍可以由原文和类型定义识别多个局部提及；编号只保留为未映射原字段，
不能宣称已按不存在的编号属性完成本体对齐。需要在新运行冻结修订本体，旧快照不回填。

## 5. 验证方法与落地范围

建议先固定原文、本体、模型、预算和独立期望，比较三个条件：

- A：移除业务硬编码后的通用指令，仍使用当前简化阅读卡。
- B：同一通用指令和卡，仅增加已有身份标记，检查标记本身的贡献。
- C：同一通用指令，提供身份标记、属性定义、作用域描述和完整键组，检查完整语义的贡献。

先用已有身份标记的类型验证通用机制；本案例使用单独、明确标记为待维护的本体草案验证，
不能把草案当成已发布本体。金标和具体期望不得进入模型输入。

| 必须覆盖的情况 | 验收重点 |
| --- | --- |
| 多类型、多语言的并列编号，以及不同标点/空白 | 成员数量、局部位置和编号归属；领域示例只在测试资料中 |
| 单个复合编号、型号、日期、比值 | 不因分隔符产生额外实体 |
| 单对象改号、别名、两个系统编号 | 不因多个 ID 自动拆成多个对象 |
| 相同编号但不同场所/范围 | 不直接归并；缺少范围保持未决 |
| 复合键及缺少一个键组件 | 保持完整键语义，不把字段组件当实体，不作笛卡尔组合 |
| 前导零、字符串大小写和缺失标记 | 按原值和本体声明处理，不隐式数值化或改写 |
| 身份键没有入选、类型卡不匹配、只有“ID”字样而无身份标记 | 不猜造键和属性事实，允许保留局部提及与观察 |
| 备选对象、否定关系、集合总量 | 不复制总量，不将备选关系改成全部确定成立 |
| IRI 重命名、同标签不同定义、不同类型赋予不同编号语义 | 结果随声明语义变化，不依赖固定 IRI、词表或原案例记忆 |

分别计实体数量/边界正确率、编号归属正确率、属性采信、错误拆分/错误合并、未决率及调用成本。
原文关系需重新核验，不能只检查节点数量；也不能以全部拒绝获得形式上的零错误。

拟修改位置限于本体维护项、`reading_card`、发现/核验输入与通用协议及对应测试。
不新增数据库、运行恢复机制或默认外网依赖。替代方案必须先移除上一版通用协议和 Schema
描述中的领域示例；不能保留旧业务提示作为隐藏兜底。

本轮实际只完成仓库与冻结卡核验、W3C 规范核对和文档修订。未修改运行代码、权威 TTL 或
在线运行，未调用识别模型，也没有将此前 215 项测试或旧模型实测计为新方案验证。
