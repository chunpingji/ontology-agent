# 本体卡直接发现独立文本属性实测（2026-09-22）

后续状态：带字段标签作为原文观察是正常的，不据此判定违反本体契约；取值区间
和核验分工已另行修订，见
[后续修订与复核](属性值边界与根类型核验分工实测-20260922.md)。下文保留本轮原始结果。

结论：指定报告的封面实测支持该策略。向本地 LLM 提供当前主体的本体卡和原文，
即使原文没有“密级：”字段名，也能直接提出
`confidentialityLevel = "绝密▲长期"`，并通过独立证据核验。
保持相同卡片、仅移除这行原文后，模型返回 `not_found`，没有凭本体卡补造密级。
这验证了本案例的可行性，尚不能证明跨文档准确率或全文完整度。

用户指定文档为 `upload-a255fd30-192c-4f81-92df-5f76a56b8383`。
实证从运行 `19e34873-feb3-41c7-af3d-79cc59743e88` 读取已冻结输入，
仅使用第 1 物理页的非空原文单元；未修改、暂停、续跑该运行，也未重启主服务。
模型调用使用独立实测身份，会写入既有调用用量记录。

封面原文按输入顺序为：

1. `HRXS-P-2419(HRS-1597)`
2. `研发项目临床备样生产信息`
3. `绝密▲长期`
4. `编号： DP-C-PI-S-X2419 2601 04`
5. `时间：2026年05月`

发现输入只包含主体卡、卡片的全部 8 个合法属性及上述原文；属性卡包含 IRI、
标签、定义、别名和数据类型。没有提供预提取字段，也没有预先构造“密级”字段。
模型逐属性回答 `status / value_quote / context_sources / confidence / reason`。
有依据时提出候选及精确引文，没有依据时返回 `not_found`，含义不明确时允许
`uncertain`。输出属性只能来自本次卡片，不将相似度或模型置信度当作采信依据。

随后用 `Window.resolve` 将模型引用解析为原文位置，并将候选交给当前独立
harness 的 `Engine.evidence_review`，实际调用模型核验语义和主体归属，
再执行服务器引用覆盖和主体状态检查。每个实验各调用一次发现、一次核验。
这条直接候选发现路径是隔离脚本，未接入在线发现流程。

密级使用合法 IRI
`https://ontology.pharma-gmp.cn/slpra/document/confidentialityLevel`。
原文位置为第 1 物理页、`paragraph:6:0`、字符 `[0, 5)`，
来源单元 `7299db1862d0e2de72ffb2e63a265042b672c85818f621acb8598718b13762ca`。
核验原答为：“原文S3明确标注'绝密▲长期'，符合密级定义，且该标记位于文档头部，
属于文档属性。”候选保留完整原值，没有擅自把“长期”丢掉或推导访问权限。

实测暴露了两个尚未解决的边界，不能用 accepted 数量掩盖：

- 正例的文档编号值夹带“编号：”，核验仍采信。后续需区分值本身与上下文引文，
  核对值边界；不能用领域专用正则修补该案例后就宣布通用提取准确。
- 负例中，核验器以“像生产指令/计划类文档，而非 CMC 报告”为由拒绝文档名称。
  它在属性核验中重新质疑用户已指定的根类型，暴露出核验职责边界和输出稳定性问题。
  应将属性归属/语义核验与根类型争议区分；本轮没有改提示后重跑来隐藏该失败。

文档名称也需遵守卡片关于文档记录显示名称的定义，封面标题候选通过模型核验，
不等于已经与登记文件名完成一致性核对。其余 5 项的 `not_found` 仅适用于封面。
内容哈希应来自文件计算或可信元数据，不能要求 LLM 从封面文字补出；登记记录
版本也不能充作文档修订版本。

现有故障更符合协议瓶颈：调查时，根节点只关联预解析的“编号”“时间”字段，
已送入发现输入的标题及密级行没有根节点新增字段入口，字段标签又要求原文引文。
直接给卡片和原文后，同一模型能提出密级候选，说明至少本例不需要先换模型。
通用策略可采用“主体卡及其合法属性 + 当前原文上下文 → 属性候选与原值引文
→ 引用、归属、含义及值边界核验”；没有显式字段名时不伪造字段名引文。
