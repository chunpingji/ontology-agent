# Harness 实体查询最小接线与可行性实测

日期：2026-09-28。范围：用户授权的最小发现接线与真实本地模型可行性试验。
依据：[接入方案](Harness实体查询接入与模型验收方案评估-20260928.md)、
[036 任务](../../specs/036-mapped-entity-query/tasks.md)。

**最小接线工程验证通过，但核心识别目标未通过：当前版本三次试验均未将“644/642车间”
识别为两个成员。** 共完成 27 次真实模型调用，包含初始失败迭代；本文不代表完整图谱或来源身份验收。

## 1. 本次实际实现

调用链为：原文窗口与本体阅读卡 → 带引文的发现草案和查询假设 → 既有映射查询服务 →
一次完整发现修订 → 单次登记 → 既有后续核验阶段。

| 文件 | 实际变更 |
|---|---|
| [protocols.py](../../backend/app/services/document_harness/protocols.py) | 在既有 discover 阶段增加 draft/refine 协议、原文查询和来源候选建议；不增加公开阶段 |
| [lookup.py](../../backend/app/services/document_harness/lookup.py) | 逐项核对引文与条件，一轮反馈、预算核对、当前步骤保存、修订遗漏原字段保留 |
| [lookup_adapter.py](../../backend/app/services/document_harness/lookup_adapter.py) | 核对冻结本体与当前映射，再调用既有查询服务 |
| [controller.py](../../backend/app/services/document_harness/controller.py) | 推迟到最终发现结果才登记一次，避免留下草案整组节点与旧边；候选建议保持未核对 |
| [runtime.py](../../backend/app/services/document_harness/runtime.py) | 默认注入本地查询端口，沿用执行所有权、暂停检查和独立只读 Session |
| [entity_query.py](../../backend/app/services/entity_query.py) | 增加只读能力元数据视图，不为能力发现扫描 Mock 实例 |
| [harness_lookup_probe.py](../../backend/app/evaluation/harness_lookup_probe.py) | 复用生产 Engine、模型传输、语义阅读卡排序及查询服务的隔离试验入口 |

每窗口最多 8 个查询、每项最多 6 个字符串属性条件及 5 条候选、最多一次模型反馈。
名称与属性条件须逐字定位于同一假设 anchor；非法项跳过，有效兄弟项继续。
无条件全表浏览不向发现模型开放。生产代码没有车间编号、领域词表或按分隔符拆分规则。

来源命中只保存为 `source_candidates`，保持 `identity_status=not_checked`；原文名称不被来源标签覆盖。
来源名称可作为既有观察项显示，不能据此宣称已正式识别为规范名称或已建立身份关联。
完整未命中、查询未执行、读取不完整、映射变化及预算未完成分别记录。
草案被撤回的整组字段保留为未归属观察，不重新创建整组主体。

待消费草案和反馈保存在当前窗口状态中；消费后删除，已付费回答继续复用现有调用账本。
本轮未增加数据库表、迁移、来源镜像、历史状态或正式来源身份核验阶段。

## 2. 实验方法与边界

模型配置为 `Qwen3.6-35B-A3B`，配置 revision 为
`0b21525e972670ed59e1812e170b27c26355381f0656ecc4e25617ece7dac58b`，temperature 为 0.1。
沿用生产传输的 `reasoning=none` / `enable_thinking=False`；输入保守上界 32,768，输出上限 16,384。
实际 token 以模型返回 usage 计，`request_size()` 的 UTF-8 字节预算不当作实测 token。

使用完整当前 TTL 的隔离副本、独立 World 与 SQLite Mock 表，映射来自现有配置文件。
真实调用在已有后端容器内运行，使用现有本地模型服务及调度；原文为下表的单句合成 DOCX。
没有使用完整原报告，本轮仅回答发现阶段可行性。
评测参考只供评分，未传入模型、查询或排序输入；属于开发回归参考，不是专家金标。

| 组别 | 条件 |
|---|---|
| A | 同一原文、本体阅读卡，无查询端口，一次发现 |
| B | 生产查询接线：模型自主提查询，真实映射查询后修订一次 |
| C | 复用 B 同一草案，多核对一次；明确告知查询未执行，不伪装成完整未命中 |

每组三个条件复用生产语义排序选中的同一阅读卡，没有人工强制指定生产区域类。
C 的草案复用不产生第二笔调用，报告分别计实际调用和共享草案成本。
核心句的当前版本执行三个独立试验，反例各一次；重复不使用固定随机种子，不能解释为统计稳定率。

| 用例 | 原文 | 隔离来源 |
|---|---|---|
| members | 计划于644/642车间完成本次临床样品的生产。 | 644、642 |
| composite | 本次仅使用一个车间，其完整编号为644/642，不代表两个车间。 | 644/642、644、642 |
| missing | 计划于644/642车间完成本次临床样品的生产。 | 仅 642 |
| alternative | 本次计划选择644车间或642车间之一生产，尚未确定具体车间。 | 644、642 |

实验在发现登记后、类型对齐前停止。数量和编号归属分开评分，逐主体核对编号字段及其原文跨度，
并防止两个成员编号互换后仅凭值集合相同通过。来源建议数、独立原文跨度和所有提及同时保留。
原字段正确不等于本体编号属性已经采信；备选提及正确不等于共同生产关系成立。
没有对类型、正式身份、关系或完整图谱作通过结论。

## 3. 实测结果

### 3.1 核心并列句

当前版本三次重复中，A、B、C 各为 **0/3 通过**：全部只登记一个 `644/642车间` 提及，
原字段仍为整串 `644/642车间` 或 `644/642`，没有形成各自的 `644`、`642` 编号字段或来源建议。
这不是调用失败、预算未执行或缺少生产区域阅读卡；B 每次均完成真实查询和模型反馈。

B 草案每次只提出一个 `areaIdentifier="644/642"` 查询，名称条件为 null；
没有提出 `644` 和 `642` 两项成员假设。服务正确返回完整未命中，模型随后仍保留整组。
失败位置在查询假设生成及发现解释，当前证据不支持“查询服务把两个车间合并”的判断。

在此前初始迭代中，模型也仅提出整体查询，而且将名称与编号同时作为 AND 条件。
随后只调整通用提示和 Schema 输出顺序：要求先提出整体/成员竞争查询，编号查询优先不用名称条件。
调整后改善了查询条件，却未解决成员遗漏。初始失败保留在 smoke-01，不计入当前版本三次重复。
smoke-02 与 final-01 保存的 18 个 Harness/查询运行文件已逐字比对一致，因此两者合并统计。

### 3.2 完整发现矩阵

下表“编号”指发现阶段是否保存独立、归属正确的编号原字段，尚不代表属性采信。
核心句三个重复，其余各一次；没有以反例一次成功替代原方案中的完整反例重复验收。

| 用例 | A：无库 | B：接库 | C：同草案再核对 | B 的实际查询/反馈 |
|---|---|---|---|---|
| 并列核心句，3 次 | 数量 0/3；编号 0/3 | 数量 0/3；编号 0/3 | 数量 0/3；编号 0/3 | 每次仅查整体，完整未命中，反馈仍保留一个提及 |
| 单个复合编号 | 数量、编号均通过 | 数量、编号均通过 | 数量、编号均通过 | 只查整体，命中一条，保留一个未核对来源建议 |
| 缺少 644 记录 | 数量、编号均失败 | 数量、编号均失败 | 数量、编号均失败 | 只查整体，未实际检验一成员命中/一成员缺失 |
| 644 或 642 备选 | 数量通过；编号失败 | 数量通过；编号失败 | 数量通过；编号失败 | 提出两个成员查询，但反馈超输入预算，没有执行修订 |

复合编号例的模型没有查询成员，故本次真实结果只能证明它保留了原文明示的单对象，
不能宣称已验证“看到整体及两成员竞争命中后仍正确判断”。B 的来源建议保持未核对，
A/C 也正确保存单对象和编号，因此没有证据证明查询提高了该例的数量或编号质量。

备选例三组均保存两个不重叠的提及，但字段为 `644车间`、`642车间`，未保存独立编号值。
后续属性阶段可能再提取值，本轮没有执行该阶段，不把这一可能性记为已通过。
B/C 的角色说明保留“选项之一”，三组 `relation_hints=[]`；没有采信任何共同生产关系，
也未完成关系反例验收。B 的 `lookup_feedback_budget_exceeded` 明确保存在观察及窗口状态中，
不能以发现窗口 `complete=true` 代表来源辅助已完成。

该 B 条件没有发出反馈模型请求，因此原始模型请求文件不含反馈。随后仅用保存的草案和隔离来源库
重算查询及输入预算，没有新增模型调用；草案请求 payload/Schema 与原记录逐项一致。
两个编号均完整命中各自车间，反馈输入保守字节上界为 **33,257 > 32,768**，超出 489。
这里是既有预算算法的判断，不是实测 tokenizer token 数。诊断另存
[alternative-budget-replay.json](../../backend/data/evaluations/harness-lookup-20260928-review/alternative-budget-replay.json)，
不伪装成原模型已消费的反馈，也未覆盖原始结果。

评分修正：初版评分器要求编号引文包含在实体 anchor 内，误将 A 复合编号例判为编号失败。
该例 anchor 是“一个车间”，另有正确独立字段“644/642”，符合现有原文字段契约。
修正单对象评分并增加反例测试后，只改变这一项判定；并列成员的归属交换检查保留。
原始 `summary.json` 和模型输入输出未改写，复核结果单独保存于
[review.json](../../backend/data/evaluations/harness-lookup-20260928-review/review.json)。

### 3.3 成本与可复核产物

| 试验目录 | 实际调用 | 输入 token | 输出 token | 模型请求耗时合计 | 阅读卡排序耗时 |

| smoke-01：初始失败迭代 | 4 | 24,849 | 1,075 | 98.99 秒 | 80.71 秒 |
| smoke-02：当前版本核心重复 1 | 4 | 24,284 | 1,029 | 94.21 秒 | 79.70 秒 |

| 全部实测 | **27** | **165,660** | **7,793** | **625.31 秒** | **242.65 秒** |

当前版本合计 23 次调用，输入 140,811、输出 6,718 token，模型请求耗时 526.31 秒。
全部模型调用正常返回，无传输/解析失败；有一个 B 条件的反馈因预算而未调用模型，已计入失败结果。
耗时是逐请求计时合计，不是纯 GPU 计算时间，也不是含启动和检查的整轮墙钟时间。
排序按实际调用单独计时，同组 A/B/C 复用；C 只计新发的修订调用，其草案已在 B 计费。
没有货币单价配置，本报告不估造费用。初始失败迭代的成本未从总量中剔除。

核心句当前重复 1 中，A 为一次调用 18.74 秒；B 为两次调用 53.51 秒，数量和编号均无改善。
这支持“当前最小接线增加成本但尚未解决目标问题”的结论，不支持查询辅助已提升识别质量。

## 5. 生效与剩余范围

工作区新运行代码默认注入查询能力，未新增关闭开关。主后端进程未重启，本轮未部署，
不能将独立评测进程成功加载代码写成在线服务已生效。
共享 Mock、映射和本体未修改；试验只在新隔离目录中写文档、来源、模型输入输出和当前状态，
模型调用仍通过既有调度写用量记录，因此整轮实验不是纯只读操作。

H01a 最小工程接线完成，H02a 试验执行完成但识别目标未通过；完整 H01/H02 仍未完成。
下一步应先处理通用成员假设生成和反馈输入体积，并以同一矩阵复测；当前证据不支持先扩大
来源身份展示或完整文档调用规模。正式来源身份核验、完整阶段及文档回归属于后续独立范围。

按用户后续要求，对失败原因、Mock 键约束及键值数组注入的分析见
[Mock 身份键候选数组方案](Mock身份键候选数组引导指称识别方案-20260928.md)。
该分析另做原始产物的字面定位和输入体积核对，未新增模型调用或改变以上实测结果。
