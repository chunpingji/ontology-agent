# 实体库辅助文档指称识别准备度分析

日期：2026-09-23。范围：核对已有设计、工作区实现、当前后端连接的数据库和相关工程测试。
本次仅新增分析文档；未修改运行代码、配置或业务数据，未重启服务，未调用识别模型。

## 1. 结论

**具备开展最小接入试验的基础，尚不具备直接启用“实体库辅助文档指称识别”的条件。**

项目已有实体存储、声明式外部源映射、实例查询工具及相关测试。缺口集中在已有组件之间：
真实来源配置与数据覆盖、编号/作用域映射、实体库查询适配，以及当前独立 Harness 的调用和身份绑定。

对 `611/642/646车间`，现场数据不满足“三个车间均已映射入库”的前提：

- 通用实体表 `entity_shadows` 当前只有 4 个 CMC 文档实体，生产区域实体为 0。
- `ontology_class_mapping` 为 0 条，因而没有已配置的数据库/API 来源类映射。
- 独立的 Mock 车间表有 `642、644、646` 三条；没有 `611`。
- 这三条记录有各自 IRI 和 `code`，但 `data_properties` 内的“车间编号”等属性 `iri` 均为空；尚未形成到本体 `areaIdentifier` 的有效声明式映射。

因此可以复用现有设施推进试验；不能把“有实体管理页面”“有车间 Mock 数据”或“旧工具存在”当作这条链路已经就绪。

## 3. 需要明确的连接断点

### 3.1 “映射已实现”与“现场已映射”不同

014 的类绑定可指定数据库表或 API 端点，属性绑定可声明字段路径、属性 IRI、值转换及 `is_identifier`。
[声明式抽取分支](../../backend/app/services/extraction/pipeline.py)实际消费这些配置，产出带来源的候选。

但当前运行库没有任何类绑定。Mock 车间记录的独立 CRUD 不会自动创建这些绑定，也不会自动将记录写入 `entity_shadows`。
[报告演示来源](../../backend/app/services/reporting/demo_sources.py)可查询 Mock 车间，只证明报告域已有读取能力，不证明文档识别已接入。

此外，`is_identifier` 是来源映射配置，`identityKey` 是本体语义注解，两者目前没有在当前 Harness 中贯通。
属性绑定契约只允许同一来源类绑定有一个 `is_identifier`；流水线也只读取第一个标识绑定。
不能据此声称来源映射层已经支持“组织＋编号”等完整复合身份键。

### 3.2 已有实体查询尚不足以查询身份

`KGStore.search_entities()` 的 `q` 只在中英文标签和 IRI 上执行包含匹配；类型为单一 `class_iri` 精确过滤。
它不接受“属性 IRI＝编号值＋所属范围”等通用条件，也不读取本体键组。
即使名称恰好含有 `642`，搜索命中也只能作为候选召回，不能作为编号精确匹配或身份确认。

[旧实体对齐器](../../backend/app/services/extraction/aligner.py)支持标识精确比较和类型层级检索，但存在三个适用限制：

1. 候选池来自 `OntologyEngine.get_individuals()`，未查询只存在于 `EntityShadow` 的记录。
2. 标识比较是单属性值比较，没有来源编号命名空间或组织/场地范围判定。
3. 名称相似度可以产生 `merge` 结果，不能直接作为本次严格的全局身份核验器。

### 3.3 外部结构化数据到实体库的闭环不能按旧设计直接认定已完成

声明式 DB/API 抽取当前产出 `ExtractionCandidate`，而 [候选确认接口](../../backend/app/api/extraction.py)中的
`_commit_candidate()` 明确返回 `409 legacy_unverified`。相关回归测试也明确要求该行为。
因此“声明映射→生成候选”的测试通过，不代表“审核→可查询规范实体”的完整链路通过。

另一路 [事实源物化](../../backend/app/services/integration/materializer.py)对非文档源仍使用
`facts#<entity_type>` 作为类型、直接保留原始字段，未消费 014 的通用类/属性绑定。
其实例 IRI 为 `facts#<entity_id>`，生成时未包含连接器标识；不同源使用相同裸记录键时有覆盖同一影子行的风险。
这条路径也不能直接视为带完整跨源身份语义的车间主数据接入。

以上是准备度缺口。本次不扩大为全量入库流程重构；只读候选源接入试验可以独立开展。

### 3.4 `query_instances` 已存在，但不在当前 Harness 中

[外部记录读取器](../../backend/app/services/extraction/external_records.py)及
[工具处理器](../../backend/app/services/extraction/ontology_guided/tool_runtime.py)已经提供有价值的约束：

- 显式指定可查询来源和目标类；名称、别名及完整复合键用于召回。
- 返回来源系统、数据集、记录键/版本、匹配字段及查询完整性。
- 处理器固定标记 `identity_status="not_checked"`，避免把命中变成身份确认。
- 缺源、部分结果或截断不冒充“完整查无匹配”；键组件不得跨原文主体拼接。

但 [旧运行适配器](../../backend/app/services/document_analysis/execution.py)只从显式传入的
`external_sources.records` 构造 `FrozenInstanceReader`，没有自动读取实体影子表或声明式映射。
默认记录核验注册表也只注册设备 Mock，未注册车间来源。

当前普通新文档运行由 [应用入口](../../backend/app/services/document_analysis/application.py)转入独立 Harness。
[Harness 控制器](../../backend/app/services/document_harness/controller.py)没有实例读取器依赖；
[模型调用](../../backend/app/services/document_harness/model.py)发送各阶段 JSON Schema，不提供外部实例查询工具。
[现有共指](../../backend/app/services/document_harness/coreference.py)只比较文档内部提及。

[035 规范](../../specs/035-independent-document-harness/spec.md)明确要求隔离旧识别协议。
因此后续应复用已有存储、映射读取能力和查询约束，为当前 Harness 接入最小查询契约；
不能通过直接导入旧 `ToolContext`、候选/执行协议把旧引擎重新接回。

### 3.5 查询结果还需要“源记录→规范实体”的明确对应

旧 `ExternalCandidate` 有 `source_id/system/dataset/record_key/record_version`，没有独立的规范实体 IRI 字段。
其 `candidate_id` 的生成还包含匹配信息，属于一次候选的标识，不能当作稳定全局实体身份。
Mock 车间虽有 IRI，但该 IRI 尚未贯通到当前识别结果。

后续返回值应区分来源记录键与已知规范实体 IRI。多个来源记录可能对应同一实体；
三个查询候选或三个不同候选 ID，不能直接计算为三个独立车间。

此外，旧工具通常从已登记提及及候选主体构建编号查询。要帮助模型纠正最初的合并提及，
查询需要能够在发现阶段消费带原文定位的编号假设，不应要求三个实体已经确认后才允许查询。

## 4. 当前数据对原例意味着什么

现场查询使用后端现有数据库连接，显式执行 `SET TRANSACTION READ ONLY`，结束后回滚。
仅查询现有记录；未触发连接器同步、播种、模型任务或 World 加载。

| 查询对象 | 本次观测 |
|---|---|
| `entity_shadows` | 4 条，全部为 `CMCReport`，模块为 `document` |
| `ontology_class_mapping` | 0 条 |
| `ProductionArea` 的来源绑定 | 无 |
| 影子行中含 `areaIdentifier` 的记录 | 0 条 |
| `integration_connectors` | 29 条，全部为 `doc_repo`；22 条 `last_status=success`，7 条为空 |
| `mock_production_areas` | 3 条：642、644、646；分别有不同 IRI |
| Mock 车间属性本体映射 | 三条记录的 `data_properties[].iri` 均为空 |

该观测仅描述本次连接的运行库，不代表外部真实系统、其他环境或历史评测数据。
连接器历史成功也不证明任意新业务类型已完成映射。

若仅将现有 Mock 车间作为候选来源接入，合理的预期是：

- `642`、`646`：在明确映射和范围条件下有库记录可供核对。
- `611`：该来源没有记录；应保留文档中的局部实体候选，不因未命中而删去，也不能替换为库中的 `644`。
- `611/642/646`：仍须查询整体标识与模型提出的成员标识，判断复合编号、并列、别名或改号等解释。
- 最终文档实体数量与已链接库实体数量分别统计；“三个文档实体、两个已链接、一个未链接”可以是正确结果。

以上是目标行为与验收口径，本轮未运行模型证明模型已经能够做到。

## 5. 达到可试验状态的最小工作

1. **声明一个可用来源及映射。** 复用现有来源和映射设施，明确源记录类型、编号、名称、编号适用范围与已知实体 IRI。
   对本例，`code→areaIdentifier` 的选择属于来源配置；通用运行代码不写车间名称、编号、领域 IRI 或分隔规则。
   现有 Mock 足以测试部分命中；三实体全部命中的试验需在隔离 fixture 中完整提供三个记录，并明确其为实验数据。
2. **接通只读实例查询。** 在当前 Harness 中接入已映射来源/已确认实体的候选查询，输入包含类型、原文引用、
   身份属性值和可用范围；返回规范实体引用（如有）、来源记录、匹配依据、歧义及不完整状态。
   复用现有数据库与读取设施，不新建实体库或历史快照平台。只读来源试验不以修通全部业务事实发布流程为前置条件。
3. **让查询参与发现与绑定。** 模型可以对完整指称及有原文定位的成员编号提出查询假设，依据结果调整指称构造。
   工具不按 `/` 自动拆分，不替模型预置正确实体数量；缺范围或相互竞争的整体/成员匹配保持未决。
4. **分别验收数量、属性、身份和关系。** 先核对文档实体及各自跨度，再核对编号归属、库实体绑定，最后核对生产关系。
   库中地点、用途等属性若用于图谱，应保留外部来源身份，不能伪装成文档陈述。

最小真实模型对照：固定原段落、本体、模型和预算，比较未接库与接库；覆盖三记录齐全、缺少一条、
同号不同范围、多个编号对应同一实体、整体编号与成员同时命中、选择/备选表达。
不能向模型输入金标分组或把预先给定的三个查询请求当作模型自主发现成功。
