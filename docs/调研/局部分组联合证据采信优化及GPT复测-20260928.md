## 实施范围

仅修改 [protocols.py](../../backend/app/services/document_harness/protocols.py) 的 `referent_selection` 提示。与上一轮冻结运行模块逐文件比较，仅该文件有变化；v3 消息字段、Schema、分组登记函数、自评分辅助地位、原文定位及属性/关系核验均保持不变。

新的判断口径为：

- 先核对共享称谓、完整编号边界、成员归属与对象层级，再核对各表达精确查询的属性、类型与来源记录。
- 原文的编号列举结构与对应不同记录的完整键匹配共同支持多个文内成员，且无实际反证时，可选择该分组；不要求额外出现“和”“分别”，不要求逐一排除所有理论可能。
- 竞争菜单仅表示待比较的解释，不自带证据。原文明示的复合编号、改号/别名、层级冲突及编号子串必须处理，不能被单号命中覆盖。
- 命中、记录数、分隔符或缺记录中的任意一项均不能单独决定对象数；`complete` 不声明来源是权威全集。无来源命中仍可依据明确原文分组。
- 文内分组不确认来源全局身份，不决定生产地点的实际选择、全部参与或并行时间。

程序仍验证合法属性、原文范围、完整分组、成员不重叠及证据覆盖；模型分组为 supported 才能登记候选成员。本轮没有新增按斜杠自动拆分或硬编码车间编号的规则。

## 试验方法

入口：[harness_joint_evidence_probe.py](../../backend/app/evaluation/harness_joint_evidence_probe.py)。继续使用用户授权的 Responses 网关及 `gpt-6-sol`，不改变传输适配或模型配置。

1. 原句复用上一轮的原文、候选分组、原文片段、本体卡及冻结来源反馈。旧/新提示各三次交替调用；核验六次请求除 instructions 外完全相同，Schema 也与旧试验相同。
2. 明确并行句的新提示重复三次；七个边界各一次。复合编号、改号、显式歧义、子串和错误层级例新建单句 DOCX 并重新定位片段。改号例额外提供“同一成员拥有两个编号”的竞争方案；无来源及缺记录例对明确并列句的来源反馈做受控删减。这些属于开发回归用例，不是专家金标。
3. 各次选择回答均经过生产 Schema、`validate_partitions` 和 `resolve_selection`。参考答案只用于响应后的评分，不注入模型输入；未决和失败保留在分母中。
4. 两条原句分别从空 Engine 状态执行。冻结本体及精排结果，发现、类型、分组、属性、关系及共指全部重新调用 GPT；Mock 查询通过正式 `lookup_current` 在同一数据库只读事务快照内执行，保存逐次查询。评测状态和本体 world 写独立目录，不写业务事实。

预算为 60 次请求、1800 秒，每个完整运行最多 22 次。评测方法参照 [OpenAI Docs 的评测指南](https://developers.openai.com/api/docs/guides/evaluation-best-practices)，包含实际失败输入、典型例和边界例，并分别报告工作流各阶段结果。
