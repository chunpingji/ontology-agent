# 关系图谱暂停继续的状态存储简化分析

日期：2026-09-13。状态：基于当前工作区的代码与契约分析，尚未实施、迁移或部署。

实际新格式运行的耗时分布与性能关联见[缓慢原因分析](关系图谱识别缓慢与状态复杂度分析-20260913.md)。状态去重的设计收益与已测在线耗时分别说明。

范围：`DocumentAnalysisRun → OntologyGuidedExecutor` 关系图谱识别。用户明确当前版本只需暂停和继续，不支持回到历史检查点重新执行。本文不改变本体发布的回滚能力，也不将这一限制扩展为取消既有审核、局部修复、取消或删除能力。

本轮按用户明确方向收敛为：**一个当前恢复入口、一份权威工作状态、一份最新展示缓存，精排结果和调用账本独立保存。** 不再让每个执行时刻都成为永久可恢复的历史快照。下文的 v3 兼容与分阶段去重只用于过渡，最终目标以本节为准；当前尚未实施。

## 0. 极简目标与效率边界

这个设计能够针对性消除状态管理中的重复快照、历史链解码、全前缀重放和重复账本处理。要得到这些收益，必须同时改变状态的产生、更新和恢复方式，而不只是减少文件名或制品种类。

| 最终保留对象 | 最小职责 | 不再承担的职责 |
|---|---|---|
| 当前恢复入口 | 从同一 run 取得当前工作提交版本、冻结身份和调用账本水位；使用现有运行入口承载 | 不再增加另一份包含全部数据的恢复快照，不提供历史选择 |
| 权威工作状态 | 当前候选/证明 heads、依赖、待执行/重试/重验、覆盖、搜索阶段、精排活动游标及已消费结果标记 | 不内嵌全部历史任务、向量、模型响应，不从头重放才能得到当前状态 |
| 最新展示缓存 | 带工作版本的公开图与必要证据定位，沿用条件/否定/有效性投影 | 不参与恢复，不复制私有队列和精排历史，不永久保存每版展示图 |
| 独立精排结果 | 按精确输入、权限、模型及依赖身份保存结果；工作状态引用当前池、顺序和消费位置 | 不再每次保存完整 `RankingService`，不重复嵌入 graph/checkpoint |
| 独立调用账本 | 每个请求的身份、尝试、预扣、派发、结果引用、实际/未知费用，以及必要累计计数 | 不将全量回执数组放进每次工作提交或预扣载荷 |

“一份权威工作状态”是唯一数据来源，不要求只有一行大 JSON。沿用候选/证明表，并按运行、槽位、任务等稳定业务键保存当前分区即可；不再给新格式增加通用 `state_block` 内容树、历史前驱链或每 32 版大基线。不可变证据和已付费结果仍按稳定身份各存一份，属于结果与审计，不属于历史执行快照。

新格式必须满足四个执行要求：

1. **变更从产生处给出。** 完成任务直接产出变化的候选、覆盖、游标和依赖；只更新变化及受影响的依赖闭包。不能先遍历整个工作状态、生成完整 JSON，再比较哪里变化。
2. **继续时直接加载。** 加载当前分区和必要结果引用后，确定下一任务；不再解码历史链、重放全部 `task_outcomes` 或全部精排 epoch。当前 `GraphSnapshot` 不完整，需要补齐真正的执行状态后才能替换旧恢复。
3. **展示与统计按变化推进。** 候选或依赖变化时更新相关展示数据；只变预算、心跳或控制状态时不重建全图。固定文档证据索引、本体和按类型菜单复用。首版沿用现有协调器和提交边界，不新增独立队列或缓存服务。
4. **账本按请求更新。** 预扣、派发与响应分别更新对应请求记录及必要计数，事务校验本次合法转换；不为新增一次请求重新扫描全部历史费用或重新生成完整排序摘要。

单协调器负责工作状态和结果发布，模型线程只返回结果或提出持久化请求。公共运行 revision 可以继续供客户端刷新，但工作提交应校验 `work_revision` 和真实依赖版本，控制与调用账本各自维护必要版本。暂停、心跳、无关预扣不应仅因整条 run.revision 改变就使合法工作结果失败；取消、失租、删除和主体/证明依赖失效仍须拒绝不合法写入。

发布事务读取最新恢复入口，仅更新本次变化，保留已经独立提交的结果和账本水位。纯版本竞争可以有界重读并重验后提交，不能重新调用模型、回退费用或盲目覆盖。这样缩小当前 `HeadConflict` 的无关竞争范围，但不能承诺从此没有真实版本冲突。

暂停仍在安全提交边界完成；继续仍使用同一运行和新执行代际。预扣在派发前持久化，合法任务结果与消费标记、覆盖、工作版本和幂等回执一起提交。读取当前分区使用一致视图。最新权威状态损坏时明确报告不可继续，展示缓存丢失则可确定性重建。事务回滚、owner 隔离、证明版本和必要审计不属于用户历史回退，继续保留。

效率判断必须分成两层：

- **状态层的根因可以针对性消除。** 目标是日常状态工作量主要随本次变化和必要依赖扩大，不再随所有已完成历史反复增长；恢复成本取决于当前有效工作集，而不是累积执行轮数。这是待验证目标，不是当前代码已达到的性能结果。
- **整体识别慢还要处理模型工作量。** 已测运行中，摘要/识别请求占总历时 68.33%，1237 次发现/核验产生约 709 万输入 tokens，输入处理占其请求时间 80.87%。仅改变状态存储不会直接减少这些调用和输入。

作为边界说明：若保持本次模型工作量、单次时长及主识别串行关系，即使其余时间全部消失，这段已观察工作仍约需 **9.3 小时**；按原 13.6 小时计算是约 **1.46 倍**的极端值。原历时包含用户明确暂停，扣除后极端值约 1.44 倍。未归因时间并非全是状态开销，原运行又以失败结束，所以这些数字不是改造收益承诺，也不是全文完成时间预测。

要解决整轮缓慢，应同时减少相同主体/谓词/证据的重复模型义务，避免低收益分支持续扩大，并压缩每次提示中的重复结构、复用稳定前缀。必要原文、反证、条件与独立核验不删。状态简化与模型工作量优化分别测量，不能把质量损失或少执行必要任务当作提速。

最终验收至少包含：固定本次变化、增加已完成历史后，常规提交不重新遍历全部历史载荷；冷进程从当前状态继续且不重做已提交任务；未消费精排结果可接续；费用不重置；无关控制/账本更新不使合法批次失败；反证导致的失效仍传播；相同输入、本体和义务范围下分别报告正确结果、模型时间、状态时间及首条关系/目标路径/整轮耗时。仅完成去重、保留原历史重放不算极简目标完成。

## 1. 当前复杂度来自哪里

现有 [API 契约](../specs/021-ontology-guided-doc-graph/contracts/document-analysis-runs-api.md)已经要求继续同一运行，不提供历史检查点选择。代码的 `_restore_recognition_checkpoint()` 只取当前 head，要求候选和证明 heads 与数据库当前值相同。因此，“保存了多版状态”不代表“当前产品支持回退”。

| 对象 | 当前实现 | 简化方向 |
|---|---|---|
| 恢复检查点 `recognition_checkpoint` | 每批包含前沿、覆盖、任务结果、依赖、图、精排、模型调用状态，以及重复的重试、轮转和进度字段 | 保留一个当前恢复清单；状态各有唯一来源，清单只绑定精确版本与提交边界 |
| 内部图谱制品 `graph` | 保存图快照、选择映射、检索计划、依赖、诊断和精排状态；其中多项又在检查点内 | 去掉独立的完整历史包装；图的运行数据归入权威工作状态，展示所需内容由其投影 |
| 展示图谱 `public_graph` | 为读取性能额外保存图、选择映射、谓词菜单和部分依赖；仍使用不可变制品的多版存储 | 保留最新、可重建的展示缓存，不作为恢复依据，不保存每次刷新对应的历史图副本 |
| 状态块 `state_block` | 通用不可变块树复用大内容；v3 再增加基线与前驱增量链，块随运行一直保留 | 近期只保留当前恢复闭包和明确历史引用；目标按业务键保存当前分区，减少通用树、历史链和垃圾回收复杂度 |
| 精排状态 `ranking_state` | 独立制品保存，同时嵌入图和检查点；内容混合当前轮次、历史轮次、缓存、观察、派发回执和预算 | 过渡时只保留一个当前头；最终活动控制归工作状态，精排结果与请求账本独立，取消完整精排服务快照 |

可核验入口：批次组装与恢复见 [execution.py](../backend/app/services/document_analysis/execution.py) 的 `_persist_recognition_batch()`、`_restore_recognition_checkpoint()`；字段见 [ledger.py](../backend/app/services/extraction/ontology_guided/ledger.py)；展示制品见 [read_artifacts.py](../backend/app/services/document_analysis/read_artifacts.py)。

这些重复是逻辑载荷重复。现有块复用和增量编码已经减少部分物理写入，不能直接据此宣称磁盘占用或耗时会减少三倍。

## 2. 当前恢复入口与权威工作状态

当前恢复清单只说明“本运行现在从哪里继续”，概念上保留：

- 运行身份、owner、冻结指纹和状态格式版本；指纹绑定原文、本体、模型及识别政策。
- 当前提交版本、最后完整任务批次及其幂等标识、任务提交水位。
- 工作状态的提交版本、必要精排结果的精确引用、调用账本水位，以及当前候选/证明 heads 的一致性依据；兼容过渡期间可引用旧精排/模型状态制品。
- 恢复格式所需的执行代际信息；当前执行权仍由租约和 fencing 判定，不复制 bearer token。

一个恢复入口不要求把所有内容塞进一条大 JSON。当前工作分区、精排结果和请求记录由同一个运行入口绑定，清单是该入口的小型元数据，不另建完整恢复副本。读取时必须获得一致的已提交视图，不能先后随意读取几个可能正在变化的“最新状态”再拼接。

权威工作状态需保存前沿/游标、待重试任务、覆盖、搜索阶段、图中候选、精确证明依赖、待补证与重验任务、有限探索和公平轮转计数。只保存“下一任务编号”不足以恢复关系图谱识别。

可以消除的重复字段包括：检查点中从 `frontier.retries` 复制的 `retry_queue`、从 `frontier.turn` 复制的 `scheduler_turns`，以及多处完整 `graph_state`、`ranking_state`、`model_call_state`。进度指定唯一统计来源，其他位置仅为带版本的展示值。字段去重应进入新状态格式，不能让旧格式悄悄换含义。

候选/证明已有精确版本表，可供工作状态引用。合并后用事务边界、精确引用及内容校验保证一致性，消除现有“两份完整图解码后比较相等”的恢复步骤。不能仅保存一个未经对象更新事务维护的总哈希来替代校验。

## 3. 内部图谱与展示图谱如何合并职责

需要保留内部与展示的语义区分，但可以减少持久副本。

内部工作状态包含未决、否定、条件、失效和待重验对象，以及继续搜索所需的数据。展示图从中计算有效图、全部候选、拒绝项等视图，继续遵守端点精确版本、主体归属、证明有效性、反证、条件及人工审核的规则。

特别注意：**现有 `graph_state` 不是完整工作状态。** [projection.py](../backend/app/services/extraction/ontology_guided/projection.py) 的 `project_graph()` 即使采用 `all` 投影，也过滤不匹配当前端点版本的断言，并只留下相关端点节点。不能直接将该图改名后用于接续执行。

建议展示层保留一份当前轻量数据，按请求计算各投影，不给每种投影再存一套完整历史。沿用现有投影与审核叠加逻辑，保留证据选择映射。缓存身份绑定图/覆盖版本、投影策略及适用的审核版本；运行状态和精排摘要使用各自版本，暂停或一次预算变更无需重建图。

第一步仍在任务提交边界生成展示缓存，减少改动范围。最终缓存若丢失，可以由持久状态做确定性重建；GET 和页面刷新始终不能启动识别或精排模型。展示缓存损坏可以重建，权威工作状态损坏则明确阻止继续，不能静默选择较旧状态。

## 4. 状态块记录如何减少

`state_block` 是存储实现，不是产品状态。现有 [state_artifacts.py](../backend/app/services/document_analysis/state_artifacts.py) 将大对象拆块，块由运行绑定并一直保留至运行删除；[incremental_state.py](../backend/app/services/document_analysis/incremental_state.py) 每 32 版建立基线，当前状态最多需要其后 31 层增量。

因此可以取消“所有历史状态都长期可解码”的目标，但不能直接删除除最新 artifact 之外的记录：最新增量仍依赖前驱与基线。

近期可复用现有编码，仅保留当前恢复清单可达的基线、尾部增量和块，另保留被审核/修复等明确引用的数据。发布成功后再回收不可达数据，确保在途读取和未完成提交不受影响。该方案减少存储增长，但引用追踪和增量解码的代码仍然存在。

若要进一步降低设计复杂度，推荐新格式采用**按运行和业务键保存当前分区**：例如槽位搜索状态、任务状态、当前精排轮次、请求状态分别更新；不可变计划、模型结果和证据按稳定身份各存一份，由分区引用。可以使用一个统一的当前状态分区模型，不必为每个 Python 字段增加新表。

分区保存当前 payload、revision/hash 和所属提交版本，事务只更新变化的分区及当前恢复入口。旧执行态不再需要应用层的前驱链；数据库事务仍负责提交失败后的原子性。该目标需要新 reader/writer 和适用迁移，不能原地修改目前明确不可变的 artifact 行。

不建议改成每个模型调用前全量覆盖一个累计几十 MB 的 JSON，也不建议只在点击暂停时保存。前者重新引入编码放大，后者不能应对进程中断。历史验证已显示当前 v3 热保存与大基线/冷恢复的成本差异，见[增量性能验证](../specs/022-semantic-graph-closure/incremental-performance-validation.md)；该记录是历史证据，本次未重新测量。

## 5. 精排状态拆成当前控制、结果复用和审计

精排结果与请求记录独立于任务完成边界推进；活动排序控制归入工作状态，完整 `ranking_state` 制品只作为兼容过渡。评分或预扣可能在第一项识别任务完成之前已经发生，也可能领先最后完整图谱批次。每次预扣与已完成结果都应及时持久化，不能为了合并检查点而延后至任务完成。

精排或模型协议独立提交时，在同一事务更新当前恢复清单的对应版本引用，保持任务提交水位不变。任务批次发布须基于最新清单做 CAS/重读合并，不得用准备时的旧协议引用覆盖较新的结果。工作状态另记已经应用的 epoch/响应身份及消费位置，区分“结果已持久化”和“结果已进入图谱”，避免重复应用或遗漏已付费结果。

| 数据 | 建议处置 | 不能丢失的作用 |
|---|---|---|
| 当前活动槽位、待完成/暂停 epoch、已提交精确池、排序和消费游标 | 当前状态保存；大内容按 epoch/输入身份引用 | 继续原池与原次序，不因恢复重新评分 |
| 已准入/已消费记录、搜索阶段、依赖与失效标记 | 按槽位保存当前值 | 不重复准入，不把失效主体旧评分用于新任务 |
| run/slot/record/intent 费用、请求尝试次数、派发状态 | 当前聚合计数与持久请求账本分别保留 | 暂停、超时、换执行代际均不重置预算；未知派发不能作为免费重试 |
| embedding/score 缓存 | 从累计状态中移出，按权限、模型、完整输入及政策身份存一份并引用 | 已付费结果复用；缓存不能被当作关系成立的证明 |
| 确定性的 token 计数缓存 | 可成为有界派生缓存；确认为纯本地计算后允许重算 | 不把可重算计数与需要再次模型调用的结果混为一类 |
| 已完成 epoch 的完整 queries/views/observations | 结果记录单份保存；当前状态引用活动所需部分，历史详情按需读取 | 支持结果解释和复用，避免每次预扣遍历全部历史 |
| `paused_attempts`、`discarded_epochs` | 当前暂停/失效原因留在控制态，历史详情移入诊断或结果记录 | 失效轮次不能再被消费，已发生费用与失败原因仍有据可查 |
| `ranking_summary` | 保留最新轻量派生值 | 页面无需读取向量、完整计划或私有模型响应 |

具体字段见 [semantic_reranker.py](../backend/app/services/extraction/ontology_guided/semantic_reranker.py) 的 `RankingEpoch`、`RankingService.snapshot()`，以及 [executor.py](../backend/app/services/extraction/ontology_guided/executor.py) 的 `current_ranking_state()`。

`discarded_epochs` 也用于记录主体/依赖在精排期间失效，不是历史回退功能。可以用 epoch 引用、失效原因、请求引用和费用保留标识代替完整副本，但不能删除失效语义。派发账本的详细历史可以移出热状态，当前请求身份和合法状态转换仍须核验。

## 6. 暂时不能删除任务重放和精排历史

当前 `execution.py` 向执行器传递检查点的 `task_outcomes/frontier/recall_ledger/dependency_index/diagnostics`，并优先读取独立精排、模型调用状态。执行器从根节点和空工作图开始，逐项应用已保存的任务结果，重建已执行前缀；此过程不重新调用已完整提交的模型任务。

`committed_at` 与历史精排 epoch 参与这个重建过程，在原任务边界应用原排序。因此只保留最后一个 epoch、直接删除 `task_outcomes` 或 `ranking_excluded_slots`，会破坏当前恢复机制。

实施顺序应为：

1. 先把任务结果、epoch 和已付费响应各存一份，检查点使用引用，沿用原有重放与校验。
2. 定义能直接加载的完整当前工作状态，覆盖图、计划、菜单身份、搜索阶段、注册主体、证明代际、槽位完成度、覆盖、补证/反证重验及公平计数。
3. 在冷进程中验证直接加载与原重放得到相同的下一任务、排序、候选/证明、覆盖和剩余预算。
4. 再将热恢复收敛为当前状态加少量未完成协议；已完成任务结果作为证据与审计保留，停止每次从头重放全部历史。

这一步是执行器恢复方式的重构，独立于是否提供用户回退。可以分阶段验证，不必重写无关识别算法；但本轮极简目标必须完成直接加载，不能将原重放机制留作新格式的永久依赖。

## 7. 暂停和继续保留哪些状态边界

主流程仍为 `running → pausing → paused → queued → running`。`pausing` 表示停止派发并等待安全提交，与已经可以交接执行权的 `paused` 有区别。

暂停时停止新的模型派发，处理已经在途的工作；合法结果提交，未完成工作保留阶段和已发生/未知费用，然后发布暂停状态。继续时获取同一运行的新执行代际，验证冻结依赖和当前恢复边界，先接续已经持久化的结果及协议，再派发后续任务。

| 提交边界 | 必须一起保证的内容 |
|---|---|
| 模型派发前 | 请求身份、预扣/额度、派发认领状态先持久化；确认失败不得调用模型 |
| 评分或协议响应完成 | 结果与对应请求、输入、依赖及费用绑定，之后才能被任务消费 |
| 识别任务完成 | 候选/证明变更、覆盖与搜索反馈、当前工作状态、任务水位、批次幂等回执原子提交；第一步继续同步发布展示缓存 |
| 暂停/继续控制 | 控制版本、状态事件、执行权交接一致，旧 worker 的迟到写入被拒绝 |

统一恢复入口不要求图、精排和运行控制水位相等。控制事件及模型预扣可以领先最后完整任务；入口绑定各自合法的精确版本和关系即可。请求在外部已执行而结果未落盘的窗口，不能承诺绝对不重复物理调用；应保留未知状态与费用，按有限技术恢复契约处理。

不支持用户回退仍必须保留事务 rollback、CAS、owner 隔离、租约、失租拒写、幂等提交和指纹验证。新的反证导致旧关系失效属于当前运行继续产生的新判断，也必须保留。

## 8. 历史记录保留与清理前置条件

应该缩减的是历史执行快照，不是全部历史证据。候选/证明精确版本、审核、原文引用、调用费用和控制/提交回执分别按既有用途保留；由当前工作状态读取其必要索引。事件不等于完整恢复日志，不能删除检查点后直接宣称 SSE 事件能恢复一切。

目前有两处硬依赖需要先解除或明确保留引用：

- [DocumentRecognitionEventBatch](../backend/app/models/document_analysis.py) 的 `checkpoint_artifact_id` 外键指向每个批次的完整检查点。目标保留 `batch_id/hash/committed_version/sequence` 等小回执，解除对旧大检查点的强制引用；同键同内容幂等、同键异内容拒绝仍保持。
- [DocumentPropertyRepair](../backend/app/models/document_analysis_review.py) 的 `base_checkpoint_artifact_id` 引用修复基线；[reviews.py](../backend/app/services/document_analysis/reviews.py) 还从 `task_outcomes` 查找候选原始任务。应先建立稳定 `origin_task_ref` 和修复所需的精确候选/原文/任务边界，保留可解释的基线摘要与必要证据，再解除对整个旧检查点的依赖。

迁移完成前，这些引用会继续保留相关检查点及其完整恢复闭包；不能承诺“只剩一个物理检查点”。完成后的执行状态可以只保留当前版本，审核或业务证据明确固定的历史内容仍独立保留。

既有冻结运行继续其原格式，不能在 GET 或 resume 时静默改成新政策。当前分析不清理用户运行、不重写历史评测、不修改已有未提交实现；后续实施需要同步 021/022 的 spec、数据模型、恢复/精排契约和适用验收。

## 9. 推荐实施次序与验收

| 顺序 | 交付内容 | 验收重点 |
|---|---|---|
| 1 | 唯一当前恢复入口，去掉 graph/checkpoint/ranking 的重复重载荷；展示只保留当前缓存 | 原重放继续可用；精排先于任务提交时恢复不丢结果；公开图及证据选择等价 |
| 2 | 完成批次回执、候选原始任务、局部修复基线的引用调整；按当前闭包回收历史执行制品 | 重复提交不重复应用；修复/审核仍可追溯；清理后冷恢复、读取及跨用户隔离正确 |
| 3 | 采用按业务键的当前分区和源头变更，替代新格式的通用历史链；请求按行更新 | 小变更不重编码或遍历全部历史；事务失败不污染当前态；无关控制更新不造成工作提交冲突 |
| 4 | 完成完整工作状态直接加载，取消新格式的全前缀重放和完整精排服务快照 | 相同下一任务与排序、相同覆盖/证明及费用；已持久完成任务无新增模型调用；纳入极简目标必需验收 |

应覆盖：首任务前暂停；精排成功后任务尚未提交；预扣后崩溃；结果提交后确认丢失；暂停期间在途结果返回；失租旧 worker 晚到；反证失效；审核后修复；最新权威状态损坏；展示缓存重建；历史清理后恢复；预算耗尽后继续不刷新额度。

现有回归入口包括 `test_document_analysis_execution_recovery.py`、`test_document_analysis_model_call_recovery.py`、`test_document_state_artifacts.py`、`test_incremental_state.py` 和 `test_document_analysis_retention.py`，均位于 `backend/tests/test_extraction/`。实现后使用专用可销毁 PostgreSQL 库验证事务竞争与清理，SQLite 不能代替该验收。性能分别测热保存、基线/分区建立、冷恢复和展示读取，不将历史存储微基准当成本次在线收益。
