## 结论

这份短报告的主要问题是**对象发现的任务粒度、证明请求的大小，以及已识别对象后续工作的调度方式**。原文名称已经被准确定位，但系统仍把大量属性记录作为同一关系的对象发现任务。模型调用很多，并不代表对象类型和属性已得到充分核验。

`CMCReport —describes→ HRS-1597 (DrugProduct)` 在运行创建后 **2 分 49.69 秒**已获系统支持。本次核查时该结果仍保留。因此，应区分“没有识别名称”和“无法低成本形成类型明确、属性完整的对象”：本例的证据支持后者。

## 3. 为什么找到对象后仍要检查大量记录

当前基本执行单元是“主体 × 谓词 × 逻辑记录”。知道文档是 `CMCReport`，会得到合法关系菜单，但不会直接把基本信息字段组转换成一个待确认对象及其属性。

`ontology_plan._range_class` 把目标类的全部直接属性标签放入 `direct_field_labels`；`heuristic_search.candidates` 又把这些标签用于关系对象检索。名称类标签权重较高，普通属性标签也参与准入。因此，“这条记录含药物属性”被用于产生“对这条记录发起新药物对象发现”的任务。

本例 describes 的 H0 候选池为 **26 条**，H1 为 **9 条**，合计 35 条，占全文 86 条逻辑记录的约 41%。这是候选池规模，不代表已经完成 35 次模型调用。

| H0 排名 | 记录文本节选 | 对象发现时的实际意义 |
| --- | --- | --- |
| 1 | 项目名称：HRS-1597 | 有明确名称，是首次成功来源 |
| 2 | 项目代码：HRXS-P-2419 | 可作为身份线索，仍需判断项目与物料角色 |
| 3 | 是否细胞毒药物：否 | 对已有对象的分类属性，不能据此新建细胞毒药物 |
| 4 | 是否是高致敏药物：否 | 对已有对象的分类属性 |
| 7 | 分子式：C23H28N6O5S | 属性值，本字段没有对象名称 |
| 8 | 分子量：500.60 | 属性值，本字段没有对象名称 |
| 12 | 制剂剂型：口服片剂 | 剂型线索，需要核对其对应生产物料还是计划制剂 |

前 12 条实际都属于已识别的同一个 **19 条记录字段组**，系统已有这份分组信息。但在 [上下文组装](../backend/app/services/extraction/ontology_guided/context.py) 中，只有当前目标记录的原文标记为 `fact_eligible=True`，同组其他 18 条记录仅作为 `field_group_binding`，不能作为新对象端点来源。

这形成直接的不匹配：对“分子式”发起对象发现时，模型虽然在上下文里看得到 HRS-1597，却不能用该上下文名称新建端点；目标字段本身又只提供一个属性值。保存事件中，项目代码、细胞毒标志、高致敏标志、分子式等后续任务确实返回了空候选。

证据来源权限本身需要保留，不能把整组上下文无条件升级成事实。应调整候选任务的意图：由有名称/代码和归属证据的字段形成对象候选，由同组标量字段支持该对象的属性核验。单纯继续优化排序作用有限，因为正确名称已经排在第一位。

“是否细胞毒药物：否”是否定分类属性，既不是一个细胞毒药物对象，也不意味着否定 `describes`。降低成本时不能混淆这两种语义。

## 4. 类型判断应停在 DrugProduct 粒度

本次冻结本体与权威 TTL 的约束一致：

- [describes](../ontology/slpra/slpra-drug-development.ttl) 的 range 只有 `DrugProduct`，但注释写的是 “drug product / drug substance”。
- [DrugProduct](../ontology/slpra/slpra-drug.ttl) 定义为 “A finished dosage form drug product”。
- `ActivePharmaceuticalIngredient` 与 `DrugProduct` 都直接继承 BFO 物质实体，前者不是后者的子类。因此它不在本任务允许的 12 个对象类中。
- 同一模块的 `drugSpecification` 注释又包含原料药用途，说明当前业务表述与类型边界存在混用。

原文同时有“原料药”生产/供样语境与“制剂剂型：口服片剂”字段。此前据此要求先区分生产物料与计划制剂，超出了用户所需的 describes 识别粒度。该步骤只需核验报告描述的药品为 DrugProduct；不要求原料药/制剂、成品剂型或子类型判定。API 是活性药物成分，不能直接作为“原料药”的同义类型。

保存的首次核验结果将各项判断标为支持，而类型支持仍只引用 `项目名称：HRS-1597`。名称须结合原文药品角色和报告描述主体的联系核验；没有细分原料药或制剂不是缺口。系统 supported 仍应与原文证据充分性分别判断。

本任务无需提出 API 类型。此前将缺少 API 菜单视为完整性障碍、建议扩大 describes range 的推论撤回。修复收敛任务菜单至 DrugProduct 并明确核验粒度，保留权威 TTL，不将此次任务粒度政策解释为本体的全局重新定义。

## 5. 为什么有了 describes，属性仍迟迟不出现

在 [executor](../backend/app/services/extraction/ontology_guided/executor.py) 中，成功关系的对象会登记为下一跳主体，但分层模式下不会立即启动它的属性任务。`advance_layer` 要求当前层的调度、已准入覆盖、检索状态及补证队列满足完成条件后，才进入下一层。

所以本例在固定截止的 **18 分 27.54 秒**时，仍处于根节点关系层，有 9 条系统支持的关系、0 条属性。无关分支上的清洗方法引用失败和待补证，也可以推迟已经找到的产品对象的属性任务。这是“图中出现名称，但结果仍不完整”的直接执行原因；不能据此认定原文没有那些属性。

现有 [slot_completion](../backend/app/services/extraction/ontology_guided/slot_completion.py) 已支持有证明依据的提前结束，但 `single_value_candidate` 限定为属性、`max_count=1` 且约束已解析。`describes` 是关系，冻结计划未给出最大数量，不能利用此机制在第一个成功结果后结束搜索。也不能擅自把它改成单值，否则会漏掉多产品报告。

## 6. 建议的最小调整方向

| 优先事项 | 对应本例问题 | 应保留的语义边界 |
| --- | --- | --- |
| 对象候选按有来源的名称、代码及字段归属组织，复用已有字段组 | 同一组属性被逐条用于发现新对象 | 项目代码不自动等于物料身份；不同对象不因同组或同名合并 |
| 收紧 document-description 请求，仅传本任务需要的类型、原文和证明字段 | 496 字符原文被包装为两份庞大请求 | 保留原文锚点、对象角色、类型、方向、否定/条件及必要独立核验 |
| 评估让已获支持对象的属性按实际依赖就绪执行 | 不相关根层分支阻塞可用对象的后续结果 | 支持多对象及反证检查，不把局部完成宣称为全文完成 |
| describes 仅保留 DrugProduct 类型 | 后代类型菜单与额外剂型判断增加成本及未决 | 保留药品角色、描述关系和原文引用核验，不扩展 range |

对于这类显式字段，可以评估让程序先定位名称端点，再由精简的语义核验确认对象角色、类型及关系；不能用字段匹配直接替代全部语义判断。完整摘要在现流程中耗时明显，亦可评估明确名称候选是否必须等待摘要完成；本次未测量改变该顺序后的收益。

当前 −3 阈值作用于后续语义检索剪枝。既有固定截止内精排请求与剪枝均为 0，H0/H1 已准入的上述任务不先经过该阈值。因此继续调整 −3、增大输出限制或单纯提高并发，都不能消除对象发现与属性记录的意图错配。应保留用户当前阈值，将候选粒度和请求体积作为先验证的优化方向。

后续效果应在同一原件、本体与模型条件下比较：首个证据充分的 describes 耗时、相关属性形成耗时、重复对象发现次数、输入 tokens，以及多对象、否定分类、缺少药品角色的结果。原分析阶段尚无受控优化后的实测；后续数据另见修复验证，不能承诺降至几秒或一轮调用完成。
