## 1. 决策摘要与目标

### 1.1 核心决策

采用“**用户指定文档本体类型 → 本体限定当前主体的直接菜单 → 结构和摘要定位多个候选章节 → 完整原文记录发现实体 → 独立证明当前关系 → 以已关联实体递归展开直接菜单**”的主链路。

重构重点是把原来混在候选和布尔判定中的四种问题拆开：

1. 原文中是否出现某个实体提及，以及它属于什么类型。
2. 若干提及是否指向同一个文档局部实体。
3. 某个编号究竟标识哪个对象，是否足以建立跨文档唯一身份。
4. 原文是否支持当前主体与属性值/对象之间的**指定谓词**。

章节树和摘要解决“去哪里找”；原文和本体解决“找到了什么”；验证证据包解决“为什么可以这样归属”；调度台账解决“拒绝之后还找哪里”。四者不能互相代替。

### 1.3 用户操作与唯一新入口

用户选择或拖入 Word 文件，选择本体类型后点击“开始分析”。选择文件只更新待提交状态，不再立即请求摘要或识别；类型缺失时禁止启动，不从全文猜测候选根类型。

服务端保存该次源文件，冻结用户选择及本体/文档身份，后台依次构建 IR、记录索引与分层元数据，再执行本体指引识别。浏览器始终展示同一运行的两个产物；选择新文件或类型后须新建运行，不能重新标注旧图的根类型。新入口详见第 13 节，旧数据清理与单次切换详见第 14.3、15.5 节。

### 3.2 已在工程实现中闭合的四个缺口

1. **输入和生命周期**：运行级原文、必选类型、鉴权、owner 检查和后台持久运行已取代请求内临时文件流程；创建接口不等待图谱完成。
2. **摘要时序**：新运行先准备并冻结 MetadataSnapshot，两个 Tab 引用同一快照；页面只读请求不会隐式发起摘要或识别。
3. **版本与确认语义**：新工具统一运行级 ID/revision、直接保存证明，不经过旧 `persist_validated`/`automatically_review` 入口，不把系统验证等同专家确认。
4. **进度与显示**：统一 RunProgress、耐久事件水位和服务端图投影已接入 UI；候选树的展示连通性不再被当作语义有效路径。

以上工程交付不等于单次切换已获批准；真实数据库、质量、清理、浏览器与治理证据仍须通过发布门禁，不通过保留旧写入或双协议读取来规避。

## 4. 不可破坏的重构约束

为测试与审阅分配固定编号：

| 编号 | 约束 |
|---|---|
| I01 | 本体限定菜单及类型，不由模型新增 IRI、改 domain/range 或放宽类定义。 |
| I02 | 摘要、标题排序、候选置信度、已有图路径不是新增事实来源。原文标题可作为明示的上下文，不自动当实体名称。 |
| I03 | 检索范围不等于主体归属授权；授权必须绑定主体、谓词、范围、证据及版本，不能跨谓词泛化。 |
| I04 | 类型成立不要求全局唯一编号；类型、局部共指、全局身份分别判定。 |
| I05 | 物理 mention 去重不等于实体合并；同名、同项目、不同试验来源号均不能单独决定实体数量。 |
| I06 | 两端分别有证据不等于关系成立；关系须有与当前谓词匹配的原文桥接。 |
| I07 | 既有父关系只能授权递归和解释路径，不能证明子关系、子属性或产品组成。 |
| I08 | 类型/关系/属性拒绝不删除其他记录；技术失败不记作原文否定。 |
| I09 | 肯定事实、否定事实、条件事实、模型拒绝、审核拒绝是不同状态。 |
| I10 | 只有当前版本、证明有效、无条件肯定且未被审核拒绝的路径可以驱动肯定递归。 |
| I11 | 原文引用沿用 ID/精确子串协议；坐标由程序计算，权限、回放与语义分别校验。 |
| I12 | 同一新运行内的归并、拆分、审阅或证据变化必须可追踪；不能静默升级引用或用算法结果覆盖独立审阅。 |
| I13 | 每个范围内谓词均有检索台账与补充召回；路由阴性不得记作已穷尽。 |
| I14 | 新运行保留期内的原始提议与判定追加式不可变；历史离线实验不得改写。旧在线数据切换清理及新运行到期删除按明确规则执行，不等于修改判定历史。 |
| I15 | GET、刷新与切换 Tab 不得触发模型或识别候选写入；两个结果 Tab 共用同一新运行。模型调度、运行产物与业务事实提交是不同域，本工具不自动提交事实。 |

```text
                     │                              ▼

                     │                    PredicateEvidence
                     │                              ▼
                     └─ 仅有效肯定边 ─ ProofGate / EntityResolver
                                                    │
                                   RunStore / Ledger / Dependencies
                                                    │
                                           GraphProjection
                                                    │
           同一 recognition_run_id ────────┬─────────┘
                                     分层元数据 Tab / 关系图谱 Tab
```

摘要与结构只进入检索及带角色的原文上下文。模型阶段通过受控协议调用；模型没有写入注册表、授予权限、合并实体或提交事实的能力。元数据产物就绪即可通过只读 API 展示，不等待图谱执行完。

## 6. 数据契约：先分清对象，再编排模型

### 6.1 四层实体模型

| 层次 | 拟新增对象与关键字段 | ID 与约束 |
|---|---|---|
| 物理提及 | `SourceMention`：mention_id、analysis_id、source_cell_id、source_spans、text、record_view_refs | ID 来自文档/解析身份和物理来源区间，不含当前逻辑行、检索阶段或模型身份判断。同一合并 cell 被两行观察时只增加观察引用。 |
| 文档局部指称 | `LocalReferent`：referent_id、revision、mention_refs、coreference_proof_refs、alternative_refs | 名称/代码等不同提及只有经局部共指证明后归入同一指称；允许没有全局编号。共享 mention 不自动证明两项研究使用完全相同的物料实例。 |
| 本体实体解释 | `EntityInterpretation`：entity_id、revision、referent_ref、class_iri、type_decision_ref、qualifiers、level_evidence_refs | Product/API/批次等解释可竞争，不能因任务要求 DrugProduct 就赋予该类型；类型未决的解释不驱动肯定递归。 |
| 跨文档身份 | `IdentityClaim`：identity_claim_id、entity_ref、key_predicate、value_span、field_role_refs、identified_role、namespace、uniqueness_scope、qualifiers、decision_ref | 本体允许的身份属性只是必要条件；编号角色、命名空间和唯一性范围必须有依据。没有这些依据不建立全局链接。 |

局部实体句柄与全局实例 IRI 分开保存，建议增加 `identity_origin=document_local/verified_external/verified_key`。当前 `urn:evidence:resolved:` 的存在不能被解释成跨文档身份成立；必须检查其实际生成规则及适用域。

`qualifiers` 表示原文明示的时间、剂型、规格、批次等适用限定，值仍需来源；不是模型可自由发明的新本体属性。无法通过当前本体表示的事实保留为 `unmodelled_observation`，不偷偷映射到“最接近”的错误类或属性。

### 6.2 统一验证目标

新增 `VerificationTarget`，由程序构造并冻结：

```text
target_id = hash(
  run_fingerprint, claim_id@revision, check_kind,
  subject_ref@revision, predicate_iri, object_ref@revision | literal_hash,
  assertion_polarity, applicability, source_scope_hash, context_hash
)

VerificationTarget:
  target_id, claim_ref, task_id, check_kind
  document_context: {document_hash, document_class_iri, root_ref}
  subject_ref, subject_class_iri, predicate_spec_ref
  object_ref | literal_ref
  ontology_hash, source_scope_hash, context_hash
```

模型响应使用该请求允许的 `target_id`，程序以完整服务端目标检查返回的角色与端点。没有可自由替换的目标 class、predicate、revision。文档类型保留在 document_context，不以单个 effective_class 同时代表文档和当前主体。

目标签名只能防止目标串用，不能检查理由是否真的在讨论正确对象；这一点仍由角色证据、谓词证明和独立语义审阅承担。

### 6.3 判定不是一个总布尔值

新增通用 `SemanticDecision`：

| 字段 | 要求 |
|---|---|
| `decision_id / target_id / check_kind` | 指向唯一检查目标；check_kind 区分 type、field_role、local_coreference、global_identity、predicate_entailment、applicability。 |
| `verdict` | `supported / unsupported / undetermined / not_checked`。技术失败单独放执行事件，不伪装为 unsupported。 |
| `reason_code / reason / reason_status` | 新请求的支持、拒绝和不确定均要求理由及代码；not_checked 由程序写前置条件原因。离线审计旧 trace 的缺理由仅标 missing，不为此引入在线旧格式读取。 |
| `support_refs / counterevidence_refs` | 可回放原文引用；无反证列表不能解释成“已检查全文且无反证”。 |
| `searched_context_refs` | 明确本次实际看到的记录及范围；不可引用当次未提供的远处材料解释模型判定。 |
| `verifier_version / model_identity / attempt_id` | 可追踪模型输出、重试与版本；后续重验追加新判定，不覆盖旧判定。 |

新增 `VerificationBundle` 保存定位检查、类型/角色/身份/谓词检查、适用性检查、依赖检查。分清 `structural_valid`、`model_supported`、`policy_eligible`、`independent_review` 四层，不能从其中一层自动填充其他层。

模型拒答另记 `model_refusal`，其语义结果为 undetermined；禁止用空数组冒充已经逐项验证过的 unsupported。

### 6.4 关系与属性证明

`PredicateEvidence` 的最小字段：

```text
proof_id, proof_revision, target_id, predicate_iri
subject_role_refs
object_role_refs | value_role_refs
predicate_support_refs
bridge_kind
bridge_steps[]: {step_kind, input_refs, output_role, source_refs, decision_ref}
competing_owner_refs, counterevidence_refs
applicability_refs, dependency_refs, verdict, proof_policy_version
```

其中 predicate_support_refs 必须提供支持**当前谓词**的原文；不能仅重复主体名称、对象名称和父边来源。允许结构化字段组/表格映射与跨段指代作为证明，不机械要求原文出现谓词中文标签。

初始桥接类别：`explicit_assertion`、`owned_field_group`、`role_mapped_table`、`resolved_reference_chain`、`document_subject_description`。`same_document`、`same_name`、`adjacent_only`、`path_reachability` 只能作为检索/解释线索，不是可接受的桥接类别。派生推理若将来接入，须有已审核规则及独立 provenance，不能伪装为原文抽取。

### 6.5 原文角色与值存在状态

增加 `FieldRoleClaim`：`span_refs、header_refs、record_view_ref、owner_ref/owner_hypothesis、role_kind、ontology_slot_ref、verdict`。role_kind 可表达名称、属性值、项目编号、试验来源、批次标识、文档编号、组成成员、条件等**抽取角色**；它不是新增 OWL 类。角色不明时保留 unknown，不按编号外观判定身份。

增加 `ValueObservation`：`slot_ref、raw_text、source_refs、presence、interpretation、normalizer_version`。presence 至少区分 present、placeholder、not_mentioned；placeholder 的解释区分 unknown、not_applicable、unspecified。N/A 无补充语境时记 placeholder/unspecified，不擅自解释为未知或不适用，也不作为 CAS 事实值。

“否”可以是有效布尔值，不能被缺失值过滤器删除；原文没有提到、原文否定和模型拒绝也不能合并。

## 7. 本体直接菜单与元数据提示

### 7.1 LocalMenuCompiler 的确定性算法

先增强只读 OntologySnapshot：在当前扁平 schema 之外保留 declared_by、原 domain/range 定义、继承路径、同 IRI 的各项约束及定义来源 hash。当前 `semantic_schema_from_engine` 按属性 IRI 覆盖继承定义，单独消费该投影不足以证明约束未放宽。R2 须从引擎只读定义构建可追溯快照，规范“并列 range 声明、显式 union、继承限制”等不同语义；解析器不支持的表达式标 constraint_unresolved，不能把它们一律当可选类型并集。该变化是抽取快照契约增强，不是修改本体。

1. 固定 OntologySnapshot，读取当前主体实际通过的 class_iri。
2. 收集该类及本体允许继承的属性/关系，保留来源类与约束。这里的“直接”指**当前主体的一个谓词步骤**，不排除合法的类继承属性。
3. 数据属性产生 SlotSpec；对象关系产生 EdgeSpec，并只展开其正式 range 及合法子类闭包作为对象候选菜单。
4. 为本次关系的合法 range 类读取其名称、定义、身份属性和一层直接字段，作为检索线索；这不是预先创建二跳实体任务。
5. 关系通过之后，才为具体对象实例编译它自己的直接菜单。多跳类集合不得提前进入全文实体召回。
6. 相同谓词的继承约束须按增强快照保留的正式本体语义合并，不能用最宽 range 覆盖更窄约束。无法解析的约束显式诊断，不默认允许。

domain/range 是约束，不是存在性证据。不能因为 DrugProduct 有 hasActiveIngredient 就认为报告里必有该边；不能把逆关系、未声明属性或非当前类菜单偷偷加入任务。合法子类太多时按确定性小批处理，台账保留剩余类型，不依赖首批命中裁掉后续类型。

类型验证可附带少量必要的相邻类/竞争角色定义，用于区分实体与容器、试验、API/制剂；这属于 contrast_context，不是扩充 allowed_output_types。验证上下文若出现一个非当前 range 的正确解释，只能保留类型分歧/观察，不能绕过局部菜单直接产出该边的对象。

给定根类型是用户确认的运行输入，不计为抽取成功。本文档工具必须由用户选择 root_class_iri；缺失或无效时前后端均拒绝启动，不自动分类、不从全文生成候选根类型。

### 7.2 CMCReport 示例

09 冻结 schema 的 CMCReport 菜单有 12 条关系、0 条数据属性；实现中必须动态编译，不把这个数量或全部列表硬编码。

| 当前主体 | 当前谓词 | 对象/值菜单 | 检索线索的边界 |
|---|---|---|---|
| CMCReport | `https://ontology.pharma-gmp.cn/slpra/drug-development/describes` | 正式 range 为 `https://ontology.pharma-gmp.cn/slpra/drug/DrugProduct` 及合法子类 | 产品概况、项目名称、剂型等帮助排序；API 不作为该边的直接对象。 |
| CMCReport | `https://ontology.pharma-gmp.cn/slpra/drug-development/hasSynthesisRoute` | 从当前本体读取 range | 合成路线章节是候选范围，章节标题本身不等于路线实例。 |
| 已关联 SynthesisRoute | `https://ontology.pharma-gmp.cn/slpra/drug-development/hasStep` | `SynthesisStep` | 每个步骤须有自己的原文证据；步骤顺序使用 `stepOrder` 或 `nextStep`。 |
| 已关联 SynthesisRoute 或最终 SynthesisStep | `https://ontology.pharma-gmp.cn/slpra/drug-development/producesFinalProduct` | `DrugProduct` 或 `ActivePharmaceuticalIngredient` | 只有明确的路线/最终步骤—最终产物证据才能建边；不从同一报告内的共现补造。 |
| 已关联 SynthesisStep | `https://ontology.pharma-gmp.cn/slpra/drug-development/producesIntermediate` | `ProcessIntermediate` | 允许一个步骤产生多个中间体；RDF 多值断言本身无序。 |
| 已关联 ProcessIntermediate | `https://ontology.pharma-gmp.cn/slpra/drug-development/intermediateIdentifier` | `xsd:string` | 保存 `SM5592-A14`、`SM5592-A15` 等原文明示标识；裸标识不作为跨项目全局唯一键。 |
| 已关联 DrugProduct 或 ActivePharmaceuticalIngredient | `https://ontology.pharma-gmp.cn/slpra/drug-development/hasProcessIntermediate` | `ProcessIntermediate` (`0..*`) | 这是经已明确最终产物路径可推导的无序产品/API 级视图，不是报告共现或数组位置关系。 |
| 已关联 DrugProduct | `https://ontology.pharma-gmp.cn/slpra/drug/hasActiveIngredient` | `https://ontology.pharma-gmp.cn/slpra/drug/ActivePharmaceuticalIngredient` | API 表头支持寻找 API；仍须独立证明其与具体产品的组成关系。 |
| 已关联 DrugProduct | appearance、dosageForm 等本体数据属性 | 对应值类型、单位、条件 | 不因词形符合属性就跳过主体和制剂/API 层级核验。 |

原文中的“口服片剂”可支持产品解释，毒理表 API 列可支持 API 类型；二者不能仅凭 HRS-1597 同名就构成组成边。也不得为强行成功而将 API 解释成 finished dosage form。

以 HRS-5592 场景为例，路线通过 `hasStep` 连接各合成步骤，各步骤再通过 `producesIntermediate` 连接标识为 `SM5592-A14`、`SM5592-A15`、`HRS-5592` 的 ProcessIntermediate；路线或最终步骤通过 `producesFinalProduct` 连接最终 DrugProduct/API。如果同一字面标识 `HRS-5592` 在原文中同时承担工艺中间体和最终产物角色，分别保留对应角色实例及证据，不因字符串相同自动合并。

`hasProcessIntermediate` 上的两条 `owl:propertyChainAxiom` 分别覆盖路线直接指向最终产物，以及最终步骤指向最终产物后回溯所属路线的情形。它们是正式可推导公理，不代表当前服务已运行 reasoner 或已将产品级数组物化到 ABox/API。在增加版本化推导器或显式路径投影前，业务端应以基础边为准；任何数组展示均须保留其路线、步骤和来源版本。

### 7.3 MetadataSnapshot 与潜在关系—实体标签

元数据最小契约：`snapshot_id、analysis_id、document_hash、structure_hash、summary_version、summary_model_identity、generation_source、source_record_refs、node_summaries、dependency_hash`。generation_source 区分模型摘要、摘录回退、无摘要。所有摘要只关联有效的原始节点/记录，不生成 fact-eligible 来源 ID。

检索标签采用 `RetrievalHint`，而非 Candidate：

```text
hint_id, metadata_snapshot_id, node_id | record_ids
subject_type_iri, predicate_iri, object_type_iris
hint_kind = relation_target | entity_role | property_value
support_origin = heading | summary | source_label
source_record_refs, score_components, policy_version
authority = retrieval_only
```

标签只能从 LocalMenu 及当前关系的合法 range 中选择；模型输出未知标签立即拒绝。标签表示“这里值得找某关系/类型”，不能授予主体归属、确认实体类型或触发全局归并。

先采用可复现的确定性排序：当前谓词/合法 range 的原文标签、列头、章节标题、节点摘要分项计分。保持分量可审计，首期不训练一个不可解释的总分分类器。后续语义重排仅改变顺序，不改变必保留的补充队列。

GLiNER 是可选的原文 mention 召回器：动态标签由本次小菜单映射而来，输出必须回到当前原文 span；它不判定实体全局身份、属性归属或 hasActiveIngredient。缺失或未命中时仍有主召回路径。离线历史对照锁定相同权重/阈值；不在本次重构中更换模型并将收益混算为架构收益，也不为对照保留线上旧实现。

### 7.4 摘要准备与稳定性

正式识别入口显式准备元数据，模式为 `cached_summary / generate_summary / structure_only`，选择进入 run_fingerprint。页面 GET 继续只做预览，不能因此阻塞或触发摘要生成。

可用且 hash 匹配的摘要直接复用；缺失时由显式后台识别任务生成，或记录为 structure_only。降级不能标作摘要模型成功。摘要在识别开始前冻结；晚到的新摘要只能用于新 run，不能改变当前 run 的快照、排序、缓存或完成度。摘要成本单列，不藏进抽取耗时，也不能算作正文事实。

## 8. 记录检索与完整验证上下文

### 8.1 物理来源、记录视图和语义对象分开

保留 SourceRecord 的段落/逻辑表格行粒度，增加两个辅助对象：

- `FieldGroup`：同章节连续、带标签的字段块；保留每一段的来源和候选 owner，表格/标题/章节边界阻断无条件扩展。
- `RecordView`：物理 cell/段落在某逻辑行的视图，保留 column_ids、logical_row_ids、header_refs、rowspan/colspan、单位、图例、父表及相关注释。

FieldGroup 只是局部共指和属性归属的候选结构，不预先声明所有字段具有同一实体层级。RecordView 不生成新 mention，也不按试验行数生成 API 实例。嵌套表父容器只提供上下文，不能把父表文字自动变成子记录的新事实目标。

### 8.2 每个主体—谓词统一两阶段

计划键为 `subject@revision + predicate + ontology_hash + source/metadata_snapshot + retrieval_policy`。

第一阶段按高相关章节排序，默认沿用最多三个章节的实验初值；各章节轮转。第二阶段保留该次文档范围内的所有其余非标题记录，包括零匹配、路由阴性和其他章节。该机制同时用于关系与属性，不能只覆盖 focus_path。

计划满足：两阶段不重叠、并集等于范围内全部目标记录、没有记录因一次候选拒绝被移除。表头和标题可以是验证来源，但不作为单独的实体召回目标；如果原文确实在标题中陈述事实，应由明确的标题事实政策另行支持，不能偷偷放开全体标题。

提供 `focus_path` 与 `document_graph` 两种 scope：前者仅用于焦点验证，其他根谓词标 `out_of_scope`；后者全部根直接谓词都进入计划。所谓“完整两阶段”只指该运行范围内的调度覆盖，不保证已经发现文档所有真实实体。

### 8.3 范围授权必须针对断言

原文记录一旦被检索到，就可用于发现当前合法类型的 mention；这不等于它的事实可以归属于当前主体。将以下范围分开：

1. `discovery_ranges`：可发现 mention/值的原文。
2. `binding_ranges`：可解释身份、指代、单位、条件和桥接的原文。
3. `authorized_claim_ranges`：已经为当前主体及特定谓词/角色获得证明的范围。

跨记录检索先产生候选，逐条通过谓词归属检查后才产生授权。产品代码被确认，只能支持相应的身份或共指用途，不能因此授权“同份文档中所有属性都属于该 Product”。

### 8.4 TaskContext 的必需内容

上下文必须保留：当前目标、主体/对象的原文构造来源、当前完整逻辑记录、相关表头和合并映射、连续字段块、已知竞争主体、原文明示的否定/条件/反证、可绑定父容器、根与祖先路径的独立角色。

调用内来源别名 c0/e0 等仅在该请求有效，日志保存局部到全局映射。同一原始区间去重时合并其角色和权限，不因去重丢掉反证或把 binding-only 升成 fact-eligible。候选的历史模型理由可以保留在审计，不作为新的可靠原文传给下一验证器。

引用继续使用 FactSpan/BindingSpan，wire 仅为 evidence_id 与可选精确 text。禁止模型 start/end/context；唯一子串由程序计算坐标，重复子串不任选第一处。新增原子协议从 evaluation 移入公共核心时必须保持已有回归行为。

### 8.5 大记录和上下文超预算

不能静默截掉表头、另一逻辑行的反证、竞争主体或原主体证据。先进行不损失内容的结构去重和局部菜单分批；仍无法容纳则记录 `context_budget_exceeded`，保留记录并继续其他任务。

后续若支持记录投影，投影必须满足：当前字段、完整 owner/关系角色、列头、单位、合并映射、条件与竞争 owner 的证据闭包均在；其余部分进入显式未检查台账。一个视图不能通过完整闭包检查时，不允许拆成独立小格后宣称原记录已验证。首期可不实现这种复杂投影，明确超预算比假装无事实更可靠。

## 9. 验证流水线与证据门禁

### 9.1 执行顺序

每个原文记录产生 ProposalBatch，其中每条提议独立执行：

```text
协议/引用定位
  → mention 与记录角色
  → 类型检查（实体提议）
  → 局部共指、标识角色、全局身份检查（按实际需要）
  → 属性值存在性/规范化，或关系对象选择
  → 当前主体/对象角色与当前谓词桥接检查
  → 极性、条件、适用层级及竞争归属检查
  → 当前版本与证据依赖检查
  → 保存判定；计算候选可用性；必要时递归
```

无全局身份不阻断已有充分局部实体及谓词证据的抽取。没有通过的类型解释则不能建立该类型肯定节点和肯定递归；原 mention 和竞争解释仍保留。类型未知时不得为了探索二跳而先保存一条假的第一跳。

某条提议已经明确定位失败或前置语义不成立，后续阶段记 `not_checked` 并结束该条提议，继续其他提议/记录。09 CAS 的 binding=false 后继续调用 reference 是历史行为；新执行器应避免这种会遮蔽首个拒绝原因的路径。原始和派生 reason 都保留，不能只剩最后一个异常字符串。

### 9.2 类型、标识角色和唯一性三道检查

类型检查回答原 mention 是实例、属性值、章节标题还是其他角色，并根据真实本体定义判断。缺少身份键本身不是类型否定；项目代码存在也不是 finished DrugProduct 类型成立的充分条件。

身份验证分为：

1. **标识对象角色**：字段值究竟标识产品、API、项目、试验、文档或批次；引用字段/列头以及必要的 owner 来源。
2. **局部对应关系**：该标识是否与当前实体解释相关，而非同表的其他对象。
3. **唯一性适用域**：命名空间、发行方/系统、时间/规格/批次范围及本体身份约束，是否足以支持所请求的 identity scope。

只有所请求层级的全部检查 supported，才能升级该层级身份。原文没有说明唯一性，结果是 undetermined，不可用模型置信度代替。被确认属于试验来源的编号，对“API 唯一身份”提议应给 unsupported，并保留其实际来源角色，而非删除编号。

未支持身份继续只显示验证状态，不在下游主体、共享候选、路由和缓存中作为可靠 key。初次身份验证必须看得到待验证键及其来源。这保留 v6 已修复的信任传递，并新增“错误 true 也要经过角色和唯一性门禁”的要求。

### 9.3 PredicatePolicyRegistry：区分描述、属性与组成

新增版本化的验证政策注册表，输入是**精确谓词 IRI 及本体约束**，输出是允许的证明类型、必需角色与禁止推论。它不修改本体，不包含 HRS-1597、项目号或文件专用抽取规则；政策须经业务审核、随实验冻结。无专门政策的谓词使用通用显式断言/明确角色表格政策，不能默认放行。

| 谓词语义 | 可接受的来源形式 | 必须拦截的替代证据 |
|---|---|---|
| 文档描述正文对象 | 已知文档根、正文真实对象、原文描述结构及匹配的描述谓词；无须正文重复报告标题或逐字出现“描述”。 | 只有标题、只在目录出现、引用其他报告的对象、与本文主体无关的背景提及。 |
| 实体数据属性 | 主体明确的显式陈述、经过 owner/层级验证的连续字段块或表格字段、可回放指代链。 | 只有数值/属性词、只有同节/同报告、字段属于 API 却挂到制剂、历史批次事实挂到当前批次。 |
| 产品含活性成分 | 明确组成陈述、主体已确定的配方/组成表、经原文消解的跨记录产品—成分关系。 | API 表头、毒理试验行、同名、项目代码、父 describes、domain/range 允许该边。 |

`document_subject_description` 是对文档描述关系的证明类别，不是文档根的无限授权；不能在 hasActiveIngredient 检查中使用。只有来源属于本报告仍不足以证明对象是本报告描述的实例，需区分主题内容、背景和他文引用。

跨记录证明至少包含“指称消解”和“当前谓词陈述”两个不同责任；可以由同一片段支持，也可以由多段组成。不强制两端名称同句出现，也不能只有若干 same_referent 步骤而没有任何 predicate_assertion 步骤。

### 9.4 结构门与语义门的分工

程序硬检查：目标签名、引用域、唯一定位、角色引用完整、允许的桥接类别、端点与依赖版本、极性/条件一致、无循环证明、自我证明或仅父路径证明。

独立语义检查：引用实际是否支持所声称的角色和谓词、来源号究竟属于什么对象、粉末是否为制剂性状、跨段指代是否成立。该检查使用原文和目标契约，不以召回模型的自由理由作为已知事实。

首期保留召回与验证的独立调用；角色、身份和谓词决定分别留档，可在不混淆目标的前提下批量请求。局部 binding 与跨记录 reference 都调用同一目标/证明契约，不再维护两套目标字段缺失的协议。跨记录情况在通用谓词验证外还必须通过指称桥接；本地字段同样不能跳过 owner/层级验证。

当模型填入 `bridge_kind=role_mapped_table` 但表格没有产品角色/组成映射时，不能仅因 schema 合法放行。硬约束只能检查证明结构，语义检查仍可能误判；关键配对反例、独立来源审阅和上线前质量验收不可删除；取消灰度不等于取消这些检查。不能宣称新增一个 verdict 字段解决了 09 的错误 true。

### 9.5 极性、条件与层级

肯定、否定、条件原文均可成为有证据的候选；只有无条件肯定关系进入肯定递归。模型认为“未获支持”不是原文否定，不生成 negated 边。

属性的 owner/type/applicability 一起核验。例如“类白色到白色粉末”可以明确属于某局部化学物质条目，但对 finished DrugProduct 的归属仍未决；保留 ValueObservation 与拒绝/待定理由，不能为了输出把该属性移到一个当前本体不允许的类上。

冻结本体若存在定义与注释冲突，记录 `ontology_constraint_ambiguity`，遵守正式类型/range 限制，对受影响提议保守待定；其他独立谓词继续。是否对冲突定义继续修改本体是后续单独治理事项，不作为本轮继续检索的前置条件。

## 10. 实例归并、图递归与失效传播

### 10.1 归并权限表

| 情形 | 操作 |
|---|---|
| 同一物理 span 在另一逻辑行再次出现 | 去重观察，增加 record_view_refs；不自动创建或合并业务实体。 |
| 连续名称/代码字段有明确局部对应 | 可建立 local_coreference proof、归入文档局部指称；全局身份继续独立判断。 |
| 相同名称、相同项目但缺局部对应 | 保留 possible_coreference，不能合并。 |
| 来源号不同而 API 名称跨行合并 | 保留一处 mention 和多次研究观察；实体数量未决，不按来源号拆成多个 API。 |
| 可靠键在相同 namespace/scope 下相同，类型及限定兼容 | 可以建立全局关联；须同时检查冲突来源、同名多剂型/批次等反证。 |
| 明确不同对象，或标识/层级冲突 | 拒绝归并；冲突不能通过第三个模糊节点的传递闭包被消解。 |

每次合并/拆分保存 `ResolutionEvent`：输入实体/mention 精确版本、决定依据、canonical 选择、别名映射、更新后的版本、受影响断言与范围、旧值及新值。继承旧 canonical ID 的稳定性，但不以稳定 ID 掩盖意义变化。

拆分是显式重新归属，不是一对多 alias 改写。旧实体解释先失效，每条属性/关系根据自己的 proof 重新确定新端点；无法唯一归属的断言保持 invalidated/undetermined。禁止把旧属性复制到所有新节点，或默认继承给保留 canonical ID 的节点。只有重新获支持的断言才能形成新版本、恢复递归或进入有效图投影。

### 10.2 统一 EligibilityPolicy

从当前多个 `_usable`、positive_eligible 和图导出判断中抽出统一政策：

```text
seed_eligible(root) =
  root 的 document_hash 与冻结 IR 相同
  AND 根类型来自用户提交的 root_class_iri 且符合根类型政策
  AND 来源角色允许（analysis_source/default_source）
  AND 根授权未被撤销或审核拒绝

expandable(entity, incoming_path) =
  entity 的类型和局部指称足以支持当前解释
  AND incoming_path 存在当前有效的肯定证明
  AND 所有必要引用版本匹配
  AND 非条件、非否定、非冲突
  AND 相关实体/边未被审核拒绝
```

RootSeedPolicy 是唯一无入边启动例外：seed_eligible 的文档根可以展开自己的直接菜单，不伪造父边或原文抽取 proof，不计入抽取 TP。普通实体不能使用该例外，也不能通过文档标题给自己授予 root 权限。

无全局身份不是否决条件。independent_review=unreviewed 不阻断原文证明已支持的分析路径探索，但图上须标明未经专家确认，不因此取得业务事实提交资格。领域层已有明确审阅拒绝事件时按依赖规则阻断；首期工具不要求新增审核按钮。

对象已识别而当前关系未通过时，保留对象候选为 unassociated；不能沿失败边将其属性归到根图。其他合法关系若在后续记录独立关联该对象，可以激活对象的直接菜单。

### 10.3 依赖是证明依赖，不只是树父指针

建立 DependencyIndex，覆盖主体解释、局部共指、身份键、谓词证明、范围授权、关系路径、审核状态及原文/元数据版本。

除显式引用依赖外，还记录 proof 的读取范围与竞争集合订阅：`record/field_group + owner_role + applicability + competitor_set_version`。同一原文中后来发现的新 owner 可能不在旧 proof 的引用列表；新解释进入订阅范围时主动重算相关结论，不要求原文 hash 变化。旧 supported、unsupported、undetermined 均可能失效或需要重验，不能只重验待定项；替代 OR proof 也须证明未受同一新竞争证据影响。

一个证明中的必要依据是 AND；同一断言的独立替代证明是 OR。父边被拒绝时，依赖它的路径授权失效；若存在另外一条完整独立有效路径，应重新计算可达性，不能机械删除全部对象事实。反过来，没有独立替代证明时不能只改引用版本让断言重新通过。

已独立证明但不再根可达的候选可保留在非根投影；必须依赖已失效实体解释的断言标 invalidated。历史肯定判断、审核拒绝与当前失效状态分别保留。

### 10.4 递归与公平调度

保留主体的直接谓词轮转和章节轮转；子分支与尚未完成根分支采用有界加权轮转，默认沿用“两次子记录/一次根记录”的实验初值。关系与属性各一次轮转，不能因庞大属性菜单阻断 API 候选，也不能因描述分支未成功阻断其他根关系。

防重键至少含 entity@revision、predicate、record、scope/proof 依赖 hash；路径作为见证单独保存。循环本体不等于可以无限递归：相同实体/谓词/证据上下文只执行一次，max_hops 与任务安全上限保留。因为 hop/task 上限未探索的前沿显式记录，不能报告全图穷尽。

## 11. 拒绝、续检、覆盖与停止状态机

### 11.1 四个独立维度

| 维度 | 拟新增状态 |
|---|---|
| `execution_state` | queued、running、finished、retryable_failure、blocked_dependency、paused |
| `semantic_outcome` | supported、unsupported、undetermined、not_checked |
| `assertion_polarity` | affirmed、negated、conditional、uncertain |
| `coverage_state` | unattempted、attempted_incomplete、examined；路由分数/阴性另列 |

工作单元为主体—谓词—记录，其下有 proposal 与 stage 子事件。一次模型调用、一次提议、一个记录、一个谓词和一个图分支分别计数，不相互替换。

### 11.2 拒绝处理转移

| 当前事件 | 当前提议 | 同一记录/谓词后续 | 全局影响 |
|---|---|---|---|
| 类型不支持 | 该类型解释 unsupported，不生成肯定实体 | 继续其他合法类型/提议和下一记录 | 不宣告没有 DrugProduct。 |
| 身份角色不支持 | 身份提议 unsupported；可保留已通过的类型/局部实体 | 继续关系/属性验证所需的局部证据 | 不用该键归并，不停止主体所有任务。 |
| 缺少组成/owner 桥接 | 断言 undetermined；已独立发现对象保留 | 有界补充上下文；随后仍继续其他记录 | 不生成肯定边，不沿该边递归。 |
| 有明确相反的原文证据 | 提议 unsupported；原文否定另走否定事实验证 | 继续其他提议/记录 | 不自动写一条否定边。 |
| 引用/记录映射错误 | 执行失败，语义阶段 not_checked | 允许协议修正或留作未完成；其他提议继续 | 不记作原文无事实。 |
| 模型拒答/输出无法解释 | 保留原始答复，undetermined 或技术失败 | 有界重试，超限仍保留未解决项 | 不无限占用整个队列。 |
| token/请求超时/模型不可用 | 技术失败、原任务未完成 | 可恢复失败队列；局部失败让出调度机会 | 整体服务不可用时安全暂停，不伪造空结果。 |
| 人工审核拒绝上游边 | validation 历史不改，审核状态更新 | 重算依赖并阻断失效任务 | 其他根谓词/独立路径继续。 |
| 第一阶段无肯定输出 | 第一阶段各记录保留实际结果 | 必须进入第二阶段 | 不能因 phase1 全拒绝而结束谓词。 |

新版本初始重试政策：同一输入的语义 unsupported 不靠重复采样“刷到通过”；undetermined 只在新证据或显式上下文扩展后重验。每条提议默认最多两次有新证据的补充验证，技术重试另由 TaskBudget 限定，配置与实际次数进入 run 身份/日志。额度耗尽标待解决，不删除其他待检索记录。

补充验证额度按稳定 `claim_lineage_id` 计，而不是易变化的 proposal_id；用 evidence_delta_hash 识别实际新证据，纯 alias、revision 或计划重建不算新证据，额度跨这些变化继承。已 supported/unsupported 的提议遇到实质新证据也由第 10.3 节触发重验；先撤销不再可靠的使用资格，额度不足时保留未决，不继续使用旧通过。默认每处理一次重验，至少让出一个未尝试记录的调度机会；没有新记录时才连续处理重验。显式追加额度需记录操作者和理由，不允许循环归并绕过限额。

claim_lineage_id 由执行器首次登记逻辑断言时签发并随内容版本保留，模型不得指定。重复提议先匹配主体 lineage、谓词、对象/值及适用限定；实体归并导致两个断言 lineage 合流时已用额度并账，实体拆分时子 lineage 继承已有消耗，不因分裂获得全新额度。无法确认重复的提议保留独立审计，同时仍受主体—谓词与整轮安全预算约束。

### 11.3 RecallLedger 与覆盖守恒

每个范围内主体—谓词保存 planned_record_ids、phase1/phase2、range_type_batches、路由结果、实际任务/调用编号、每阶段判定、剩余记录及触发重验的证据版本。

要求 `planned_records = unattempted + attempted_incomplete + examined`，三者按当前有效计划互斥。queued/running/retry_pending 是执行维度，不能再加到覆盖总数中。旧计划失效时单独归档，不混入新计划分母。

examined 表示计划的必要类型批次和提议检查均有终结记录，可以全是合法拒绝或待定；待定另计 unresolved_claims。技术失败且检查未完成为 attempted_incomplete。空召回记录 `no_candidate_observed`，不是证明世界中不存在事实。

这里的“待定”必须是模型完成目标检查后返回完整、合法的语义 undetermined；召回拒答、类型决策缺项、协议失败或技术前置失败产生的 not_checked 都是 attempted_incomplete。前置语义明确 unsupported 后按政策跳过后续检查，才属于合法终结。重试额度耗尽不会把前一类未完成提升为 examined；即使可执行队列已空，仍不能映射 completion=complete。

后续执行证据必须是更晚的不同记录实际调用/任务事件；同一条提议从 binding 到 reference 不算“继续其他记录”，同记录的兄弟提议继续也单独计数。pending 队列只能证明工作被保留。

### 11.4 正常结束、暂停与取消

新增 RunStatus，分开：

- `execution_status`：queued、running、paused、finished、failed、cancelled。
- `stage`：ingest、parse、metadata、recognition、finalize；各阶段另有状态和错误，不用一个 loading 覆盖全部过程。
- `coverage_status`：partial、exhausted_in_scope。
- `semantic_status`：unreviewed、unresolved、reviewed；另带 unresolved_claims/invalidated_count 和审阅来源，模型不能自行设 reviewed。
- `stop_reason`：queue_exhausted、operator_pause、operator_cancel、observation_complete、budget_limit、service_failure、retention_expired 等。
- `artifact_status`：metadata 与 graph 各自为 pending、building、ready、partial、failed；图谱 partial 可以已有有效节点/边，并不表示全图完成。

控制请求另存 `control_action/control_version`；收到 pause 请求后显示“正在暂停”，安全边界提交成功才转 paused。删除使用 `deletion_state=none/requested/deleting/deleted`，不伪装为正常执行完成；requested 起即拒绝领取、恢复及识别写入。以上控制状态及允许操作由服务端返回，前端不根据按钮点击自行推定成功。

正常语义拒绝不自动令整个执行 failed；队列耗尽不自动令语义准确或完整。新 API 的 `completion=in_scope_complete` 只在必要计划已执行、没有技术未完成或未探索上限前沿时成立，显示“范围内处理完成”，不显示“事实全正确”；其他情况均为 incomplete。完成执行但仍有语义未决时，执行完成度和未决数同时展示。

软暂停在原文记录/原子事件批次的安全边界保存；paused 可恢复。取消立即撤销执行令牌，禁止后续写入，保留已持久化产物为取消时快照；cancelled 不能恢复，要继续须新建运行。关闭页面、切换 Tab 和清空本地选中文件都不自动取消后台任务。

租约丢失、异常退出或取消时，当次未完整提交的记录保持 attempted_incomplete；恢复按日志确定最后一个完整事件，不伪造正常记录结束。历史 09 的观察清单暂停仍是 incomplete；新真实全图验收另建运行，不复写 09。

## 12. 运行身份、缓存和恢复

### 12.1 两阶段冻结的 RunFingerprint

创建运行时固定 `recognition_run_id、owner_id、document_hash、root_class_iri、ontology_snapshot_hash` 及实际执行配置；保存用户选择，不在后台重新分类或替换根类型。IR 和摘要生成后再固定完整 run_fingerprint，**完整 fingerprint 持久化之前不得开始图谱识别**。

完整 fingerprint 至少包含：document_hash、root_class_iri、analysis/structure/parser 版本、ontology/schema hash、metadata_snapshot hash、runner/协议/验证政策/解析投影/归并政策版本、模型及 tokenizer 身份、生成设置、scope/focus_path、检索政策、预算与重试设置。

`analysis_id` 标识解析 IR，`metadata_snapshot_id` 标识元数据，`recognition_run_id` 标识本次分析运行，三者不是同一个 ID；运行 manifest 明确绑定它们。模型名相同不等于同一模型身份，摘要内容相同也不能省略来源/版本。记录实际生效设置而非配置文件默认值。

### 12.2 缓存分层

| 缓存 | 最低失效依赖 |
|---|---|
| IR / RecordIndex | 原文、解析版本、结构 hash |
| MetadataSnapshot | 原文/结构、摘要模型/提示版本及实际内容 |
| LocalMenu | 本体/schema、主体类型及约束政策 |
| RetrievalPlan | 主体版本、完整菜单、记录/摘要身份、身份可信状态、检索政策 |
| ModelDecision | 完整目标、原文上下文、协议/schema、模型及生成设置 |
| Coreference/IdentityProof | 提及、角色来源、限定、竞争者和全部验证版本 |
| GraphProjection | run revision、候选/证明/审阅/依赖状态、投影政策 |

晚到竞争主体、身份状态变化、角色重判或审阅拒绝都可能使后续验证缓存失效。不能仅以候选文本和 key 字符串缓存。缓存复用还须通过权限域检查；同 hash 不授予跨用户读取原文/产物的权限。

两 Tab 共用一个已冻结 MetadataSnapshot；Tab 切换、刷新、SSE 重连不能隐式重算它。新版本内部可复用合法的解析/摘要缓存，但不接纳本次清理掉的旧协议缓存；实体/关系候选从新运行重新识别。

### 12.3 CheckpointEnvelope 与唯一所有权

checkpoint 包含 `checkpoint_schema_version、recognition_run_id、run_fingerprint、event_seq、frontier、recall_ledger、candidate_head_refs、proof_head_refs、resolution_events、dependency_index、retry_queue、scheduler_turns、progress`。它不持久化 `execution_token` 或 token hash；恢复时由当前租约重签 token，checkpoint 只描述已提交的耐久水位。数据库追加事件是权威来源，图、统计和 checkpoint 为可重建投影。

`recognition_run_id` 在同次分析的暂停/恢复间稳定；`execution_token` 在每次 claim/resume 时更新，只用于执行租约。租约行只持久化 token hash、generation、lease owner、lease_expires_at 和心跳，不保存可重放的明文 token；每次模型调用前检查所有权，结果返回后和每个持久批次再次检查 token。过期 worker 即使收到模型成功响应也不能写入。

可从现 AnnotationExecution 抽取通用所有权机制，但不复用其 job 外键记录，不创建假 ExtractionJob，不让旧 Job lease 与新 Run lease 同时管理一个运行。前端会话不是租约所有者，浏览器断开不使任务丢失。

文件 checkpoint 与数据库各有 durable 水位，按事件序列/内容 hash 对齐；先保存不可变产物、校验 hash，再提交引用及事件，孤立临时产物可回收。数据库事务失败不提交该批，恢复重放至已确认水位；不能宣称文件与数据库天然原子。尚在解析/摘要阶段的恢复只从已持久化阶段边界重启，不能套用图谱 fingerprint 尚未形成的 checkpoint。

**只支持新协议内部、fingerprint 一致的恢复。** 旧 generic/quality 在线断点、旧候选及缓存按第 14.3 节丢弃，不提供转换、旧 runner 恢复或降级执行。新协议自身遇到 schema/fingerprint 不匹配也明确拒绝恢复并指引新建运行；离线冻结实验仍只能在其隔离环境回放。

## 13. 文档分析工具、持久化与 API 契约

### 13.1 独立运行域与最小存储

新工具不是旧 ExtractionJob 的展示壳，不接旧 CandidateStore、PublicationMap 或审批中心。运行、存储、API、图投影统一使用 `recognition_run_id + candidate_id@revision`；首次写入 Product@2 就保存其真实版本，不重置成 revision 1，不建立第二套 public ID。

以下为已新增的表/模型，不能与已有 `document_analyses / DocumentAnalysisRecord` 混淆：

| 对象 | 必需字段/唯一性 | 用途 |
|---|---|---|
| `DocumentAnalysisRun` / `document_analysis_runs` | recognition_run_id、owner_id、request_key、file_name、source_uri/hash、root_class_iri、ontology_snapshot_ref、fingerprint、stage/status、control_action/version、deletion_state、event_head、artifact_manifest、expires_at；唯一(owner_id,request_key) | 独立运行、唯一所有权与保留期限；不依赖 job_id。租约/token hash 位于独立 execution 行。 |
| `DocumentRecognitionEvent` | recognition_run_id、sequence、event_key、event_type、payload_hash、payload；唯一(run,sequence)、唯一(run,event_key) | 追加式提议/判定/归并/失效/覆盖事件；重复事件幂等。 |
| `DocumentRunCandidate` 及 head 索引 | recognition_run_id、candidate_id、revision、kind、payload、proof_refs；唯一(run,candidate_id,revision) | 版本不可变，head 受乐观并发检查；原始提议、当前判定与专家审阅来源分开。 |
| `DocumentVerificationProof` | recognition_run_id、proof_id、proof_revision、target_id、payload_hash、payload；唯一(run,proof_id,proof_revision) | 目标/来源/端点/依赖的不可变证明，不跨运行借证据。 |
| 运行产物清单 | source、IR/record_index、ontology_snapshot、metadata_snapshot、graph_snapshot、checkpoint、trace 的 URI/hash/revision/durable_head | 文件或对象存储产物；浏览器不取得服务器真实文件路径。 |

mention、局部指称、检索计划首先作为类型化事件和 checkpoint 投影保存，不为每个中间字段建业务表。数据库结构直接创建新契约，不导入旧行，不将清空共享表作为创建新结构的前置条件。

后台创建任务与运行记录同事务登记可领取状态，worker 以租约从持久队列领取；进程重启只自动领取 queued 或租约过期的 running，仍须满足未请求暂停/取消、未删除、未过期。paused 和可恢复的 failed 必须经显式 resume 再进入 queued；取消/删除/到期运行不可恢复。不得仅使用随 API 请求进程退出而丢失的内存任务。

### 13.2 事件批次、图快照与确认边界

写入一个候选/归并批次时：

1. 检查 recognition_run_id、当前 token、预期 event_head/候选 head，拒绝并发陈旧结果。
2. 分配当前候选真实 revision；建立批内实体、属性、关系、proof 的完整引用闭包。
3. 检查 subject/object/path_root/scope/binding/dependency 均指向本运行允许的精确版本；发生归并/拆分时先追加失效与重新归属事件，不静默改旧引用。
4. 同一数据库事务追加候选/证明/事件并更新 head；失败不提交，重试按 batch_id/content_hash 幂等。
5. 从已持久事件水位生成不可变图快照，更新 manifest；前端只见完整的某一水位，不拼接新节点与旧边。

GraphSnapshot 至少包括 run_revision、event_head、metadata_snapshot_id、root_ref、实体/属性/关系及精确引用、projection_policy、覆盖和未决统计。增量中删除/失效也要明确表达，不能只向图上追加节点。刷新可用完整快照重建。

默认输出为“系统验证通过的分析结果”，并非专家确认或正式业务事实；没有专家审阅时 independent_review=unreviewed，不能由模型或完成状态填成 reviewed/confirmed。本方案保留领域层审阅拒绝及依赖失效契约，便于离线独立评审和后续明确需求；**首期不要求增加人工审核/编辑接口**，不导入旧审核状态。正式业务提交若另行建设，必须有独立授权、重验证及事务契约，不属于上传后的自动流程。

### 13.3 单一新 API

统一前缀 `/api/document-analysis/runs`，响应声明一个 `contract_version`；删除旧 `POST /api/document-analysis/word` 与 `analyzeWordDocument` 客户端，不保留双读/双写分支。

| 接口 | 请求与响应要点 | 副作用边界 |
|---|---|---|
| `POST /runs` | multipart：file、root_class_iri；请求幂等键 request_key。验证通过返回 202、recognition_run_id、stage/status、查询地址。 | 用户显式“开始分析”才调用；保存源文件、本体快照及运行，登记后台任务，不同步等待识别。 |
| `GET /runs/{recognition_run_id}` | 输入身份、阶段状态、RunProgress、产物 revision、保留期限、错误与可用操作。 | 只读，不创建任务、不复算结果。 |
| `GET /runs/{recognition_run_id}/metadata` | IR 展示结构、章节树、节点元数据、summary/source 状态及快照身份。 | 未就绪返回明确 pending 状态；不在 GET 中生成摘要。 |
| `GET /runs/{recognition_run_id}/graph` | 当前完整水位的 GraphSnapshot；支持本 Tab 内的 projection/filter，返回覆盖和未决说明。 | 未就绪/部分完成均有明确状态；查询不触发识别或审核。 |
| `GET /runs/{recognition_run_id}/source` | 授权原文预览/下载或 evidence_ref 定位所需片段，包含 analysis_id 与结构 hash。 | 来源必须属于本运行；不接受任意文件路径或未授权 URL。 |
| `GET /runs/{recognition_run_id}/events` | SSE：event_id、recognition_run_id、状态/进度、artifact_revision；支持按 Last-Event-ID 续读。 | 只订阅已存在事件；缺失旧游标时客户端 GET 重建，不重启任务。 |
| `POST /runs/{recognition_run_id}/pause`、`/resume` | 预期状态/版本；暂停在安全边界生效，恢复仅限 paused 或可恢复技术失败。 | 改运行控制状态；resume 重新签发 token，不重做已持久完成的逻辑任务。 |
| `POST /runs/{recognition_run_id}/cancel` | 显式取消，保留已有产物和真实未完成范围。 | 撤销租约；取消后不能恢复。 |
| `DELETE /runs/{recognition_run_id}` | 显式删除本次运行及其独占产物，先撤销执行权限；可异步返回 202 删除中。 | 清理关联记录/缓存，完成后不可查询/恢复，不影响其他运行共用产物。 |

表内 /runs 均相对于 /api/document-analysis。所有接口验证登录身份、owner/授权范围；现同步端点未显式实施该运行级鉴权，必须补齐，不能因分析工具独立就公开源文件。SSE、原文片段、取消/删除与普通 GET 使用相同授权。request_key 按 owner 隔离，同键同输入返回同一运行，同键不同文件/类型返回冲突；仅按文件 hash 不能吞掉用户明确请求的新运行。

服务端校验 Word 格式/大小、实际解析内容、类型 IRI 存在且符合根类型政策；选项来自当前本体，而非文档候选类型。无文件/类型或非法 IRI 返回 4xx，不调用模型；转换器/模型故障记录为阶段错误。返回类型 label 及完整 IRI，启动时冻结本体版本，禁止仅用可重名的中文 label 标识类型。

外层地址和分析工具导航保留 `/analysis?tab=document`；在 DocumentAnalysisPanel 内提供**恰好两个并列结果 Tab**。详情、过滤和覆盖面板均在关系图谱 Tab 内，不新增“候选”“审核”等同级结果 Tab。

```text
文档分析
[上传/更换 Word 文件]  [本体类型：搜索并选择 ▼]  [开始分析]
文件名 · 类型标签及 IRI · 运行状态 · 当前阶段 · 暂停/恢复/取消

│ 关系图谱：筛选/进度 │ 根关联实体与关系 │ 属性/证据详情与原文定位
└ 两种视图共享一个 recognition_run_id、原文和元数据快照
```

**公共提交区与运行身份：**

- 未选择文件或合法本体类型时禁用开始按钮；拖入文件不立即运行；开始后显示上传进度和运行阶段，防止重复点击创建重复任务。
- 本体选择器搜索类标签/IRI，选中项同时显示标签及完整 IRI；不自动把最近类型或文档推断结果当本次已确认输入。
- 已提交运行的文件、类型与本体快照不可编辑。更换选择进入新草稿，旧运行显示其原身份；再次点击开始才建立新运行。新建运行不隐式取消旧运行，允许通过其运行链接回看/取消。
- 基础路由不变，可用 `documentRun=<recognition_run_id>` 保存可刷新的运行定位；内层 Tab 可留在本地状态。打开/刷新链接只读恢复状态，不重新提交。
- 前端响应和 SSE 按 recognition_run_id 与单调水位过滤；快速切换运行时，旧请求迟到不能覆盖当前文档的元数据或图谱。

**分层元数据 Tab：**

复用现 ChapterTreePanel、WordViewer、MetadataPanel 及移动端侧栏能力，保留文档/章节/节点分层结构、各层摘要、标题路径、页码/来源范围、表格和解析信息、选中节点与原文联动。原有信息重新收纳，不删成一个摘要列表。摘要缺失/摘录回退/structure_only 要如实标识；解析已完成但摘要进行中时允许显示已有结构，不宣称最终快照就绪。

**关系图谱 Tab：**

1. 根节点显示用户给定的文档本体类型并标“用户指定”，不计为识别成功；默认显示通过当前 ProofGate 的根关联肯定图。
2. 实体节点展示类型、文档局部身份/可靠键状态及属性；关系显示标签、IRI、方向、判定状态和独立证明。支持选择实体后查看其直接属性与多跳路径，不仅展示节点计数。
3. Tab 内筛选提供“有效肯定图”“全部候选”“未归属/否定/条件/待定/拒绝”；拒绝记录不混入默认肯定边，但可追溯原始提议和后续续检。
4. 详情同时显示主体证据、对象/值证据、谓词桥接、适用条件、反证/竞争者、版本和拒绝/待定原因。仅两端高亮不能显示“组成已确认”。
5. 点击节点/属性/边的 evidence_ref，通过共享 SourceSelection 定位原文段落或表格逻辑行，并可联动到对应章节。SourceSelection 至少含 recognition_run_id、analysis_id、source_record/cell_id、span_refs；切换到分层元数据后保留定位。
6. 覆盖面板按主体/谓词显示 phase1/phase2、已检/未完成/未尝试、当前续检记录、拒绝原因和停止原因；图为空时仍能解释是在运行、未决还是范围内处理完成未得到有效关系。

### 13.5 进度、异常与数据保留

RunProgress 至少包含 tasks_attempted、model_calls、records_planned/examined/incomplete/unattempted、phase_counts、supported/unsupported/undetermined、pending_frontiers、stop_reason、contract_version。没有总数时显示阶段/计数，不制造百分比；计划记录数不是模型调用分母。前端不解析 checkpoint 私有字段。

| 场景 | 页面行为 |
|---|---|
| 元数据就绪、图谱仍运行 | 分层元数据立即可看；关系图谱显示当前水位、进度及部分结果，不阻塞整页。 |
| 摘要失败但结构可用 | 明示失败及结构回退；服务端按冻结降级政策选择 structure_only 或暂停，不由切换 Tab 重试摘要。 |
| 图谱失败/暂停/取消 | 元数据和已提交图快照保留；展示错误、未完成范围与合法操作，不清空原文。 |
| 尚未有有效边 | 显示“尚未识别到有效关系”及执行/覆盖状态；仅执行穷尽也不能断言全文客观无关系。 |
| SSE 断连/页面刷新 | 重连或只读轮询状态/快照；不重新上传、不额外调用模型。 |
| 来源已删除/到期 | 明确“分析结果已删除或过期”，不能显示还可回放的假引用；未知/无权访问按统一安全策略处理。 |

替换当前“上传 Word 文档即时分析”“仅用于本次临时解析，不执行实体/关系识别”“关闭页面结果即丢弃”及页面“独立于知识图谱的即时结构分析”等旧文案。新说明须表达：**上传并指定本体类型后生成分层元数据与关系图谱，结果为系统分析产物、不自动提交业务事实；关闭页面不取消运行，数据按保留策略清理。**

首期保留策略建议并作为配置验收：运行中不自动到期删除；终态运行从结束时间、paused 从暂停时间起默认保留 7 天，页面显示实际 expires_at；恢复须在有效期内。到期/用户删除前先使运行不可领取并撤销 token，再清理仅该运行拥有的源文件、产物、缓存和数据库引用；保留最小删除事件/墓碑用于防止迟到 worker 复写，不保留可恢复的业务结果。该保留策略只管理新运行，不延缓第 14.3 节对旧在线数据的一次性丢弃。

新运行创建时应明确告知保留期限及删除不可恢复边界；上传和转换实行大小、解压/资源上限与安全文件名策略，具体数值纳入配置和测试。原文、证明和日志受相同权限保护，不将全模型 prompt、业务片段或标识写入通用遥测。

## 14. 可直接拆成开发任务的重构计划

### 14.1 依赖顺序与任务包

`R0 固定证据/清理盘点 → R1 新协议与执行核心 → R2 本体/记录/元数据 → R3 证明与身份 → R4 调度/新运行存储 → R5 API/生命周期 → R6 双 Tab 页面 → R7 真实验收/清理/一次性切换`。

R2 与 R3 可在 R1 契约稳定后并行；R4 的存储与 R5/R6 的接口设计可提前按契约并行开发，但不因此提前接纳线上旧数据。分工/分提交仅是开发顺序，不是分流发布阶段；各工单不同时改本体、模型权重、评测参考和调度器。

| 任务包 | 主要改动点 | 交付物与退出条件 |
|---|---|---|
| R0：证据、回归与清理盘点 | evaluation、09 档案、现存接口/调用方/数据库引用 | 固定代码/模型/本体/摘要身份；正反例不改原银标；列出旧域 job/文件/依赖 manifest 和受保护资源；无需备份旧业务数据供恢复。 |
| R1：唯一新协议与公共执行核心 | 新 schemas、extraction_tasks、citation_protocol、ContextAssembler | 目标/Decision/Proof/事件/候选/RunProgress 契约；抽出 TaskExecutor 与原子引用；无新旧模式字段，在线不 import evaluation；其他业务共享能力回归通过。 |
| R2：本体/元数据/记录 | ontology_plan、records、metadata、retrieval | 动态直接菜单、增强只读本体快照、前置 MetadataSnapshot、物理 mention/逻辑记录分离；全部谓词计划守恒，路由阴性仍在 phase2。 |
| R3：证明、身份与依赖 | verification、resolution、dependencies、projection | 类型/局部共指/全局身份分开；谓词桥接、N/A、层级、两个来源号及错误 true 配对例通过；有效图与全部候选区分，不一律拒绝。 |
| R4：调度、运行存储与恢复 | scheduler、ledger、document_analysis/run_store、execution、新数据库结构 | 独立 DocumentAnalysisRun、真实版本闭包、唯一 lease/fencing、持久事件与快照；phase2 真实执行；归并/拆分/重验/幂等/断点恢复；不调用旧 CandidateStore。 |
| R5：上传及运行 API | api/document_analysis、新运行应用服务、后台任务、源文件存储 | 必选 root_class_iri、202 启动、状态/metadata/graph/source/SSE、pause/resume/cancel/delete、鉴权、保留策略；GET 零模型副作用，旧同步协议删除。 |
| R6：文档工具双 Tab | document-analysis-panel、analysis/page、api.ts、新关系图谱面板 | 显式提交及可刷新的 run 定位；现层级组件收入分层元数据；关系图谱含属性/证据/覆盖；单运行共享状态、迟到响应隔离、失败不清元数据、旧文案更新。 |
| R7：验收、清理与直接替换 | 评测薄适配、独立金标、清理工具、部署脚本、入口引用检查 | 同核心完成机制/API/前端/真实质量验收；维护窗口使旧写入失效、按清单丢弃旧域数据、启用唯一新实现；没有旧 runner/协议退路，提交清理计数和残留核验。 |

### 14.2 首个可交付纵向切片

第一张工单是 R0/R1，不是把实验 QualityGuidedRunner 直接挂到页面。首个端到端开发切片至少包含：

1. 上传合法 Word、选择本体类型并创建一个 DocumentAnalysisRun；缺类型不启动。
2. 真实 IR、记录索引和 MetadataSnapshot 保存；两个 Tab 读取同一运行，元数据先可见。
3. 单根、一个直接关系、两个章节记录；第一记录类型/关系被拒，第二记录明确支持，必须有真实执行事件见证。
4. 对象没有全局编号，但类型/局部指称可靠；关联后展开一项属性，候选与 proof 精确版本落库并呈现在关系图谱。
5. 模型回调可模拟，但原子引用、证据门禁、调度、仓储和 UI 真实接通；暂停恢复不重做已持久任务，Tab 切换不增加调用。
6. 只写新运行产物，不触达旧 CandidateStore、自动审核或中央事实提交。

随后增加 CMCReport 两跳配对正反例、跨章桥接、共享表格 mention、实例归并及全根菜单，再进行真实模型验收。开发测试数据与待清理旧在线数据隔离；分步开发不提供线上新旧选择。

### 14.3 旧实现退役与旧数据一次性丢弃

**代码范围：**

- 保留并复用原文 IR、结构解析、tokenizer/模型调度、安全预算、单位规范化、原文回放及正确的引用/版本机制。
- 替换本次 Word 域的预展开多跳类型菜单、各自拼装的验证上下文、单布尔身份、仅双端重叠的关系门禁、focus-only 分期、隐式 checkpoint/progress 协议。
- 删除旧同步文档工具端点/客户端、被替换的 Word 算法入口、候选旧格式适配和新旧选择开关。若共享类还服务于 Excel/声明式任务，只保留其所需职责，不保留 Word 旧路径作备用。
- 活动评测改用新核心；历史冻结 runtime/报告只作离线回放证据，不挂在线路由或恢复器，不恢复模板特定旧抽取器。

**清理对象以显式 manifest 为准，不按目录或 source_type 粗删。** manifest 至少列 job_id、源模式、目标表/主键、文件绝对路径及 hash、独占/共享归属、被引用对象、处理动作、清理后核验项。R0 用只读盘点生成，切换前重新核验；旧识别结果不做数据转换或导入。

| 数据类别 | 丢弃/处理规则 | 必须保护的边界 |
|---|---|---|
| 旧 Word 任务 | 明确本次被替换的普通文档识别任务 ID，停止接单并清理其运行/候选派生数据；任务根记录最后处理。 | `extraction_jobs` 还包含 class_mapping、声明式和 template_default 模式，`ast_templates.default_source_job_id` 有引用；不能仅按 Word 格式删除全部任务。 |
| 候选及运行关联 | 清单覆盖 `annotation_executions、evidence_job_states、evidence_candidates、evidence_candidate_revisions、evidence_reviews、extraction_candidates、slot_dismissals、evidence_coverage` 中目标任务的行；按实际外键顺序处理。 | 大部分 FK 没有级联删除；`extraction_candidates.merged_into_id` 可能跨任务。PDE/计算决策还可能有无 FK 的 job 引用，必须盘点并明确失效，不默认级联。 |
| 注解/断点/摘要 | 精确清理 `data/uploads/{job_id}.annotated.json`、`{job_id}.annotation_checkpoint.json`、`{job_id}.annotation_checkpoint.json.jsonl` 及 manifest 中其他独占缓存；现章节摘要在 annotated 的 section_tree 中。 | 不清空 data/uploads；旧 worker 和晚到摘要须先失去写入资格，防止删除后重建。 |
| 原文与共享解析 | `extraction_jobs.document_path` 指向的仅旧任务拥有的上传副本可丢弃；`document_analyses` 仅在全引用检查无保留引用时清理。 | 原文可能是模板默认来源；DocumentAnalysisRecord 没有 job_id，可被多个 job state 按 analysis_id 共用，同 document_hash 不是删除授权。 |
| 已提交旧事实依赖 | 对目标任务的 `evidence_commits、evidence_assertions、evidence_snapshots`、`conditional_assertion_bindings`、独占 commit world 文件和物化结果建立完整闭包；旧域独占数据删除，共享消费引用显式失效或从保留来源重建。 | 报告、report_runs/source_bundle、report_input_snapshots JSON 等引用不全由 FK 表示；不能删除候选后留下仍可被当有效事实消费的快照。跨域报告/模板不得随意删除；归属或失效影响不清时必须先补齐范围决定再执行切换。 |
| 模型排队/日志 | 取消清单内旧请求，撤销旧 annotation 和 evidence commit 两类 lease，记录清理事件；按准确 job/请求关联清理可丢弃的运行记录。 | local_model_requests 没有完整 FK，不能清空共享 local_model_pools；全局 audit_log 是 hash 链，不抽删其中记录，只追加清理审计。 |

用户/权限、系统配置、本体/类定义、模型/tokenizer、其他业务任务、全局实体索引和本体存储均不是本次旧识别缓存。尤其不能删除整个数据库、`data/`、共享 `settings.owl_store_path` 或全部 evidence world 目录。已有共享资源的旧域派生条目须按 provenance 定位，不能用整个存储文件作为替代目标。

09 等历史报告、冻结实验、评测输入和测试夹具保留为**离线研发证据**；不等于保留旧在线业务数据供展示、恢复或迁移。目标 CMCReport 的验收原件须在清理前确认位于独立保留清单，之后作为新上传建立新运行，不能依赖被删除的 upload/job 记录。

清理脚本已提供只读盘点、默认 dry-run 和受审批 envelope 约束的执行路径；执行只接受确定目标及依赖闭包，处理共享边界后再删独占子记录与根记录，并记录删除、保留/失效和失败项。没有明确来源的目标不删。数据库结构变更使用现有 schema 工具，不编写旧结果迁移器。实际删除后的旧业务结果不可恢复；该事实须在维护说明中明确。当前工作区只完成工具及合成回归，没有对真实旧域执行上述清理。

## 15. 验收矩阵、真实评测与发布门禁

### 15.1 自动化机制验收

以下编号是稳定验收语义，不要求测试文件与早期建议名称一一对应。当前已执行、部分覆盖和 pending 的逐项证据以 `specs/021-ontology-guided-doc-graph/validation.md` 为准；确定性测试通过不冒充真实数据库、浏览器或模型质量验收。

| 编号 | 用例及输入 | 必须断言的结果 |
|---|---|---|
| T01 | CMCReport 根 + 多跳本体 | 首次召回只见当前关系合法 range；尚未关联对象的二跳菜单不进入全文类型召回。 |
| T02 | 继承属性、多个 range 子类、未声明 IRI | 原约束及定义来源保留；并列约束不误作 union；合法子类批次不丢失；未知 IRI 拒绝。 |
| T03 | 摘要称“含 API”，原文没有组成 | 可提高检索顺序，不能产生桥接证据或事实。 |
| T04 | 路由零分/阴性；第一阶段全部拒绝 | 第二阶段的不同记录实际被调用；全部计划记录守恒，不只断言 queue 存在。 |
| T05 | 类型可靠但无唯一编号 | 保留文档局部实体；合法关系/属性可通过；不生成全局身份链接。 |
| T06 | API 表头+名称+试验“来源”编号 | API 类型可支持；把来源号当 API 全局身份的提议不可支持。 |
| T07 | 两行共享 API 合并 cell，来源号不同 | 只记录一处物理 mention 的重复观察；不按试验数创建两个已确认实体，不按同名强合并。 |
| T08 | 复现 call 50/51 的引用组合 | 名称+表头定位未决；加 row1 来源格定位 row1；两种定位结果都不代替身份/组成判断。 |
| T09 | 只有 Product 代码、API 名称和父 describes | 即使模型给 supported=true，缺少可接受的谓词证明时不得形成有效第二跳。另测模型谎报桥接类别的语义评审。 |
| T10 | 明确组成句、配方表、跨段明确指代 | 三种合法形式都能通过，不能只靠提高拒绝率通过 T09。 |
| T11 | Product 属性验证响应讨论 root 或其他对象 | 目标不匹配硬拒绝；ID 正确但语义错目标通过独立角色/谓词核验发现，不能把 ID 校验当全部保护。 |
| T12 | Product 口服片剂与 API 粉末配对例 | 成品外观可通过；不能把原料粉末属性未经证明挂到成品。 |
| T13 | CAS=N/A、布尔=否、字段未提及 | 分别为 placeholder、有效布尔、not_mentioned；不产生 N/A CAS，不吞掉 false。 |
| T14 | binding unsupported、同记录另有合法提议 | 当前提议后续阶段 not_checked；合法兄弟提议和下一个记录仍实际执行。 |
| T15 | 空召回、模型拒答、引用错误、token 超限、超时 | 分别记账；不伪造语义否定；拒答耗尽仍属 attempted_incomplete；换 revision/计划不重置重验额度，失败任务不无限阻塞其他记录。 |
| T16 | false/缺失/错误 true 身份状态 | false/缺失不泄露为可信 key；错误 true 仍须角色/唯一性门禁；router/shared/cache 同样测试。 |
| T17 | 名称+代码局部共指，跨制剂/批次同项目 | 前者可局部归并而全局身份未决；后者不因项目号相同跨层级合并。 |
| T18 | 合并、拆分、晚到竞争主体和第三个模糊节点 | 版本/证明/范围闭包同步；拆分不复制旧属性；新 owner 触发读取范围订阅；冲突不能借传递链被“洗成”一致。 |
| T19 | 根启动、注入领域层审阅拒绝事件、多条独立根路径、本体循环 | 给定根无入边可启动但普通实体不能冒用；依赖路径阻断；合法替代路径可重算；独立根分支继续；无无限递归。 |
| T20 | 新协议暂停恢复、进程重启、租约丢失、fingerprint 不匹配 | 识别 ID 稳定而 token 更换；从持久水位恢复，不重做已提交逻辑任务；失去租约者不写；暂停/取消/删除中的任务不被自动领取；不匹配拒绝恢复，不尝试旧 runner。 |
| T21 | 新运行首次落库 Product@2 及引用它的两跳关系/属性 | 存储/API/图共用真实 candidate_id@revision，subject/object/path_root/scope/dependency/binding 精确匹配，无归一化为 1 或第二套 public 映射。 |

### 15.2 独立评测数据

建立独立版本的标注包，至少标注 mention、类型、局部共指、标识角色/作用域、属性 owner/层级、关系方向/桥接、极性/条件以及允许的等价来源集合。将“原文支持/不支持/资料不足或专家有分歧”分开。

09 的 57 项 assistant_silver 和原评分器继续原样使用作历史对照。新标注包不能覆盖该文件；需在新实验前由业务专家复核并冻结。新的实体/关系标注可以接受多处等价原文证明，避免把 paragraph:34 与 paragraph:33 的来源差异误当语义差异；该评分器版本须独立报告，不能与旧指标拼成提升百分比。

新增至少三个场景族：明确 Product→API 组成的正例、同报告同名但没有组成桥接的反例、原料/制剂/批次及试验编号混合的难例。按文档及模板族划分开发/验证/保留测试；当前 CMCReport 及其近重复文档只用于开发回归，不能作为保留集。

### 15.3 运行设计

1. 用新冻结代码重建候选，不导入 08/09 的成功 Product、API 或关系；本体固定为已包含本次批准的 CMC 最终产物/中间体扩展的版本，并将其 hash 纳入运行指纹，运行中不得变更。
2. 先完成机制正反例，再对真实焦点路径运行；取得正例路径见证与通过关键反例是两个验收条件，不能互相替代。
3. 目标文档必须实际进入第二阶段并记录真实调用；若软暂停，只报告本段观察，不补记为全图完成。
4. 随后以 document_graph 模式覆盖 CMCReport 的其他根谓词；设备/计划等分支也各自统计检索、提议、拒绝和待办。
5. 结构-only 与结构+摘要使用同一新验证核心、同一模型/预算做消融，检验摘要增量。另设 GLiNER 消融；新核心与旧核心的比较限于冻结离线实验并单列，不能把验证器变化误报为摘要收益，也不为对照保留在线旧入口。
6. 模型输出存在波动时，对关键正反例安排至少三个独立新 run，记录温度/随机种子（若服务支持）及实际波动；不挑选最好一次。共享服务排队单列。

现有目标文档若仍没有足够原文组成证据，正确结果可以是“发现 Product/API，但该组成关系未决”。这证明安全拒绝的一部分，不证明正例召回成功；正例能力必须由另一个有真实组成证据的文档验证，不能为凑链路补写原文或改本体。

### 15.4 指标与硬门

| 验收面 | 必报内容 | 首期硬门 |
|---|---|---|
| 运行完整性 | 输入/模型/本体/摘要/政策 hash、finalized、原件/副本核验 | 不混版本；正式评分前无活动 marker；原始输入和输出未改。 |
| 工程机制及页面 | 引用回放、权限、版本、计划守恒、幂等、双 Tab、运行生命周期、本体保真、清理/依赖一致性 | T01—T31 对应确定性/执行契约无失败；无跨运行读写、陈旧引用、摘要事实泄漏或 Tab 重复模型调用；旧域清理且其他业务不受损。 |
| 语义正反例 | 类型、标识角色、组成桥接、owner/层级、拒绝理由与实际目标 | 预注册关键反例不得产生已接受错误事实；正例必须有独立来源支持的输出。任一关键失败阻断单次切换。 |
| 实体/归并 | mention/类型 P/R/F1，局部共指、错误合并/拆分、全局身份精度 | 不以少节点数作为归并优化；关键来源号反例不得升级 API 身份。 |

| 覆盖 | 每谓词计划/已尝试/未完成/未尝试、phase2、未展开前沿、范围外分支 | 声称范围内执行完成时台账与实际 trace 一致；技术失败和上限截断不能算完成。 |
| 成本 | 首个有效结果、模型/非模型/排队/摘要成本、tokens、调用数 | 仅记录；本轮不设必须快于 640.99 秒的门槛。 |

生产准确率/召回率的数值 SLO 在新金标规模及业务风险明确后，由业务与技术共同预注册；本文件不虚构已经得到统计支持的 95%/99% 指标。未批准 SLO 或无保留集时，标记质量验收未完成，继续开发环境评测，不进入线上试点，不执行旧数据清理和正式切换；不能宣称全量质量达标。模型重复试验、关键零容忍反例和测试通过也不能给出总体零错误保证。

### 15.5 单次切换与故障处理

部署只有一次切换，不做灰度、软件回滚或双轨运行：

1. 开发/验收环境以新结构和新输入完成 R1—R6、T01—T31 及独立真实质量验收；冻结构建、schema、模型/本体/政策版本，清理工具的范围/依赖检查通过。
2. 进入维护窗口，关闭旧文档分析/Word 识别入口，停止相关 annotation、晚到摘要、commit/outbox 写入；撤销目标租约，核验旧进程和模型响应无法再写。无需停止无关业务共享调度池。
3. 重新核验第 14.3 节 manifest，按依赖顺序丢弃旧域在线数据并清理/失效其派生引用，创建新结构；无旧候选、旧 checkpoint、旧审核状态导入。
4. 部署唯一新入口/核心/前端，确认旧路由和 runner 选择不可达；用新上传验证必选类型、元数据就绪、关系图谱增量及证据定位、刷新/暂停/恢复。
5. 核验清理数量与残留、保护对象不变、新运行只有一个租约与一套协议、两 Tab 不重复调用模型后，开放新入口。

若切换前关键验收失败，不执行破坏性清理、不切换。若清理或切换中途失败，保持维护状态，按 manifest 幂等完成清理或修复新版本；**不恢复旧数据、不重新启用旧实现**。单次切换不取消数据库事务一致性、断点安全和故障审计。

上线后若发现摘要被当事实、错误身份/组成被接受、版本错配、跨用户读写或未授权业务事实提交，停止新入口接单，暂停受影响新运行并保存其审计，修复唯一新实现、使错误图投影失效后重验/新建运行。该处保留的是新系统运行证据，不是旧业务数据；不得为了掩盖错误改写原始提议或把取消结果标为完成。

## 16. 重构完成的定义与交接清单

“完成重构”需同时满足：

- 新在线编排以当前主体的直接本体菜单工作，未预展开多跳类型到全文候选菜单；权威本体仅包含本次经批准的 CMC 最终产物/中间体有限扩展，不含 CMCReport→API 直连或共现规则。
- 所有范围内属性/关系都保留补充召回，拒绝后的真实后续执行和真实第二阶段有日志见证。
- 原子引用、局部无编号实体、表格共享 mention、身份角色、跨记录桥接和实体层级配对正反例通过；有效图不能靠全部拒绝验收。
- `/analysis?tab=document` 可上传文件、必选本体类型并显式启动；现章节树和节点元数据在“分层元数据”Tab，旁边是可查看实体/关系/属性/证据/覆盖的“关系图谱”Tab。
- 两 Tab 使用同一 recognition_run_id、IR 和 MetadataSnapshot；元数据先可用，图谱后台增量呈现；切换/刷新只读，迟到响应不串文档。
- 新运行统一 ID/revision、证明闭包、持久事件/快照、租约/恢复、鉴权/保留/删除和异常状态通过数据库/API/前端集成测试；不接旧候选发布流程、不自动审核或提交事实。
- 旧域在线数据按 manifest 已丢弃且依赖处理完毕，无旧协议读取、旧断点恢复、旧 runner 分流、灰度或回退入口；本体、共享业务和离线评测证据不被误删。
- 在线和评测共用新核心；真实质量按新标注包与保留集报告，明确未完成、未决和范围外内容，不把图连通、银标 TP 或全部拒绝当成功。

交付物包括：模块/API/schema 变更清单、R0—R7 工单及 T01—T31 结果、运行生命周期与保留配置、双 Tab 演示/集成测试、旧域清理 manifest/计数/残留及保护对象核验、单次切换记录、新运行 manifest/trace/coverage/图投影、独立来源审阅和质量报告。

当前文档同时保留实施设计与工程交接边界：代码、增量 migration 和确定性回归已在当前工作区形成，但它不是发布完成报告。真实数据库迁移、旧域清理、新一轮真实模型评测、部署和正式切换均未执行，最终状态只以 `specs/021-ontology-guided-doc-graph/validation.md` 的门禁记录为准。
