# `/reports` 页面加载缓慢分析

日期：2026-09-14。以下结论、原因和建议为优化前的只读调查记录；后续按用户明确要求完成的实现、上线及验证见文末。

## 结论

首要原因是报告列表接口携带完整报告正文和图谱：首屏只展示两条报告摘要，相关响应却有
**14,485,785 字节（14.49 MB）**，其中 `rules_summary` 占 **14,484,756 字节**，超过 99.99%。
列表不使用这些内容，但必须等待下载、JSON 解析及全部报告查询结束后才能展示。

另外存在逐任务查报告的 27 请求链，以及开发模式下不必要的编辑器依赖加载。当前调用链
不读取新迁移的 `document_analysis_current_state/results/requests`，没有发现本次图谱状态迁移
直接造成此页面变慢的证据。这里过大的图谱/正文来自既有报告的 `rules_summary` 快照。

## 实测

在当前运行中的服务上以管理员身份只读访问。浏览器使用允许的业务域名映射到本机网关，
未经过公网链路；以下不是用户设备或公网耗时保证。页面列表可用以“加载更多”按钮出现为近似判据。
未上传文件、生成报告、继续识别或修改数据。

| 测量项 | 结果 |
|---|---|
| `/reports` HTML 连续三次返回 | 217.7 / 93.5 / 67.2 ms |
| 新浏览器：标题可见 / 列表可用 | 703 / 2,256 ms |
| 同浏览器整页刷新：标题可见 / 列表可用 | 319 / 1,935 ms |
| 每次列表 API 请求 | 27 个 GET：1 个文档、1 个任务、25 个报告查询 |
| 文档列表 | 4 条，3,264 字节 |
| 任务列表 | 全部 764 条，301,799 字节；首屏仅使用前 25 个 |
| 前 25 个任务的报告查询 | 24 个空数组；另 1 个接口返回 2 条报告、14,485,785 字节 |
| 该大型响应的单独实测 | 首字节约 606 ms，本机读取约 11 ms；Python 解码约 350 ms，不能当作浏览器解析耗时 |
| 本机网关压缩核验 | 请求带 `Accept-Encoding: gzip, deflate`，响应无 `Content-Encoding`，长度仍为 14,485,785 |
| 新浏览器初始 JavaScript | 26 个资源，解压后 6,482,717 字节，实际传输约 1,250,437 字节 |
| 字体 | 30 个资源，解码后共 907,760 字节 |
| 浏览器长任务 | 初次 4 个、合计 440 ms；刷新 2 个、合计 136 ms；不是纯 JSON 解析时间 |

后端容器内使用六连接复现相同请求顺序，两次分别耗时 1,570.7 / 1,149.7 ms。
短时采样后端、前端、数据库 CPU 分别约 1.39%、0.15%、0.85%，未见资源饱和。
报告表共有 114 条未删除报告，分布于 13 个任务；这些是表规模，不等于当前用户可见报告总数。

## 原因及代码依据

### 1. 列表错误地返回了完整报告内容

[列表路由](../backend/app/api/extraction.py) 的 `list_reports` 查询完整 `GeneratedReport`，
返回 [GeneratedReportResponse](../backend/app/schemas/extraction.py)，其中包含 `rules_summary`。
[批记录报告生成](../backend/app/services/reporting/batch_demo.py) 将 `graph`、`template`、
`validation`、`body_ast` 等保存在该字段中，因此它已不只是小型“规则摘要”。

本次两份报告的每份 `body_ast` 均为 **7,042,162 字节**，每份 `graph` 为 **193,405 字节**。
两条报告其余元数据及 JSON 结构合计仅约 1 KB。
[前端聚合](../frontend/src/lib/api.ts) 最终只取 ID、任务 ID、类型、时间、文件大小和标题，
`rules_summary` 全部被丢弃。共享 `fetchAPI` 仍先 `await res.text()`，再同步 `JSON.parse()`。

这会同时产生数据库大字段读取/解码、服务端序列化、网络传输和浏览器解析开销。
若公网出口同样未压缩，14.49 MB 在 20 Mbps 下仅理论传输时间就约 5.8 秒；
该值是带宽换算，不是公网实测。压缩能降低传输量，但不会消除不必要的数据读取与解析。

### 2. 先取所有任务，再逐任务查报告，最后统一展示

当前顺序为：

`文档列表 → 全部任务列表 → Promise.all(前 25 个任务的报告列表) → 页面解除加载状态`

[页面](<../frontend/src/app/(dashboard)/reports/page.tsx>) 将其包成单个查询，文档即使已经返回也要等
全部报告请求。HTTP/1.1 下多个请求还会排队；本次部分空报告请求在发送前等待约 0.6 秒。

[历史方案](../specs/015-frontend-restyle-new-pages/research.md) 明确以“内部、几十个任务”为依据
接受此设计，目前已有 764 个任务。点击“加载更多”把 25 改为 50、100 等，重新取文档、全部任务
并重查前 N 个任务，并非只追加下一页。扫描完整列表的请求数会累计扩大。

### 3. 小工具函数把详情编辑器带入列表首页

[item-list.tsx](../frontend/src/components/reports/item-list.tsx) 从 `reading-pane` 引入
`formatBytes` 和 `saveBlob`；[reading-pane.tsx](../frontend/src/components/reports/reading-pane.tsx)
又静态引入 `WordViewer` 等详情组件，后者依赖 Tiptap / ProseMirror。

本次浏览器实际下载了相关编辑器 chunk；仅明确命名的 Tiptap core、Tiptap 扩展及
ProseMirror view 三块就约 **0.91 MB（解压后）**。列表页没有展示 Word 编辑器。
全页 6.48 MB JavaScript 还包含 React、Next 开发工具及其他共享依赖，不能全归于编辑器。

### 4. 开发模式和查询刷新放大重复成本

当前 [Compose override](../docker-compose.override.yml) 运行 `next dev`，已安装 Next.js 16.2.9。
本次页面 HTML 的 Next 处理部分约 4–12 ms，未捕获到数秒级首次编译，因此不能把本次延迟
主要归为路由编译；开发工具和较大脚本资源的额外成本则已实际观察到。

[Query Provider](../frontend/src/app/providers.tsx) 使用 30 秒 `staleTime`，没有关闭默认的失焦后
回到窗口、重新挂载等过期刷新。整页刷新会重建内存查询缓存，实测再次发出 27 个请求。
列表查询未传递取消信号，离开页面也不能保证正在进行的请求被取消。这些是放大因素，
不是 14.49 MB 响应产生的根因。

## 建议的最小改动顺序

1. **列表只查询和返回摘要字段**，SQL 查询也避免加载 `rules_summary`、正文和图谱；完整报告
   在进入详情时按 ID 获取。先核对既有调用者契约，不删除历史快照或详情能力。
2. **报告在后端直接分页查询**，保留当前用户可见性和完成/删除过滤，避免先取所有任务再逐个查询。
   文档与报告摘要可以并行加载，先返回的内容先展示；“加载更多”只请求下一页。
3. 将 `formatBytes`、`saveBlob` 移至轻量工具文件，使列表不依赖详情编辑器。
4. 正式使用时用生产构建验证资源体积；按需要调整列表缓存刷新策略及接入取消信号。

当前证据不支持先增加 Redis、异步列表任务、历史回放或新的图谱状态机制。先减少列表的
字段和请求量即可直接处理已定位的开销。调查阶段未实施上述建议；后续收益以文末实测为准。

技术语义已通过 Context7 核对：[Next.js 延迟加载](https://nextjs.org/docs/app/guides/lazy-loading)、
[TanStack Query 默认行为](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)、
[查询取消](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation)。


## 已实施的列表优化与验收（2026-09-14）

用户明确要求：列表仅查询摘要、后端直接分页报告、移除列表对详情编辑器的依赖。

- [后端摘要查询](../backend/app/services/reporting/report_listing.py) 只选择报告 ID、任务 ID、
  来源文件名、类型、大小和时间，通过 `count` 与 `limit/offset` 两次 SQL 完成每页查询。
  不读取正文、图谱或 `rules_summary`；复用原报告列表的可见性、完成状态和删除过滤。
  [路由](../backend/app/api/reports.py) 新增 `GET /api/reports?page=1&page_size=25`，每页上限 100。
- [列表页面](<../frontend/src/app/(dashboard)/reports/page.tsx>) 并行加载文档和报告摘要，
  先返回的内容先展示；追加下一页，失败保留已加载内容并允许重试。缓存按用户名和角色区分。
  上传只刷新文档；删除报告后刷新已加载报告页，使 offset 和总数重新对齐。
- [轻量文件工具](../frontend/src/lib/file-utils.ts) 承接大小格式化与下载，列表不再导入
  `reading-pane`。详情链接关闭自动预取；原详情完整内容、下载和缺少查询参数的深链接仍可用。
- 文档仍沿用原接口及最多 100 条的现有读取范围，分类数量基于当前已加载条目。
  本次不新增存储、索引、依赖、图谱快照或数据库迁移。

### 真实业务服务测量

后端已重启加载新接口，`/api/health` 正常；业务库 revision 仍为
`0040_current_recognition_state`。重启前已核对无活动图谱执行或模型请求；遗留 `running`
抽取/报告记录的时间均早于本次服务启动，未清理或修改这些历史状态。

同一业务账号、业务库和本机网关，仍为 `next dev`。优化后新浏览器与整页刷新各测一次，
列表可用仍以“加载更多”按钮出现为近似判据，并检查摘要页计数已显示。

开发模式本次还观察到 2 个 `net::ERR_ABORTED` 的初始 API 请求，随后两路查询正常完成；
因此网络记录共 4 次尝试，不能把它们都表述为只有 2 次请求。合成浏览器检查同样观察到
Strict Mode 对消费取消信号的查询进行取消和重挂载。没有为规避开发模式重复请求增加延迟层。

首屏报告响应内容范围已由“前 25 个任务中的报告”改为“最新 25 份可见报告”。优化后报告
数量更多且覆盖旧任务，大小比较表示实际列表流量变化，不能理解为相同两份报告的压缩率。
时间是同机开发环境的短时样本，未进行生产构建、公网或多用户负载评测。首次页面仍有
React/Next 开发脚本与字体开销，不能据此承诺所有设备固定达到上述耗时。
