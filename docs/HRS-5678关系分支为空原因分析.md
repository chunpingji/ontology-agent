## 2. 为什么一个实体任务超时会导致所有关系为空

当前调度先遍历全文的实体召回任务，结束之后才建立主体队列并开始关系/属性抽取。发生模型超时等 `MODEL_FAILURES` 时，任务执行函数直接返回停止信号，外层将 `stopped` 设为 true，关系/属性队列因此不会启动。

代码证据：

- [实体阶段先遍历全文](../backend/app/services/extraction/extraction_tasks.py:1175)。
- [模型错误返回停止信号](../backend/app/services/extraction/extraction_tasks.py:1125)。
- [只有未停止时才建立关系/属性队列](../backend/app/services/extraction/extraction_tasks.py:1303)。

源作业已经配置了 `hasProductionPlan`、`describes`、`usesEquipment` 等优先路径，但这些优先级在关系/属性调度阶段才生效，无法绕过前面的全文实体阶段。

使用当前程序做了隔离调度验证：采用真实缓存中已经通过的计划实体，注入记录中的引用不匹配和超时错误，不调用模型、不写数据库。结果如下：

| 场景 | 调度结果 |
| --- | --- |
| 首个实体任务部分成功，第二个实体任务超时 | 执行 2 个实体任务，0 个关系任务 |
| 对照组：第二个实体任务正常结束 | 同样的实体输入可以继续调度关系任务 |
| 普通断点续跑 | 恢复失败记录并跳过这两个实体任务，继续后面的任务；不会自动重新请求这两个失败任务 |

这是调度行为验证，不能视为新的真实模型抽取验收。尤其“从断点继续”与“重试失败任务”是两个不同操作：普通续跑默认 `retry_failed=False`，已经丢失的实体提案不会因续跑自动恢复。见[失败任务恢复分支](../backend/app/services/extraction/extraction_tasks.py:1065)。

## 3. 上游引用错误和超时策略

`source_excerpt_mismatch` 表示提案引用不能与其指定的证据原文逐字对应；`ambiguous_source_quote` 表示允许区域内有多个相同引用，现有上下文不足以选出唯一位置。最新版本虽然支持 `context` 和完整断言消歧，本次模型输出仍产生了上述错误。

真实工艺段落 `paragraph:84:0` 中，`5678-3`、`5678-2`、`5678-1` 和 `HRS-5678` 等在同一段反复出现，确实存在短实体名称需要上下文消歧的场景。但当前运行没有保存被丢弃的原始提案，**不能把这段中的具体名称逐一对应到记录中的 7 次错误**，也不能判定每一个被拒绝提案都是合法漏项。

模型适配器使用每次 60 秒限时、`max_attempts=1`，没有在本次调用内进行第二次尝试。见[模型调用参数](../backend/app/services/extraction/local_semantic_model.py:114)。这次终止原因是类型校验的 `model_timeout`；任务数上限没有用尽，也没有 `task_budget_or_pause` 诊断。

检查时本地模型 `/health` 正常，两个推理槽位均空闲。缺少失败时的原始响应、实际耗时及排队记录，现有证据不足以判断超时由推理耗时、排队还是网络触发。每批同时携带 136 个类型和 31 个证据单元，是需要实测优化的任务粒度，不能直接认定它已经超过上下文上限。

## 4. 为什么界面显示了 69 个实体

当前证据读取按作业返回所有持久化候选，保留历史记录及人工审核。69 条实体的来源为：

| 来源 | 数量 |
| --- | --- |
| 旧版 `generic-semantic-v6` | 66 |
| `document-metadata-v1` 文档根记录 | 2 |
| 当前 `generic-semantic-v8` 业务实体 | 1 |

因此 69 是历次保存结果的总量，不是本轮新识别出的 69 个有效业务对象。本轮运行记录实际只有 1 条文档根和 1 条计划实体。

这里还有两处展示上的不足：

- [版本提示](../backend/app/api/evidence.py:213)只依据最新运行判断 `outdated`，而[候选列表](../backend/app/services/extraction/candidate_store.py:76)返回整个作业的历史记录，所以仍有 66 条旧版候选时也可能不显示旧版提示。
- [后台状态处理](../backend/app/api/extraction.py:782)把所有带断点的未完成结果统一标成 `paused`，没有区分主动暂停、模型超时和预算停止。当前页面“已暂停”没有充分说明实际中断原因。

自动审核只决定已有识别记录的审核状态，不会生成缺失的关系。此处需要补全抽取流程和分阶段状态。

## 6. 建议的修复顺序

1. **调整任务调度和故障恢复**：已有文档根及合格对象后即可调度关系/属性；对超时做有总预算的重试或拆批，避免某个实体批次让所有独立关系都停在未开始。区分整机模型不可用与单个请求失败。
2. **补足引用诊断与修复请求**：记录受控的任务、阶段、提案引用、证据 ID、耗时和错误；短引用歧义时要求完整上下文再验证，保留逐字校验及防错绑限制。
3. **区分本轮与历史结果**：显示实体、关系、属性各阶段的未开始、进行中、失败、完成状态；明确失败可重试，单独展示历史候选来源。空分支需要区分“尚未执行”和“已执行但没有结果”。
4. **以真实分支验收**：先验证 `hasProductionPlan → 批量/用途`、`describes → 产品属性`、`usesEquipment → 设备属性`，再跑完完整文档，并为每个关系分支保存执行结论及证据。

本次仅分析：读取数据库、缓存与模型健康状态，并做隔离调度验证；没有重新识别文档，也没有修改、拒绝或发布真实候选。

## 7. 超时与自动重试配置更新

按用户后续要求，配置调整如下：

| 配置 | 当前值 | 含义 |
| --- | --- | --- |
| `EVIDENCE_TIMEOUT_S` / `evidence_timeout_s` | 600 秒 | 每次模型请求的超时设置，包括重试请求 |
| `EVIDENCE_TIMEOUT_RETRIES` / `evidence_timeout_retries` | 3 | 首次请求超时后最多再请求 3 次，共最多 4 次 |
| `TaskBudget.timeout_s` / `timeout_retries` 默认值 | 600 / 3 | 任务预算与运行配置一致 |

关系图谱抽取适配器针对 `model_timeout` 重发相同结构化请求，每次使用完整的 600 秒设置。成功后立即返回，第四次仍超时则抛出原超时错误，由抽取器保存断点。其他错误按其原有类型返回。SDK 的 `max_retries=0` 和单次结构化调用的 `max_attempts=1` 保持单次请求语义，自动重试由抽取适配器统一负责。

重试日志记录当前重试序号、重试上限和超时设置；运行检查点中的 `model_calls` 仍统计抽取器调用适配器的次数，额外 HTTP 尝试通过重试日志核对。

已在 Compose 中显式配置两个环境变量并重新创建后端服务，入口健康检查通过。验证共 **91 项测试通过**，包括使用真实 SDK 与模拟 HTTP 传输验证：连续三次超时后第四次成功、第四次超时停止、提前成功停止重试、每次均采用 600 秒、错误种类保持、非超时错误不重试，以及任务预算显式关闭重试。Ruff 与差异空白检查通过。

该变更更新后续请求的执行策略；源文档的暂停状态和历史识别记录保留。新的任务预算参与运行标识计算，使用旧预算的断点会按现有兼容性规则开始新预算的运行。
