# CMCReport 根关系驱动图谱识别实测报告

结论：局部类型菜单确实缩小，但当前原型在本轮没有证明整体图谱提速或最终准确性提升。与“仅结构摘要提示”对照相比，新方案最终参考得分相同，观察到的片段耗时增加约 22.0%，模型调用由 8 次增至 16 次。主要阻力是关系检索范围仍大、验证上下文重复，以及跨单元引用失败阻断递归。

实验协议为 `cmc-root-guided-pilot-v1`，三组已于 2026-09-08 00:43:52 UTC 全部落盘。本报告不替换或修订上一轮冻结结果。三组均为相同软预算下的未完成片段，以下耗时不是全文完整运行时间。

## 1. 测什么

输入仍是 `upload-23c872fb-3ab1-41de-a705-dd4b162dfa09`，显式类型 CMCReport。新方案以文档根实例为起点，按当前类型的直接属性和关系规划章节范围；每条关系只用其直接 range 及合法子类作为实体发现菜单，验证目标及关系绑定后，再展开该目标实例的属性和下一跳关系。

本轮不添加 GLiNER，用以单独观察调度改变的效果。新增代码仅位于 `backend/app/evaluation/`，未接入生产抽取入口，不提交生产候选或事实。模型调用仍产生共享调度与用量记录。使用已核对的 Docker Compose 一次性容器选项，不重启生产服务、依赖或模型服务。

| 组别 | 处理方式 |
|---|---|
| baseline | 当前通用生产抽取器，广类型菜单 |
| root_guided_summary | 当前主体直接谓词选章、小菜单发现、验证后递归 |
| structure_summary | 上轮结构摘要提示变体，保留完整候选菜单，仅排序和提示 |

所有组使用相同的新冻结代码、本体、模型配置和源文件；按表中顺序串行执行。第三组用于区分“使用摘要提示”与“改变任务生成方式”，不是另一个新算法。

## 3. 实现边界

CMCReport 冻结 schema 为 0 个数据属性、12 条直接关系。静态预检中，各关系的发现菜单为 1～25 类；其中 describes 的直接 range 与子类为 12 类，usesEquipment 为 25 类。与原基线的 136 类菜单相比，缩小的是单次实体发现的类型集合；关系槽位数与类型数不是同一个统计量。

类型验证继续使用生产竞争类型及角色扩展，不能声称所有请求都只有 1～25 类。本轮直接 range 的合法子类仍在当前关系内展开，尚非候选实例驱动的多态逐级细分。

选章为确定性本体词法匹配，使用标题及分层摘要。每个谓词最多选择三个章节，且不超出既有主体证据 scope。未选章节明确保留为 deferred；本原型尚未实现自动逐级扩大范围的补查，也没有回退到全文全类型扫描。没有验证通过的父边便不展开后代，漏掉父边会截断该分支，需结合未完成范围解释召回率。

当前关系的候选发现完成后立即绑定，已验证子实例工作与剩余根关系交错推进。后续发现竞争主体时保守撤销受影响的属性、关系及其依赖后代，并记录失效原因；本轮不自动重验证这些撤销结果。达到关系深度上限仍处理边界实体属性，但停止继续扩边。

摘要只用于路由。原文引用回放、类型验证、主体—谓词—对象/值绑定与共享值归属检查保持有效。此前跨表格单元拼接引用的问题不通过放松证据规则来掩盖。

## 4. 实测结果

|---|---:|---:|---:|---:|---:|
| baseline | 747.91 | 5 | 14 | 164,075 | 14 / 0 / 1 |
| root_guided_summary | 932.39 | 5 | 16 | 207,656 | 10 / 0 / 0 |
| structure_summary | 764.24 | 5 | 8 | 141,705 | 9 / 0 / 0 |

三组都因软截止停止，未达到 24 次任务尝试上限，`completion=incomplete`。基线及结构摘要组各另有一个中断任务事件，因此 task_event_count 为 6；新调度器通过 coverage 记录中断，事件数为 5。不能把任务事件数误当成尝试数，也不能认为相同尝试数代表相同原文位置或相同验证工作量。

新方案相对同轮基线的观察耗时增加 24.7%，相对结构摘要对照增加 22.0%；总输入相对结构摘要对照增加 46.5%。这些是单次预算片段的描述性差异，不能外推为整篇变慢比例或因果效应。结构摘要对照期间另观察到两个模型槽位同时忙，部分请求较慢；没有停止其他作业或从统计中剔除这些请求。

新方案和结构摘要对照的冷元数据核算分别为 1,883.65 秒、1,715.49 秒，均包含一次历史摘要成本 951.26 秒；并非本轮冷上传端到端实测。

### 4.3 基线参考未命中的解释

本轮基线的 hasProductionPlan 绑定验证确实引用了正文“本次备样……计划在2026年6月……”的信息，并保存在 `bindings[0].anchors`。但对象实体“研发项目临床备样生产信息”和关系本身的 `provenance` 仅保存标题来源，而冻结评分器按 provenance 对齐参考中的正文计划记录，并不把 bindings 锚点合并为实体身份依据。因此该关系是 unscored，不是 FP，也不能解读为完全没有正文支持。

基线还将四种设备归为泛类 Equipment、将 HRS-1597 归为 API；冻结参考要求所标范围中的具体设备类和 DrugProduct。现行有限范围评测把这些预测记为未评分，而非自动判错。此保守口径贯穿三组，未根据新方案预测修改参考或评分器。

## 5. 为什么小菜单没有转化成整体收益

### 5.1 召回提示变短，但验证提示没有同比缩小

| 模式 | 实体召回菜单类数 | 实体召回平均输入 token | 类型复核平均输入 token | 类型复核最大类数 |
|---|---:|---:|---:|---:|
| baseline | 136 | 14,822.33 | 12,742.00 | 74 |
| root_guided_summary | 25 | 10,955.25 | 13,151.60 | 62 |
| structure_summary | 136 | 21,262.00 | 13,630.00 | 28 |

新方案实际执行的都是 usesEquipment 的 25 类发现菜单，没有装入 136 类可达闭包。其实体召回平均输入比基线减少约 26.1%，验证平均输入却没有相应下降。类型复核的菜单依次为 28、28、62、24、17 类；定义角色、候选和来源上下文仍产生大请求。各组访问的窗口与候选不同，上表不是等输入单请求配对测试。

### 5.2 三个章节仍是 117 个原文单元

usesEquipment 选中 `section:79 / section:81 / section:84`，合计 117/400 个非空原文单元，分为四个实体发现任务。到 506.12 秒这四个任务均已尝试完，但其中两个有失败，不能称已成功完整覆盖。

本轮实际仅尝试了这一个根关系：4 个实体任务加 1 个关系任务。其余 11 条根关系没有执行任务；每谓词另有 28 个章节节点 deferred。`deferred_sections=336` 是 12 个谓词各 28 个延后节点的累计记录数，不是 336 个独立章节。

`subjects_expanded=1`，只有根主体。没有属性任务，也没有 depth>0 的任务；真实文档中的 DrugProduct 属性及二跳分支尚未跑通。递归门槛、晚发现竞争主体后的撤销等机制通过了单元测试，但本轮没有触发成功递归或撤销事件，不能把测试覆盖写成实测成功。

### 5.3 失败绑定占用约 361 秒

| 新方案阶段 | 调用数 | 模型墙钟秒 | 输入 token |
|---|---:|---:|---:|
| 实体召回 | 4 | 227.93 | 43,821 |
| 实体类型复核 | 5 | 270.99 | 65,758 |
| 关系召回 | 1 | 63.92 | 13,612 |
| 关系绑定复核 | 6 | 361.00 | 84,465 |

关系召回提出 6 条 usesEquipment 断言，六次绑定都因 `source_excerpt_mismatch` 失败。典型问题是向“200L反应釜”的单元 context 填入相邻编号段、拼成整表行，或向仅含“设备清洗方法”的标题单元填入跨标题长句。模型返回 supported=true 并不使这些引用变成合法原文。证据详见 [trace.jsonl](evaluations/cmc-root-guided-20260908-03/root_guided_summary-01/trace.jsonl) 的第 11–16 条记录。

结构摘要对照的两次关系召回共提出 8 条断言，其中 5 次引用错配、3 次超出事实允许范围，在召回引用检查即被拒绝，没有进入绑定调用。新方案多走了六次绑定验证，但未产生有效边；范围收窄本身没有解决跨表格单元引用问题。

新方案模型调用合计 923.84 秒，占片段总耗时约 99.1%；解析约 3.31 秒、变体初始化规划约 0.08 秒。当前主要问题仍不在章节树解析。

## 6. 下一轮应优先验证什么

保留根实例与直接关系调度方向，但当前原型不宜直接作为已验证的生产提速方案。建议下一轮分别验证以下改动，并使用新的冻结版本和同一独立参考：

1. 按表格行、业务记录和原文 token 预算继续缩小谓词范围，而不只限制章节数；保留未检索账本和按当前谓词补查，不回到全文全类型扫描。
2. 缩小独立类型及绑定验证的重复上下文，保留必要竞争实例、定义及证据；避免每条边重复发送整套范围和候选元数据。
3. 采用多源单元的明确引用列表/表格行证据包，防止把多个单元拼进单一 context；继续严格回放，不通过放宽证据规则提高通过率。
4. 在已验证身份一致时归并候选及复用发现结果，再独立验证不同关系，减少重复图谱节点和调用。
5. 为每次模型调用和验证批次设置可恢复的运行预算，控制单任务越过软截止的长尾；协议变更需新一轮对照，不能追改本轮时限。

若再引入 GLiNER，应单列消融：它可能降低实体召回成本，但不能自动修复目前阻断关系和递归的引用问题。
