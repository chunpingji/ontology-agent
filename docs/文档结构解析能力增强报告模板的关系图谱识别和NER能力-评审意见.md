# 文档结构解析能力增强报告模板的关系图谱识别和 NER 能力——评审意见

> 评审日期：2026-09-05

> 评审对象：[文档结构解析能力增强报告模板的关系图谱识别和NER能力.md](./文档结构解析能力增强报告模板的关系图谱识别和NER能力.md)

## 1. 总体结论

现有设计以 `DocStructure` 为基础，统一章节树、证据坐标、模板来源和抽取上下文，这一方向合理。共享解析链路、三阶段 NER、模板锚点丢失、多跳递归缺少父实例范围等设计依据，在仓库中均有对应实现或可核实的问题。

但“结构一致”“证据可定位”“属性归属正确”“关系成立”“审核后持久化”是不同层次的保证。当前报告主要补强前两项，对后三项仍缺少可执行契约；完整父链能够提升抽取质量，也尚无充分实验依据。

用户随后明确补充目标：**彻底消除正则、硬编码 finder**。按这一目标重新评审，即使当前方案全部实施，旧规则仍会保留在生产链路中。原方案设计的是统一上下文和范围约束下的兼容增强，没有设计规则抽取机制的完整替代与退役。

建议保留 IR、Anchor、ContextEnvelope、Scope 和 Candidate 作为基础，补齐通用语义抽取、主体绑定、实例级覆盖、审核入图和旧规则退役设计后复审。若“消除正则”覆盖整个自有处理链路，结构解析和分词模块也必须纳入改造，不能默认豁免。

## 2. 核查方法与证据边界

本次评审使用以下证据：

1. 阅读评审对象、相关设计记录和当前仓库实现。
2. 检查 NER、关系抽取、Profile、模板、coverage、候选审核和本体投影的调用关系。
3. 运行三组现有测试，并用三个临时探针核实关键行为。
4. 通过 Context7 查询 GLiNER 官方文档，核查普通实体抽取接口与专用关系抽取模型的能力边界。

没有进行真实模型准确率、召回率、层次上下文消融或生产性能评测。现有测试主要使用桩模型，不能作为新方案提高真实抽取质量的证明。临时探针用于验证接口和控制流，不代表真实 GLiNER 在对应样本上的预测结果。

## 3. 第一轮评审：架构与契约问题

严重程度约定：**P1** 为进入对应阶段实施前必须补齐的设计问题；**P2** 为需要补充验证依据或实验方案的问题。以下意见针对待实施设计，不将所有设计缺口等同于已经发生的生产故障。

### R01 · P1：数值属性的抽取路径不完整

**涉及原报告：** §9.3、§9.4、§9.5、§16.3、场景 A。

现有 `ontology_typer._is_non_entity_span()` 会过滤 `250mg`、`250 mg` 和纯数字；`document_annotator._type_and_filter_spans()` 在归类前调用该过滤器。Stage 3 又以已归类实体为入口。因此，保留 Stage 1、仅在 Stage 2 增加父标题，不能直接实现“相同数值在不同章节下归为规格、剂量或 PDE”的验收目标。

例如标题出现药品 A，下级段落只有“规格：250 mg”，目标段落可能没有可保留的实体 mention。设计必须解释属性任务如何启动，以及如何取得已经确认的主体。

**建议修订：**

- 区分实体类别识别和属性值识别，不将规格、剂量等属性 IRI 混同为实体类 IRI。
- 增加由主体候选、属性定义和证据范围驱动的通用属性抽取任务；目标正文没有实体 mention 时也能够执行。
- 明确父实体候选的产生时机、确认条件及传递顺序，避免 NER 等待关系端点、关系端点又等待 NER 的未定义依赖。
- 对数值、单位、范围和比较符号定义属性候选表示及验证规则。

**复审要求：** 用“主体在标题、数值在正文”和“同值不同属性”样本验证完整调用链；说明旧数值过滤策略如何迁移，并避免引入新的专用正则补丁。

### R02 · P1：证据位置和作用域不足以证明绑定正确

**涉及原报告：** §7.7、§9.5、§10.1、§10.3、§10.4、§10.6。

`allowed_fact_regions` 可以防止取值来自禁止区域，但同一合法区域内仍可能有多个主体和属性值。例如“药品 A 规格 250mg，药品 B 规格 500mg”，两组值同属一个段落，合法 anchor 和相同 scope 都不能决定它们的归属。

现有 `_extract_property_triples()` 使用实体附近的文本和该类的属性标签抽取值。短段中的两个同类实体可能收到完全相同的模型输入；接口没有显式标识本次主体，也没有独立的绑定证据输出。临时探针已核实这一调用行为。

拟议 `RelationshipCandidate` 保存两端 anchor 和 `binding_scope`，但没有明确记录支持谓词与绑定成立的原文或结构证据。两个实体共现、类型合法，不等于关系成立。

**建议修订：**

- 定义显式主体条件及通用属性、关系绑定步骤。
- 为候选增加绑定证据、绑定方式和拒绝原因。表格可以引用记录身份和行列对应关系；叙述文本需要引用支持谓词的证据。
- 明确 scope 的构建、继承和扩展条件，不能仅列出“同一行、同一章节”等搜索优先级。
- 覆盖同段多主体、否定句、条件句、多值属性和无法唯一归属的情况。

**复审要求：** 同段不同主体的属性不得互绑；实体共现但无关系、明确否定关系的样本不得因 anchor 和 domain/range 合法而通过验证。

### R03 · P1：Coverage 的现有语义不足以驱动多实体补抽

**涉及原报告：** §11.1、§11.2、场景 B、场景 D。

现有 `coverage_validator._relationship_present()` 主要按目标类型判断是否存在对象，没有校验目标谓词和主体实例；`_prop_present()` 也只需要某个该类型对象有非空属性。临时探针确认：目标声明 `usesEquipment`，输入只有另一谓词下的 `Equipment`，仍得到 `filled`。

拟议 `TemplateExtractionTarget` 只有文档类、谓词、目标类和属性列表，没有主体实例或关系路径。药品 A 的数据因此可能掩盖药品 B 的缺口，使定向补抽根本不触发。

**建议修订：**

- 模板层可继续声明类型级覆盖；运行时必须展开成包含主体实例、完整谓词或路径、目标对象范围的覆盖任务。
- 明确“至少一个对象满足”和“每个相关对象都满足”的量词及基数语义。
- 按正确谓词、主体、目标实例和属性归属计算缺口，并区分不存在、不适用、未抽到、冲突待审核。
- Coverage 和报告事实投影使用一致的实例筛选契约。

**复审要求：** 错误谓词不能满足覆盖；药品 A 已完整而药品 B 缺失时，缺口必须保留并定向指向 B。

### R04 · P1：ContextEnvelope 缓存身份不完整

**涉及原报告：** §7.1、§7.5、§12.4。

原报告建议缓存键为 `structure_hash + target_evidence_id + task + context_policy_version`。但 envelope 还依赖父实体、证据范围、文档分类、token 预算等输入。同一证据分别用于父实体 A、B 的关系任务时，上述键相同，可能复用错误上下文。

**建议修订：** 将父候选身份及版本、scope 摘要、有效分类、预算和 tokenizer 身份等影响输出的依赖纳入缓存身份。逐层列明 IR、envelope、模型结果、checkpoint 的缓存依赖和失效规则。最终内容的 `context_hash` 不能替代构建前正确的查找键，外层版本清单也不能修复内层键冲突。

**复审要求：** 同证据不同父实体、不同 scope 或预算不得错误命中缓存；完全相同输入应稳定命中。

### R05 · P1：审核后入图缺少存储和提交契约

**涉及原报告：** §5、§10.1、§10.7、§12、§15。

架构图承诺输出审核后的实体和关系事实，但数据库改造清单只列出模板分析快照，没有节点/边候选、结构化来源和审核状态的落库设计。

当前 `_persist_ner_triples()` 将属性压成字典，仅保存字符串来源；`_commit_candidate()` 将属性字典传给 `OntologyEngine.project_entities()`。后者按 `kind` 投影类、关系类型和数据属性等元数据，不是通用实例及对象关系的提交入口。现有调用不能直接承接拟议的关系候选提交。

**建议修订：**

- 定义节点、属性、关系候选的持久化结构，保留多值、冲突、逐值来源和稳定候选 ID。
- 区分自动校验通过、人工确认和事实提交成功，明确状态转换。
- 定义候选 ID 到实例 IRI 的映射、实体归一化后边端点的更新及提交顺序。
- 定义幂等提交、失败恢复及报告消费的已验证事实快照。
- 将相关 API、数据库迁移和图谱写入服务加入改造清单。

**复审要求：** 审核后能查询到真实实例和对象关系；重试不重复入图；失败不得被误记为成功；来源可从持久化事实回放。

### R06 · P1：Word 原文锚点硬要求与外部事实富化冲突

**涉及原报告：** §6.4、§10.5、§10.7、§20 第9项。

报告要求所有新事实都有原文 `EvidenceAnchor`，同时保留已验证外部主数据。现有设备富化确实会从档案补入 Word 原文没有的规格、材质等属性。

设备编号在 Word 中的位置可以支持设备身份匹配，但不能冒充档案材质值的出处。若所有值都强制要求 Word anchor，合法外部富化会被拒绝；若借用编号 anchor，则来源失真。

**建议修订：** 将事实来源定义为可区分的文档证据、外部记录、人工输入和推导结果。分别要求文档坐标、外部系统及记录版本、人工审核记录、推导规则及输入证据。身份匹配证据与属性值来源分别保存。

**复审要求：** 外部属性可追溯至真实记录；推导值可复算；不能用附近文本位置替代值的真实来源。

### R07 · P2：完整父链增强的效果依据不足

**涉及原报告：** §7、§9.3、§9.4、§17。

完整父链和树元数据帮助消歧具有合理性，但报告没有给出相应实验结果。`semantic_score + section_prior + ...` 也没有说明权重、校准和拒绝阈值的依据。现有代码对短 span 特意避免拼接上下文，以防上下文淹没实体语义，说明更多上下文并不必然更好。

**建议修订：**

- 将“统一提供可访问的结构上下文”与“模型必须消费全部祖先信息”分开。
- 用独立人工金标比较原始 span、局部窗口、直接父标题、完整父链等配置。
- 按文档类型、实体长度、多主体场景分别评估边界、类别、属性归属和关系指标。
- 定义评分校准、拒答阈值、延迟和内存预算，并固定模型、数据及策略版本。
- 基线输出用于回归比对；人工标注用于判断正确性。不能把旧输出直接当作正确答案，也不能以候选数量不减少替代质量门禁。

**复审要求：** 提交金标构建方法、数据隔离方案和消融计划。没有实测前，将收益表述为待验证假设。

## 4. 第二轮评审：彻底消除正则与硬编码 finder

### R08 · P1：当前方案没有实现机制替代与最终退役

新增目标是：**彻底消除正则、硬编码 finder**。

当前设计不能达成，原因如下：

| 原报告位置 | 当前约定 | 与新增目标的冲突 |
|---|---|---|
| §1 硬约束 | 保留 Profile、`doc_pattern` 和 finder 兼容路径 | 没有最终退出条件 |
| §3.2 非目标 | 先通过适配器接入旧 finder | 可以用于迁移，但后续没有完整替代阶段 |
| §10.2 | 给 finder 扩展父实体和 scope 参数 | 改善范围，保留原抽取机制 |
| §10.5 | Profile 确定性结果优先级最高 | 规则抽取仍是主要事实来源 |
| Phase 4、§15 | 扩展 finder 签名、统一 Candidate/Anchor | 规范输出不等于消除专用算法 |
| Phase 5 | Profile → NER → LLM 补抽 | 模型承担补缺，没有覆盖全部原职责 |
| §13、§17、场景 E | 模型关闭时仍保持原 finder 结果 | 依赖旧机制的降级承诺与最终退役冲突 |

#### 4.1 配置化不能充当消除证明

目前 `document_profile.py` 仍执行 `identity.pattern` 和 `number_pattern`；`relation_extractor.py` 的 `_RANGE_OVERRIDES`、`_METHOD_STRATEGIES`、`_MethodStrategy` 仍按业务类 IRI 分派专用 finder。

把正则移动到 JSON、TTL 或数据库，把 finder 包装成适配器，或仅把函数改名为通用抽取器，都没有消除原有依赖。本体菜单限制合法类别和谓词，也不会自动产生事实识别与绑定能力。

#### 4.2 正则范围不能默认缩小

用户提出的是“彻底消除正则”，未授权仅消除业务抽取正则、保留结构或分词正则作为例外。设计修订至少需要覆盖以下自有代码中的生产依赖：

| 范围 | 当前用途 | 对设计的要求 |
|---|---|---|
| 关系与属性抽取 | 药品编号、业务片段、属性值匹配 | 通用语义抽取和主体绑定替代，不能转移到配置继续执行 |
| Profile / `doc_pattern` | identity、number pattern、字段及表头定位 | 移除执行型抽取规则；重新定义剩余元数据用途 |
| Word 结构 | 标题编号、KV、字段标签识别 | 采用文档原生结构、通用解析算法或经验证的结构识别能力；重测章节和模板质量 |
| NER 前后处理 | 数值过滤、中文 word splitter、文本整理 | 提供无正则替代实现，验证边界、偏移及召回 |

若目标还覆盖第三方依赖内部的正则，需要单独列出依赖审计范围和可行性；本轮未核查所有第三方内部实现，不能据此宣称全栈零正则。不得用扫描少数文件的结果代替完整依赖说明。

消除正则和业务 finder 不要求取消本体 domain/range、datatype、单位、来源、基数等通用约束，也不要求把所有确定性处理交给 LLM。约束负责检验候选；不能借校验步骤重新制造无证据的业务事实。

## 5. 达成新增目标所需的架构修订

建议最终生产链路为：

```text
文档结构与证据 IR
  → 本体驱动的通用抽取任务
  → 证据检索、实体和属性候选召回
  → 以主体实例为条件的属性归属与关系判定
  → 来源和本体约束校验
  → 候选审核、实体归一化、事实持久化
  → 实例级 coverage 与受控补抽
```

### 5.1 定义通用抽取任务及模型责任

任务输入至少包含主体候选、谓词或属性定义、目标类型、证据范围、上下文策略和预算。新增业务类型或关系时，通过本体定义、词汇描述和示例提供语义，不增加专用 Python 分支、finder 或抽取正则。

实体与属性召回、主体绑定和关系成立判断需要分别定义算法、模型接口和拒答条件。可以采用不同的通用模型或解析算法，但必须说明每项原 finder 职责由谁替代。单纯增加 ContextEnvelope 不能替代这一设计。

### 5.2 明确规则退役路径

| 阶段 | 必须形成的结果 |
|---|---|
| 职责盘点 | 列出所有自有正则、业务类分派、Profile 执行规则和隐式兜底，逐项映射到替代实现及验收样本 |
| 通用能力建设 | 完成候选召回、主体绑定、来源校验、实例级 coverage 和审核入图契约 |
| 影子比对 | 使用固定基线和独立人工金标比较新旧结果；旧机制只承担明确的迁移职责 |
| 独立运行验证 | 禁用旧规则后完成抽取、补抽、审核、报告和模型故障场景验证 |
| 最终退役 | 删除生产调用及隐式回退，移除可执行 pattern 配置；检查结构解析和分词层是否也达到约定范围 |

旧结果可以作为离线回归资料保存。若最终生产仍调用旧 finder 或规则兜底，则只能认定为迁移未完成。

### 5.3 重写降级和不回归条款

能力不回退应约束用户可见质量、来源完整性和服务行为，不应永久锁定旧算法或保留旧错误事实。

如果通用关系绑定依赖模型，模型不可用时必须明确返回待处理候选、未完成状态或结构预览。若仍要求完整抽取能力，需要另行设计并验证不依赖该模型的通用实现，不能以重新启用旧 finder 履行降级承诺。

### 5.4 增加最终验收条件

1. 最终生产范围内不存在专用业务 finder、按具体业务类 IRI 分派的抽取分支及可执行抽取正则；配置和动态加载路径一并检查。
2. 加入此前未支持的实体类和关系，不修改抽取代码、不新增正则或 finder，仍能生成有证据的候选。
3. 使用未见过的章节名称、字段表达及表格布局，评估独立泛化能力，避免只验证已有模板。
4. 主体在标题、值在正文、同段多主体、多值、否定和条件关系均有验证；无法唯一绑定时明确拒答。
5. 错谓词、错主体和未审核冲突不能错误满足 coverage；补抽不会无限重复。
6. 节点、边和逐值来源可持久化、审核、幂等提交和回放。
7. 在约定的正则消除范围内，结构、分词、长文本窗口和来源偏移仍满足质量要求。
8. 质量、延迟及资源门禁在禁用旧机制的条件下测量；提交真实金标结果后再确认替代成功。
