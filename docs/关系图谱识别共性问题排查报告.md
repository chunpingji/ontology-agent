## 2. 历史证据：不只批量字段受到影响

4 个通用抽取任务均出现过引用定位类错误。301 条子任务事件中，40 条记录了简短技术错误作为主要失败原因：

| 主要失败原因 | 子任务数 | 解释 |
| --- | ---: | --- |
| `ambiguous_source_quote` | 10 | 引用在允许原文中有多个匹配 |
| `source_quote_outside_scope` | 11 | 引文存在于证据单元，但不在本次允许区域 |
| `source_excerpt_mismatch` | 5 | 引文与原文不一致 |
| `invalid boolean` | 5 | 值不能通过布尔规范化 |
| `unsupported numeric grammar` | 2 | 值不能通过数值语法校验 |
| `assertion_polarity_conflict` | 3 | 召回与绑定验证对肯定/否定状态不一致 |
| `model_unavailable` | 4 | 模型调用未返回可用结果 |

上述是“子任务主因”计数；一个子任务可能有多个候选错误。完整诊断中的引用歧义、范围外引用、原文不匹配分别为 29、13、6 次，不应与子任务计数相加。

目标源文档另外有 **30 个候选因 `record_mapping_mismatch` 被拒绝，涉及 12 种属性**：`equipmentID`、`equipmentName`、`packagingType`、`shelfLife`、`residueSolubility`、`residueSolvent`、`oel_ug_per_m3`、`ld50_mg_per_kg`、`pde_mg_per_day`、`inProcessControl`、`outputMassRange_kg`、`storageHumidity`。

结合子任务错误，问题记录覆盖 **19 种不同的关系或属性**，还包括 `hasStorageCondition`、`hasSolubilityCharacteristic`、`constructedOf`、`nextStep`、`lightProtection`、`isDedicatedEquipment` 和 `plannedBatchSizeMax_kg`。这是受错误机制影响的谓词范围，不是 19 种已人工确认的真实漏项。

可以直接核对的例子是 `StorageCondition.packagingType`：原文“**双层聚乙烯薄膜袋外加药品包装用复合袋**”确实位于“包装方式”列，但旧候选的映射使用 `table` / `row`，校验器要求 `table_path` / `row_index`，因此被拒绝。当前程序补齐同一行映射后，这个原始候选通过结构校验，证明上一轮修复已经覆盖这类旧问题。

相反，旧任务中也出现把物料编码 `02002668` 当作 OEL 的候选，以及为“原料厂区大浦仓库”查找毒性的无效任务。这些候选不应因提高召回而放行。历史任务的 `incomplete`、拒答或拒绝数量不能直接解释为漏识别数量。

## 3. 当前版本仍可复现的问题

### 3.1 表头与数据行的绑定契约冲突——已用真实候选复现

提示词明确要求：“绑定证据应引用说明主体、属性含义和数值角色的完整断言，表格可联合引用表头及行单元”。上下文构造也把对应列头列入允许的绑定证据。

但 `binding_record_mapping()` 只有在所有锚点位于同一表格、同一行时才生成记录映射；`validate_document_candidate()` 又要求 `table_record` 的每个绑定锚点均与映射行相等。

对原始 `packagingType` 候选重放得到：

| 绑定引用 | 当前程序结果 |
| --- | --- |
| 只引用数据行中的包装值，程序生成行映射 | passed |
| 引用“包装方式”表头 + 同一数据值 | 无法生成映射，触发 `record binding requires an explicit record mapping` |
| 表头 + 数据值，并显式提供正确数据行映射 | `record_mapping_mismatch` |

因此，**模型遵循“联合引用表头”要求时，合法的绑定仍可能被程序拒绝**。这会影响设备编号、包装、限值、批量等依赖列头解释含义的表格属性；不是每个表格候选都会失败，是否触发取决于绑定方法及引用组合。

代码位置：[提示词与映射生成](/opt/dev/chen/ontology-agent/backend/app/services/extraction/extraction_tasks.py:90)、[表格上下文](/opt/dev/chen/ontology-agent/backend/app/services/extraction/hierarchical_context.py:240)、[记录校验](/opt/dev/chen/ontology-agent/backend/app/services/extraction/semantic_binding.py:120)。

### 3.2 合并单元格的共享主体没有进入逻辑记录——已用真实文档复现

目标原文 `table:10` 的 `HRS-1597` 单元格位于第 1 行、第 0 列，解析结果明确保留 `row_span=2`，覆盖“大鼠14天亚急毒试验”和“犬14天亚急毒”两行。后者 PDE 原文为 `7.5`。本报告所有行号均为程序使用的从 0 开始的行号。

当前范围构造只比较 `row_index` 是否相等，不使用已有的 `row_span` / 表格网格。以这个共享 API 单元格作为已验证主体构造范围，得到：

- 第二行“犬14天亚急毒”不在主体可检索范围内。
- 第二行 PDE `7.5` 不在主体可检索范围内。
- 独立构造第二行的实体召回上下文，也没有包含共享的 `HRS-1597` 单元格。

HRS-1597 和 HRS-5678 各有 5 个纵向合并单元格，涉及设备和毒理等表格。这是实际文档反复出现的结构，不能只按普通单行表格处理。

这里证明的是范围和上下文遗漏；尚未证明整篇重跑一定漏掉 PDE `7.5`，因为其他提及或路径可能补回。后续修复还需保留不同试验的身份，不能将两条试验值直接合并成无条件的单一 PDE。

代码位置：[解析器保留合并信息](/opt/dev/chen/ontology-agent/backend/app/services/extraction/docx_structure.py:484)、[范围只按起始行匹配](/opt/dev/chen/ontology-agent/backend/app/services/extraction/evidence_scope.py:136)、[上下文按行匹配](/opt/dev/chen/ontology-agent/backend/app/services/extraction/hierarchical_context.py:250)。

### 3.3 重复数值或名称无法用完整断言消歧——已确定性复现，新检查点仍有同类错误

最小原文：`计划A批量5kg，计划B批量5kg。`

任务：计划 A 的批量；模型替身返回值引用 `5kg`，并附带唯一完整断言 `计划A批量5kg`。当前代码仍返回 `ambiguous_source_quote`，候选为 0，绑定验证没有被调用。

原因是属性阶段先对裸 `value.text` 定位，未使用 `proposal.assertion_spans` 缩小数值定位范围。生产协议同时把模型的 `start` / `end` 限定为 `null`，所以模型也不能通过明确的位置选择重复值。

这类问题会影响同段重复的温度、时长、数量、上下限端点及实体名称。当前新版本检查点中已出现同类引用歧义，但检查点没有保存所有被丢弃的原始提案，不能据此确定每个具体漏项。

代码位置：[唯一引文定位](/opt/dev/chen/ontology-agent/backend/app/services/extraction/extraction_tasks.py:296)、[属性只定位 value](/opt/dev/chen/ontology-agent/backend/app/services/extraction/extraction_tasks.py:471)、[坐标输出契约](/opt/dev/chen/ontology-agent/backend/app/services/extraction/model_protocol.py:52)。

### 3.4 已验证关系只扩到同一语句，后续指代句和段落仍不可见——已确定性复现

最小文档布局：对象锚定封面标题“临床备样生产计划”；另一个章节有以下正文：

> 本报告包含临床备样生产计划。该计划生产用途为一期临床。
>
> 该计划批量下限为3.8kg，上限为6.6kg。

构造并通过验证的 `hasProductionPlan` 关系引用第一句后，对象范围只包含封面标题和“本报告包含临床备样生产计划”。同段第二句的用途、下一段的批量均不可检索。再执行允许一次扩围的 `expanded_gap_scope()`，下一段仍不可见。

原因是关系扩围止于语句边界；缺口补抽的章节扩围仍从对象原始提及所在章节出发，没有从关系证据的新章节继续检索。这与原始批量漏识别具有相同的范围传递问题，只是上一轮已经修复了“属性和关系位于同一句”的子场景。

代码位置：[关系同句扩围](/opt/dev/chen/ontology-agent/backend/app/services/extraction/evidence_scope.py:155)、[补抽从原始提及章节扩围](/opt/dev/chen/ontology-agent/backend/app/services/extraction/gap_extraction.py:17)。

### 3.5 字面量和单位契约覆盖不足——语法缺口已复现，存量错误值尚未确认

在临时本体存储中加载得到 329 个类、137 个不同数据属性和 67 个不同对象关系。数据属性包括 49 个 decimal、60 个 string、18 个 boolean、7 个 integer、2 个 date、1 个 gYearMonth；**未发现未支持的数据类型名称**。问题主要在这些类型允许的原文表示及单位传递：

| 输入与类型 | 当前结果 | 影响边界 |
| --- | --- | --- |
| `是` / `否`，boolean | 正常 | 上一轮修复有效 |
| `√` / `×`，boolean | `invalid boolean` | 遇到明确图例解释的布尔勾选表仍缺少受证据约束的映射 |
| `—`，boolean | `invalid boolean` | 本文档图例表示研究数据不充分，应保留未知，不能改成 false |
| `2026年6月`，gYearMonth | `2026-06` | 上一轮修复有效 |
| `2026年6月1日`，date | `invalid date` | ISO 日期支持，中文完整日期仍不支持 |
| `12mg/kg`、`0.2mg/day`、`25℃`，decimal | `unit_unknown` | LD50、PDE、温度等相关原文写法存在语法缺口 |
| `0.2g`，decimal，无目标单位 | 数值 `0.2`、单位 `g` | 不会自动按属性要求转换为 mg |

137 个数据属性的运行时定义均没有 `canonical_unit`；其中 21 个 decimal 属性的 IRI 明确带单位含义，例如 `ld50_mg_per_kg`、`pde_mg_per_day`、`temperature_C`、`plannedBatchSizeMin_kg`。`semantic_schema_from_engine()` 的字段白名单也不传递 `canonical_unit`，导致规范化器已有的目标单位换算能力没有接入这些定义。

因此模型引用“完整数值＋复合单位”可能被拒绝；只引用裸数值又可能丢失单位语义。推理桥接读取标量时只取 `normalized_value`，进一步说明单位需要在进入事实层之前统一。**本轮未证明当前任务已经持久化了换算错误的数值**，不能把这一风险当成已有错误事实。

实际 HRS-1597 文档确有 `√` / `×` / `—` 图例，但所在毒性表不等于上述 18 个 boolean 属性的逐项验收；HRS-5678 部分毒理数值为 `XX` 占位，不应强行提取为数字。

代码位置：[规范化器](/opt/dev/chen/ontology-agent/backend/app/services/extraction/literal_normalizer.py:71)、[本体属性契约](/opt/dev/chen/ontology-agent/backend/app/services/extraction/extraction_tasks.py:211)、[目标单位调用](/opt/dev/chen/ontology-agent/backend/app/services/extraction/extraction_tasks.py:481)、[推理标量取值](/opt/dev/chen/ontology-agent/backend/app/services/reasoning/fact_bridge.py:236)。

## 4. 其他共性放大因素

**跨提及实体身份仍然碎片化。** HRS-1597 在旧冲突版中有 4 个同类同名 API 提及，在原文版中有 6 个；HRS-5678 的成品、色谱柱、粗品和存放条件也出现重复提及。当前只去重相同候选 ID，不会把正文、物料表和毒理表中的同一业务实体通过证据归并。因此属性可能分别挂在不同提及上，报告沿某条关系路径看到的对象仍然缺属性。同名不必然同一实例，后续需要设备编号、产品代码、原文指代等身份依据，不能按名称直接合并。

**任务数不是唯一预算。** 2048 已解决旧默认任务数过小的问题，但实体召回阶段仍先于关系/属性阶段，类型验证和逐条绑定也消耗模型调用；调用上限为 `2 × max_tasks`。提高任务数不能改变范围、映射或规范化规则，也不能保证所有多跳路径都已跑完。不能用新任务尚处于实体阶段时的空关系结果判断最终退化程度。

**错误分类仍较粗。** `chat_with_schema()` 会把请求异常、JSON 解析失败等收敛为无结果，抽取层再显示为 `model_unavailable`。历史 4 次该错误不能全部解释为服务宕机；应记录超时、输出截断、解析错误和请求失败的具体原因。

## 5. 建议的修复顺序与验收

| 顺序 | 修复内容 | 最小验收要求 |
| --- | --- | --- |
| P0 | 建立统一的表格逻辑记录：利用 grid / row_span / column_span；将列头证据与数据行归属分开验证 | 原包装值联合表头通过；跨两行 API 共享主体可用于第二行；不同试验和不同设备的值仍不串行 |

## 8. 证据审核页 `CONTRACT_NOT_FOUND` 修复（2026-09-07）

### 8.1 原因

运行环境中的“风险评估文档 v2.2”模板引用 `unresolved:ontology`，报告契约表为空，因此无法计算 V2 覆盖清单。这是迁移后的模板配置未完成，不是证据审核失败。另有三处程序问题放大了该错误：

- `ReportingError` 继承自 `ValueError`，证据接口把原本含有具体契约引用的 404 转成了只有错误码的 422。
- 页面将覆盖检查和证据读取共用一个错误状态；审核／提交成功后，后续覆盖刷新失败也会显示成操作失败。
- V2 冻结快照没有提供旧页面读取的 `required_gaps`、`completion`、`diagnostics`，任务也缺少显示名称。即使补齐契约，原页面仍可能因 `diagnostics.map` 报错。

### 8.2 修复行为

- 证据接口保留报告错误的 HTTP 状态及结构化详情。覆盖读取对已识别的模板配置问题返回 `availability: unavailable`、具体原因和模板入口；缺口数与清单 ID 为 `null`，不会把无法计算表示为零缺口。缺失作业、快照等其他错误仍返回对应的错误状态。
- 正常覆盖的汇总直接来自同一份 V2 冻结快照的需求与阻断诊断，包含 `material_status` 和任务名称；未通过模板校验时不会启动预览运行。
- 证据、覆盖与审核操作分别显示结果。覆盖请求失败不改变已成功的审核／提交结论；切换文档或模板时重置面板状态并取消旧读取，旧操作完成后不会刷新新文档。
- 抽取运行记录版本，读取历史运行时兼容从候选提取版本。旧版诊断保留，页面标明旧版本结果并按次数汇总重复原因。该文档的已存结果仍是 `generic-semantic-v7`；新服务已加载 `generic-semantic-v8`，重新识别后才能获得新版本结果。

没有创建占位契约、代替用户审核或发布契约，也没有自动审核证据。覆盖清单仍需在模板设置中引用真实且已发布的契约后才能计算；补抽和对象集合确认继续要求有效清单与已发布快照。
