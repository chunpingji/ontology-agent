## 3. 页面上的“2 项、模型调用 2 次”为什么长时间不变

### 3.1 一项任务并不对应一次模型请求

实体任务的实际顺序为：

1. 模型召回实体。
2. 程序校验逐字引用、范围和身份字段。
3. 将可进入类型复核的提案分批交给模型。
4. 所有复核批次结束后才保存整个任务的断点，并更新 SSE 计数。

复核批量由以下公式决定：

```python
size = min(max_objects_per_task, max(1, max_output_tokens // 512))
```

实际配置 `max_objects_per_task=8`、`max_output_tokens=2048`，所以一批最多 4 个。第 3 项有 13 个提案，分成 `4 + 4 + 4 + 1`，需要 1 次召回及 4 次复核。

第 2 项于 10:58:55 完成后，后台继续执行上述 5 次模型调用；直到 11:15:37 第 3 项结束，界面才从“2 次”跳到“7 次”。这段没有计数更新的时间约 **16 分 42 秒**。

代码：[类型复核分批](../backend/app/services/extraction/extraction_tasks.py#L603)、[模型调用计数](../backend/app/services/extraction/extraction_tasks.py#L489)、[任务结束写断点](../backend/app/services/extraction/extraction_tasks.py#L1215)、[断点触发 SSE](../backend/app/api/extraction.py#L812)、[界面统计文案](../frontend/src/components/extraction/template-slot-editor.tsx#L887)。

### 3.2 已复核的实体也等整个任务结束

类型复核循环将判定保存在任务内部的 `verified` 列表。它们只有在 `execute_task()` 返回后，才进入运行级候选及安全增量图谱发布。

因此本次已经复核了 12 个实体时，页面仍保持前一任务的计数。已实现的“安全任务批次增量发布”，尚未细化到“一个任务内部的复核子批次”。页面候选总数 83 还包含历史识别结果，不能解释成这一轮新识别了 83 项。

### 3.3 超时重试是另一个隐藏上限，本次前 7 次没有发生

配置是每次 `timeout_s=600`、`timeout_retries=3`，即最多 4 次尝试，一次逻辑模型调用可能等待约 40 分钟。内部重试没有递增 runner 的 `model_calls`，也没有独立进度事件；暂停检查只在任务边界发生。

**本次前 3 项的 `_calls=7`，`performance.stages.model.calls=7`，二者一致，加上线程采样 `attempt=0`，没有证据把这 23 分钟归因于超时重试。** 它是需要处理的可观测性和等待上限问题，不是已证实的本次主因。

代码：[实际超时重试循环](../backend/app/services/extraction/local_semantic_model.py#L148)。

## 4. 长输入和复核设计放大模型等待

### 4.1 每批复核仍发送全部 136 类菜单

只读加载这次保存的本体、文档 IR、候选及实际配置，重建前三个任务；计算得到的 `input_id` 与在线作业一致，前三个 task_id 也与断点一致。实验只调用 tokenizer，没有调用模型生成。

源文档只有 4,534 字符、486 个证据单元，其中 440 个非空。前三个实体任务各装入 31 个目标区域，每次带全部 136 个可达类菜单；输入预算分别为 **14,225 / 14,443 / 15,302 tokens**。

第三个任务的 4 次复核中，所有待复核提案属于同一个本体类别，但每次仍携带 136 类菜单：

| 复核批次 | 提案数 | 当前输入预算 tokens | 只保留待复核类别定义的实验 tokens |
| --- | ---: | ---: | ---: |
| 1 | 4 | 15,122 | 5,835 |
| 2 | 4 | 15,125 | 5,838 |
| 3 | 4 | 15,124 | 5,837 |
| 4 | 1 | 14,574 | 5,290 |
| 合计 | 13 | 59,945 | 22,800 |

四次复核的输入预算可以在该实验中减少约 **62%**。这些值按代码使用真实 tokenizer，并包含程序的 128-token 预留；不等同于服务端 chat template 处理后的 prompt token 数。

这只是输入长度实验，**没有证明裁剪后的语义判断等价，也没有得到整轮提速 62% 的结论**。正式实现需保留待判类别及必要祖先定义、身份键、原文范围、表格角色和竞争信息，逐条验证结果等价；召回阶段仍须覆盖全部允许类别。

代码：[实体菜单](../backend/app/services/extraction/extraction_tasks.py#L894)、[复核复用召回 envelope](../backend/app/services/extraction/extraction_tasks.py#L613)。

### 4.2 动态内容排在静态上下文前，削弱前缀缓存

`model_request()` 内部显式将本体 task 放在 context 前部，但最终经 `canonical_json()` 排序后，外层实际顺序是：

```text
candidate → context → stage
```

`ModelProtocol` 再次使用同样的排序。复核候选每批变化，出现在长本体上下文之前；无法利用后续静态内容形成同一长前缀。system 内的动态响应枚举也会影响前缀一致性。

现场 `/slots` 多次显示 `n_prompt_tokens_cache=0`，模型日志多次报告 LRU 选槽及 prompt cache 淘汰。这些现象与动态前缀、跨作业争用共同吻合，但本次没有分离测量各自的贡献。

建议区分“用于身份哈希的规范序列化”和“用于模型传输的稳定前缀序列化”，将候选和动态证据放在静态定义之后，同时维护原有请求身份与审计规则。

代码：[外层请求排序](../backend/app/services/extraction/hierarchical_context.py#L102)、[协议再次序列化](../backend/app/services/extraction/model_protocol.py#L44)、[规范 JSON 排序](../backend/app/services/extraction/evidence_identity.py#L28)。

llama.cpp 官方文档及实现确认：`cache_prompt` 默认开启，通过公共前缀复用 KV；并非仅设置“开启缓存”即可复用变化前缀之后的上下文。本次通过 Context7 核对这一语义，未修改服务器配置。

### 4.3 长输入处理会拖慢另一槽位生成

实际服务为 Qwen3.6-35B-A3B，llama.cpp `b9853-7af4279f4`，4 张 P100、layer split、2 个槽位。以下是共享服务的真实请求计时，**服务端 task 编号不是应用抽取 task_id，未逐条映射到具体作业**：

| 服务端 task | 输入处理 | 生成阶段 | 现象 |
| --- | ---: | ---: | --- |
| `98945` | 15,014 tokens / 63.03 秒 | 236 tokens / 5.61 秒 | 输入处理占此请求约 92% |
| `98934` | 4,607 tokens / 18.06 秒 | 596 tokens / 133.60 秒 | 同期另一槽位处理长输入，生成被明显拖慢 |
| `99236` | 15,013 tokens / 63.11 秒 | 266 tokens / 65.35 秒 | 少量输出也需等待两分多钟 |

日志在另一个槽位处理输入时，多次显示已生成请求的短窗口吞吐降至约 **0.12–0.26 tokens/s**；长输入结束后又出现约 40 tokens/s 的生成。因而简单提高应用并发不能据此预期提速。

该服务器未启用 `/metrics`，请求返回 501；`/props`、`/slots` 及已有时间日志可读取。请求的 generation prompt 已带空的 `<think>…</think>`，与应用关闭 thinking 的设置一致；未发现应把本次问题直接归因于 thinking 未关闭的证据。

## 5. 前两项未通过的具体原因

### 第 1 项：逐字引用校验失败

- task_id：`2c5d80b498684fd0e4b71a1138d07f94e8283a3b2170c54a7cd6f12afcd07ccc`。
- 断点保存 3 次 `source_excerpt_mismatch`，有效候选 0。
- `_anchor()` 要求返回的 text 能在指定 evidence 中逐字定位；不满足则拒绝。
- 本轮失败断点未保存原始响应及具体错误引用，无法进一步确定是空格、标点、证据编号错配还是模型改写。不能将错误码推断为某一个具体文本问题。

### 第 2 项：模型在召回阶段整体拒答

- task_id：`16b4ca4054eaacacace7eafc06c87ce13655ef8d714f90c8a4d3c057bd33da39`。
- `refusal_reason` 称“肿瘤药物”“注射用粉针剂”部分提案不能得到支持，并明确表示“其余候选实体（如 HRS-5678）类型支持充分”，最终仍“拒答整体实体列表”。
- 代码看到任意非空 `refusal_reason` 就抛错，尚未进入逐项提案处理；整项没有保留候选。
- 虽然模型自己的文字写了“实体类型复核失败”，实际统计阶段是 **`entity_recall`**，不是程序的独立类型复核阶段。

这一故障降低了有效产出率。应让实体召回协议表达逐提案的可支持性，明确不支持的提案只影响自身；身份唯一性与类型支持分别判断。不能靠放宽逐字引用、接受错误类型或绕过独立复核解决。

代码：[逐字锚点检查](../backend/app/services/extraction/extraction_tasks.py#L413)、[全局拒答分支](../backend/app/services/extraction/extraction_tasks.py#L532)。

## 7. 建议实施顺序与验收

### P0：统一执行入口、断点和运行所有权

让重新识别、恢复、继续、重试全部进入同一后台执行服务。以 job_id 建立原子运行租约和 run_id，重复启动返回已有运行或 409；前端运行时禁用继续/重试作为辅助保护。各入口共享同一版本的断点、暂停和取消控制，提交时检查 run_id，防止旧运行更新新状态。

验收：同一 job 同时提交不同入口只出现一个 runner；跨进程并发、重试和异常恢复仍保持唯一所有权。页面暂停必须覆盖此作业所有入口。

### P0：按真实模型调用和复核子批次报告进度

模型请求发出、排队、返回、重试、类型复核批次完成均发事件。分别报告已完成任务、当前任务阶段、提案复核数、逻辑调用数、HTTP 尝试数及本次等待时间。运行中的计时要正确处理尚未结束的模型阶段，不能直接用当前 wall 减掉仅记录已结束调用的 model 时间。

增加复核子批次的恢复能力；对于已证明不会被后续判定失效的候选，再扩展安全增量发布，避免取消后重复支付已完成复核成本。

验收：模拟第三项 `13 → 4/4/4/1`，界面能在完成前展示各次调用和复核进度；恢复不会重复已完成子批次，重复窗口及竞争主体仍触发必要失效。

### P1：缩小复核上下文，恢复有效前缀复用

类型复核使用待判类别及必要语义闭包；保留独立逐项结论，使用紧凑结果和有界理由后再评估适当扩大批量。稳定本体/协议前缀与动态候选后缀分开；全局控制发送给共享模型的并发，测量输入处理和生成相互干扰后再调优。

验收：固定源文档和本体版本，对比候选类型、身份、否定断言、原文锚点及审核结果；记录 prompt tokens、cache tokens、排队、输入处理、生成与完整响应时间。输入长度实验不能替代语义回归和真实时延验收。

### P1：改善失败局部性和失败诊断

将实体的“不支持”局限到对应提案，避免一个模糊类别导致整批拒答；保留受控诊断，至少包含 task/stage、错误码、证据 ID 和失败引用的必要信息。为调用设置总等待预算及可取消重试，分别计量逻辑调用与实际请求。

验收：一项不支持不丢弃同批有效实体；错误引用继续严格拒绝；超时重试可见、可取消，且不放大为失控的长等待。

### 10.1 复核上下文与传输协议

### 10.2 全局调度、总预算和取消

新增 `local_model_pools`、`local_model_requests` 两张表。所有本应用的本地结构化模型调用共用 `chat_with_schema`，包括实体/属性/关系识别、复核、章节摘要和模板辅助等调用；不同模型名称、同一服务地址下不同路径共用模型池。

- 按规范化的服务 scheme/host/port 建立模型池；数据库短事务串行处理入队与准入，按照入队顺序分配剩余容量，默认同时最多 **2 个 HTTP 请求**。
- 模型等待期间不持有数据库事务；槽位租约 30 秒、每 5 秒续租。排队请求也有租约，失去运行权或槽位后停止请求，过期记录可回收。
- 通过 AsyncOpenAI / HTTPX 异步请求和实际 wall-clock deadline 限制完整响应时间。排队、HTTP 尝试、超时重试及可选 schema fallback 共用同一个总预算；SDK 自动重试关闭。
- 暂停与所有权检查进入排队、请求等待和重试路径，正常每 250 ms 检查一次。取消后先等待 HTTP 协程退出、关闭其连接，再释放槽位。
- 被取消的任务记为 interrupted，不消耗一次已处理任务额度；直接“继续”即可重做该任务，不必勾选重试失败任务。已独立验证的实体兄弟项可保留。共享值联合验证被打断时不发布未验证属性，也不将临时冲突记成已完成复核；章节摘要暂停保留断点。

| 配置 | 默认值 | 作用 |
| --- | ---: | --- |
| `LOCAL_LLM_MAX_CONCURRENCY` | 2 | 本应用向同一模型服务发送的并发上限 |
| `EVIDENCE_TOTAL_TIMEOUT_S` | 600 秒 | 抽取一次逻辑模型调用的总等待预算 |
| `LOCAL_LLM_TOTAL_TIMEOUT_S` | 600 秒 | 其他结构化模型调用的默认总预算 |
| `EVIDENCE_TIMEOUT_S` / `EVIDENCE_TIMEOUT_RETRIES` | 600 秒 / 3 次 | 单次请求上限及最多重试数，均受总预算约束 |

例如首次请求用尽 600 秒后，不会再额外等待三轮 600 秒；只有总预算尚有余额时才会重试。以上运行参数独立于断点语义身份。

模型池约束的是使用这一公共客户端及数据库的应用请求；未接入该调度器的其他客户端仍可能占用同一模型服务器，应用侧容量限制不能消除其干扰。
