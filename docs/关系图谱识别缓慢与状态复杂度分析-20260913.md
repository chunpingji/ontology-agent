# 关系图谱识别缓慢与状态复杂度分析

日期：2026-09-13。依据当前代码、实际运行的只读数据库快照和历史性能记录；没有重启、暂停、恢复或创建识别任务，没有发起模型调用。

结论：**检查点、图谱和精排状态的复杂处理与后期任务间隔增长有明确的机制关联，是需要优先验证的性能因素；但当前最大的已测时间项仍是发现/核验模型处理长输入。不能把全部缓慢归于状态存储，更不能用状态块数量直接推导数据库耗时。**

本轮 v3 的事件后可见保存区间明显短于旧 v2 样本，但两轮任务规模和识别政策不同，不据此计算整轮提速比。尚未归因的大段时间位于模型请求之外，包含事件之前的状态构造/校验、搜索、图谱投影、协调等待和恢复等；这些步骤仍有全量工作，底层写小增量不会自动消除它们。

## 2. 总时间花在哪里

使用调度请求 `started_at/finished_at` 求时间区间并集，按摘要/识别模型、排序模型、可见保存区间、明确暂停、其余时间依次消除重叠。下面各项可以相加；请求累计秒数和其他函数累计时间不能再加入本表。

| 互不重叠的墙钟区间 | 分钟 | 总历时占比 |
|---|---:|---:|
| 摘要及发现/核验模型请求 | 557.71 | **68.33%** |
| 不与上述模型重叠的排序请求 | 0.90 | 0.11% |
| 不与模型重叠的可见保存区间 | 6.63 | 0.81% |
| 已确认处于 paused 的时间 | 11.77 | 1.44% |
| 其余尚未归因的请求外时间 | **239.23** | **29.31%** |
| 合计 | **816.25** | **100%** |

保存区间的起点为进度事件创建，终点为对应检查点或模型协议制品创建。它不包含事件之前的准备、部分块发布和最后数据库提交。尤其精排事件在状态编码及块发布之后产生，不能把其约 12 毫秒的事件至制品间隔当作完整精排保存耗时。

明确暂停为 09:20:10—09:31:57，共 706.43 秒。暂停请求到安全停下、恢复后重新开始执行的时间仍按模型/保存/其余区间记录，没有全部算作用户主动暂停。

因此 **0.81% 是当前可见保存部分的下界，不是“状态处理只占不到 1%”的结论**；同样，不能将未归因的 29.31% 全部记为检查点耗时。

发现/核验合计 **1237 次请求、709 万输入 tokens**。发现平均约 4841 输入 tokens，核验约 7804。调度记录中的服务端 `prompt_ms` 合计 26980.87 秒，占这两类请求累计时间 **80.87%**；记录的缓存命中约占输入 5.22%。

这说明长输入反复处理是当前最大的已测耗时来源。状态精简可以缩短两次调用之间的工作，但不会直接消除已经花在模型输入处理上的约 7.5 小时。还需减少低收益任务数量、复用稳定提示前缀、去掉提示中的重复结构，同时保留原文证明和独立核验。

全部模型调度请求的排队时间累计仅 **39.93 秒**，典型单次约 0.02 秒。这里的排队仅指进入共享调度器之后的等待，不包括请求尚未登记前等待协调器保存状态的时间。没有证据将本轮十几个小时的主要原因归为共享模型队列拥堵或精排 GPU 单次推理慢。

运行进度中的 `model_calls=1244` 与请求表 1237 次发现/核验完成记录口径并不一致；本节严格使用实际调度请求，未把两个数字混合计算，也未在本轮定位差额原因。

这两个窗口都不包含上述明确 paused 区间。全程相邻发现/核验请求间隔的最早 10 个中位值约 **1.10 秒**，最后 10 个约 **19.20 秒**；间隔也可能包含排序请求及其他工作，不是保存函数计时。

最长间隔 1325 秒跨越暂停与恢复，不能作为单次检查点性能样本。后期另有多次约 2—3 分钟的模型间隔，需要进一步对齐搜索、基线、恢复和控制事件，不能仅凭时间接近就断言是某一个函数。

现象支持“运行越到后期，模型之外的工作越明显”这一判断。结合下节同步全量处理代码，状态规模是重点嫌疑因素；尚缺函数级计时来拆出具体比例。

## 5. 五类复杂状态分别怎样影响速度

| 部分 | 当前可证实的放大机制 | 判断 |
|---|---|---|
| 恢复检查点 | 每批重新导出前沿、搜索和覆盖；构建任务批次并同步提交；部分历史仍参与校验，恢复还要重放任务前缀 | 直接处于识别关键路径，重点检查构造和校验成本 |
| 状态块记录 | v3 热保存复用未变状态，但每种制品每 32 版仍完整建基线；基线需块构建、hash、索引和插入 | 周期尖峰有依据；历史块数本身不能证明每次都全库扫描 |
| 内部图谱 | 每任务构造图快照，发布时再次投影；候选写入准备仍检查整图、全部 heads 和精确版本 | 实际写入增量之前仍有全量计算，随候选和证明数量扩大 |
| 展示图谱 | 每批重建证据选择映射、校验冻结本体、为所有节点编译菜单、生成展示载荷及 hash | 与内部图/检查点重复处理相关，静态部分可以复用 |
| 精排状态 | 每次模型派发前需持久化确认；快照仍处理累计账本/回执，保存校验历史 epoch，并重新生成排序摘要 | 保存次数乘以累计状态处理量，会延迟实际模型派发；与 GPU 推理时间不同 |

具体调用链和依据：

- [executor.py](../backend/app/services/extraction/ontology_guided/executor.py) 的 `snapshot_graph()` 扫描全部计划台账；`current_frontier()` 导出调度与搜索状态；新任务完成后同步 `batch_hook()`，成功返回才继续。
- [execution.py](../backend/app/services/document_analysis/execution.py) 的 `_prepare_batch_objects()` 读取候选/证明 heads 并检查整图候选；`_persist_recognition_batch()` 再构造图、选择映射、读取制品和检查点。`db.get()` 是否实际发 SQL取决于会话缓存，本次没有 SQL 探针，不能据代码遍历次数宣称实际查询条数。
- [read_artifacts.py](../backend/app/services/document_analysis/read_artifacts.py) 每批准备 `public_graph`，包括冻结本体解析和每个节点的菜单；[public_projection.py](../backend/app/services/document_analysis/public_projection.py) 构造选择映射和累计排序摘要。
- [semantic_reranker.py](../backend/app/services/extraction/ontology_guided/semantic_reranker.py) 的 `snapshot()/fork()` 处理当前账本及历史结果；[ranking_execution.py](../backend/app/services/extraction/ontology_guided/ranking_execution.py) 明确等待协调器的持久确认。
- [incremental_state.py](../backend/app/services/document_analysis/incremental_state.py) 缓存精确已提交前驱并按路径生成变化；[state_artifacts.py](../backend/app/services/document_analysis/state_artifacts.py) 的块查询限定本轮准备的 hash。当前不能沿用旧分析中“每次查询所有历史块库存”的描述。

如果第 n 次提交仍扫描前 n 次累积结果，即使只写一小段增量，总处理量仍可能接近累积增长的平方。结构共享已经避开部分历史正文遍历，因此这只是剩余累计扫描的机制说明，不是对全部 v3 热路径复杂度的统一结论。

## 8. 最终失败与状态提交直接相关，但不同于总耗时归因

数据库保存的安全异常栈为：`_execute_dispatched_run → _execute_claimed → executor.run → batch_hook → _persist_recognition_batch`，异常类型为 **HeadConflict**。记录的运行时行号对应批次准备后检查运行 revision 的位置；当前工作区存在一行偏移，不能直接用修改后的相同行号解释旧栈。

这说明最后一次失败发生在检查点批次发布的一致性边界，不是模型返回失败。它并未说明哪次并发控制/其他状态提交推进了 revision，也不能反推此前所有耗时都来自版本冲突。目标时间窗口的 Docker 日志为空，未取得包含异常详情的运行日志。

长时间准备与共享 run revision 的控制/协议更新之间存在竞争窗口，应单独检查其重读、合并和受控冲突处理。不能通过删除版本检查来提速或隐藏失败。本次不修改这一运行，也不自动恢复并重新产生模型费用。

## 9. 优先处理什么

1. **先量出约 4 小时的未归因区间。** 对工作状态导出、图构造、候选检查、精排快照/摘要、增量编码、基线、SQL/commit、协调确认、冷恢复与任务重放分别计时，使用互斥墙钟或明确嵌套关系。保留任务/请求身份，勿记录原文和提示。
2. **减少主模型工作量和重复输入。** 1237 次发现/核验及约 709 万输入 tokens 是最大的实测项；分析哪些主体/谓词反复低收益，优化证据定位和稳定前缀复用。不能跳过否定/条件、主体归属或独立核验来换速度。
3. **按前一份简化方案去除当前状态的重复处理。** 精排/协议结果各存一份、检查点引用；当前图按变化候选推进；缓存全文证据索引、冻结本体及按类型菜单；进度、精排和图分别按实际变化更新。见[暂停继续的状态简化分析](关系图谱暂停继续的状态存储简化分析.md)。
4. **再优化基线和恢复。** 避免多份完整状态的重复基线，明确现存引用后回收历史；完整工作状态具备直接恢复能力后，再缩减全前缀重放。只保留最新状态并不等于把所有内容改成每次全量覆盖一个大 JSON。
5. **区分页面入口。** 报告/模板入口已有 SSE 合并、图版本缓存及独立精排摘要；旧文档分析面板仍有定时和事件触发的整组读取。展示 GET 不启动模型，可能争用共享资源，但本次没有 HTTP/浏览器计时证明它是后期停顿主因。

本次完成只读运行统计、代码调用链及历史证据复核，并保存文档与汇总。未执行代码测试、函数级性能实验、真实模型重跑或部署；未承诺删减检查点后整轮识别会达到某个时长。
