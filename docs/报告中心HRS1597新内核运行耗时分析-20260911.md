# 报告中心 HRS-1597 新内核运行耗时分析

日期：2026-09-11。分析当前运行的只读快照；未暂停、重启、重跑识别，未修改配置或本体。

## 结论

新开关确已生效。当前缓慢主要来自反复提交较长输入的串行发现/核验、随状态增长而变慢的
检查点保存，以及清洗动作拆成多个实体后展开的低收益子关系检索。语义模型单次推理较快，
共享模型排队也很短；不能将全部耗时归于模型服务器或 GPU 精排。

本轮尚未达到快速形成完整目标路径的效果。此前 HRS-5592 的 v9 六轮验证关闭语义排序，
且只验收指定路径；本轮是 HRS-1597、生成摘要、开启语义排序的在线 PostgreSQL 全图运行，
不能将此前约7分钟的目标路径结果直接当作本轮整图完成时间。

## 瓶颈证据

### 1. 模型主要时间用于处理输入

104次已结束发现/核验共2554.688秒，累计输入521656 tokens、输出32609 tokens。
服务端 `prompt_ms` 合计 **1924.424秒，占请求累计时长75.33%**；输出生成约566.19秒。
缓存命中40281 tokens，占记录输入约7.72%。候选发现平均约4284输入tokens，核验约6590。

这说明长输入反复处理比输出生成更占时间。当前请求带有主体、谓词、证据、字段映射、
证明菜单和响应schema；需要压缩冗余并改善固定前缀复用，不能通过删掉独立核验或原文证据提速。
代码入口见 [model_adapter.py](../backend/app/services/extraction/ontology_guided/model_adapter.py)
及 [repair_adapter.py](../backend/app/services/extraction/ontology_guided/repair_adapter.py)。

### 3. 清洗动作形成过多实体，扩大后续检查范围

本轮根层实际是 **86条逻辑记录 × 12条关系 = 1032个覆盖机会**。子实体出现后，已建立
116个主体/谓词计划，每个仍保留86条记录，合计9976个机会；启发式只准入402项，其余9574项
延后，因此9976不是已派发任务数，但这些完整账本仍进入检查点。

候选图中已有8个 `CleaningProcess` 和6个 `ManualCleaning` 节点。部分节点名称是单个操作，
例如“加纯化水160L搅拌洗涤10~20分钟……”和“氮气吹干反应釜内壁和管道并挂清洁标志牌”。
这些清洗主体对应36个计划、3096个覆盖机会，包含历史/失效分支。

随后内核为其查找 `followsProtocol`、`hasInactivationStep`、`removesResidue`。
仅前两种子关系已消费23次LLM请求、497.65秒；当前图中没有受支持的前两种子关系。
曾经受支持的部分候选后来被撤回，不能把历史首达当作当前有效结果。

五个已提交有效语义排序批次中，四个属于前两个清洗步骤的上述子关系，一个属于降解百分比。
每批选择64条记录，对发现和反证两个意图各精排一次，即128对、32次batch4精排请求，
最后才向启发式队列准入8条。对应五个H2搜索槽的 `supported_output_count` 均为0；尚有未尝试
候选，因此这表示截至采样收益为零，不表示全文不存在相关事实。

另有一次已完成排序因主体失效而被丢弃，已花194.02秒、55次计费模型请求、128对精排。
累计排序批次时间894.62秒包含推理、准备和同步持久化，并与LLM识别并行，不能作为独立墙钟
时长相加。根源还包括批次范围偏大、低收益分支扩搜及失效后才丢弃已付费结果。

## 优化优先级

1. **完成ER06状态增量**：按任务追加结果、按主体/谓词更新覆盖账本、按协议lineage更新状态；
   大的只读排序视图与缓存独立存储，常规检查点引用版本，周期生成完整基线。保留费用预扣、
   fencing、hash、恢复回放和幂等要求。
2. **收紧按需语义扩搜**：先小批召回/精排，当前批无合格证据再扩大到64；发现与反证分别按
   实际缺口触发。对已失效主体尽早停止待派发批次，已付费记录照常保留。低相似度只延后检索，
   不作全文否定。
3. **控制清洗实体粒度及分支竞争**：以设备行的完整规程及产品适用范围聚合证据；区分规程、
   单步动作与实际执行。优先推进有明确字段证据的设备编号、规格和生产计划属性，同时为根层
   关系留出份额，避免多个清洗步骤持续扩展同一类缺证菜单。具体本体变更需单独设计验证。
4. **减少LLM输入冗余**：保持固定提示/schema前缀，精简重复标识和重复证据，按断言拆分过大的
   核验载荷；仍保留同源组合证明、否定/条件、主体归属和独立核验。
5. **补齐可观测性**：当前105条发现/核验调度记录的 `task_id` 全为null，无法直接关联任务。
   本次通过单运行串行顺序与105条费用预扣逐条匹配，阶段全部一致后才重建谓词费用。
   后续应直接记录task/lineage/检索阶段，并增加编码、SQL、提交及排序准备的独立计时。
