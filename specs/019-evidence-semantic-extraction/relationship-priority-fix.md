# 模板关系识别修复（2026-09-09）

问题：源文档存在产品介绍和清洁记录，但模型引用了其他段落，实体召回逐批扫描到较晚
章节耗时较长，空分支又统一显示“未识别”。本次修复现有模板抽取入口，不切换运行域。

验收：

1. 错位引用通过一次有界模型纠错重新定位，原错误可审计；错误坐标、歧义、越界、改写
   仍拒绝。纠错后独立类型/绑定/极性验证保持有效；有效兄弟候选、预算和暂停恢复不丢失。
2. 根关系驱动局部 range 菜单及相关记录优先识别，后部章节可早于无关前部正文处理。
   复用 RecordIndex / plan_slot；检索排名不能证明关系，未匹配记录保留全文后续覆盖。
3. 分支状态随检查点持久化和刷新；无新候选也更新。失败、待处理、无合格对象和范围内
   完成无有效关系分开显示；历史缺少台账不伪造覆盖。

实现计划：引用纠错反馈与恢复 → 根关系记录优先调度 → 运行台账与前端派生展示。
跨层字段见 contracts/evidence-api.md；无需迁移数据库，不改变本体或已提交事实。
验证包含引用反例、暂停重放、预算、后部清洗记录优先、其他分支公平、空图状态及 API
读取无模型副作用。工程测试与真实模型质量、线上部署分别报告。

## 已确认原因

目标模板为 `8542466b-d6e6-4052-ae7e-05ca9c99a1c3`（批记录 v2.2），
源作业为 `885c6aec-9b09-49ec-a368-926100e93a02`。实际入口使用
`GenericExtractionRunner`，属于模板证据抽取作业。

- 产品介绍位于第 4 页；原响应把介绍文字绑定到“是否是青霉素类药物：否”的证据 ID，
  逐字引用校验失败，导致 `DrugProduct` 没有合格关联对象，关系任务随之跳过。
- 清洗表位于第 16 页、约第 338 个证据单元。原调度在 1193 个单元上逐批扫描，
  实体菜单包含 136 个类型；调查时只处理到第 7 页。等待时间不能等同持续模型计算时间。
- 图谱空分支没有执行台账，统一显示“未识别到关系”，掩盖了未处理与引用失败的区别。
- 定向修复诊断进一步发现，清洗绑定验证把其他单元格文字作为 `context`，或把整行
  拼接预览当作某个单元格原文。纠正引用后，文档根标题与表格记录混在同一组绑定证据中，
  又使原表格行定位误拒合法关系。

## 实现结果

1. `citation_repair.py` 提供允许范围内的精确匹配提示；模型必须重新提出引用，服务器
   继续校验原文、范围、类型、主体、对象、关系方向及极性。独立绑定/引用验证要求
   `context=null`，跨格证据分别放入 `assertion_spans`。首次失败、纠错预约、累计预算
   和已通过的兄弟候选均进入检查点；空纠错响应保持未完成。
2. `table_records.py` 区分文档根标题证明与表格行坐标。仅对服务端生成、校验通过、属于
   当前文档且标记 `document-metadata-v1` / `job_metadata` 的根，允许其精确非表格标题
   span 不参与行定位。标题保留在绑定证据中并继续接受引用/范围/语义检查；事实引用、
   其他正文、其他行或其他文档不适用此规则，标题不能替代表格事实。
3. `relationship_priority.py` 复用共享 `RecordIndex` / `plan_slot`，先按模板消费路径，
   再按根关系稳定轮转，每个关系最多提前处理 3 条相关记录。类型菜单限关系 range 和
   合法子类，合格对象出现后立即独立验证关系；相关性仅影响顺序，后续保留全文扫描。
   在源文档的默认排序检查中，产品和清洗分别位于第 2、第 3 个分支，局部菜单分别为
   12、8 个类型，首条相关记录命中第 4 页介绍和第 16 页清洗首行。
4. `branch_progress.py` 从持久化任务台账投影文档根直接关系状态；没有新候选时也发布
   进度快照。API 返回运行状态，前端显示等待、对象识别、等待关系验证、校验失败、
   已识别等状态，并结合暂停/中断/失败状态显示。尚未执行的排队任务不计入执行数。
   `coverage_complete` 保守采用本轮整体完成状态，已识别关系不代表已完成全文覆盖。

新运行的策略进入运行身份；旧检查点继续沿用原顺序和任务 ID，可以追加有界引用纠错及
执行台账。已经耗尽的累计预算不会因纠错、暂停或恢复被重置。刷新/GET 不调用模型。
