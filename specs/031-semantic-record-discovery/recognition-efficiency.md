# 文档识别调用效率修正

日期：2026-09-19。需求来源：用户要求落实运行 `466e2822-2276-415d-8c04-5f2520cb3e08` 的诊断修复，并让一次输入覆盖更多合适记录、提高输出通过核验的比例。

## 需求与澄清

1. 缺少合法对象端点的关系工作不得反复发起必然为空的识别调用。保留待处理语义，定向推进该原文范围的实体发现；后到的合法候选可唤醒关系。缺少端点不等同全文无事实，也不授权创建关系。
2. 模型返回原文定位的缺失对象观察时，包括 `missing`，必须能进入已有有界补发现；没有事实资格的上下文不得变成补发现的事实来源。
3. 明确 `bridge_ref_ids` 只引用已登记桥接 ID，没有登记项时必须为空；逐字引文、字段归属、记录组成和每项 supported 核验的引用要求不放宽。可修正的输出问题应把原回答及具体错误反馈给模型，在既有任务预算内纠正，不以清空候选数组作为修正。
4. 同一张表、同一表头结构的连续数据行默认可共同识别，每批最多 4 条数据行，同时受现有记录数和字符预算限制。不同表、嵌套结构、不连续行或具有纵向合并单元格的行不合组；容量不足保留独立任务，不截断原文。表前说明仍仅在首批拥有独立事实资格。
5. 一批允许多个实体及其多个属性，每条声明保留准确物理行与原文引用。共同阅读不证明同一身份、属性归属或跨行关系，不能让甲行字段自动归到乙行主体。
6. 有明确关系端点缺口时优先推进其候选；普通候选兼顾不同章节/类型的推进，在这一约束内沿用相似度排序。只改变调用先后，不扩大候选数量或事实授权。
7. 复用当前模型、当前状态和调用账本。不开新服务、不新增历史快照、数据库表或本体公理。默认对新建运行启用，验证使用当前实现新建运行，不额外建设旧运行兼容层。

## 验收

- 同表多行的受控输入以更少发现任务识别多个实体与多个属性；跨行错配、表头作为事实、跨表或超容量组合仍被拒绝或分别执行。
- 没有可用对象时不消耗关系模型调用，也不记为已检查；后到端点能触发独立关系证明，暂停继续保留正确工作状态。
- 原文缺口 `missing` 不再被静默忽略，无证据缺口不能无界重扫。
- 错把原文 ID 当桥接引用、supported 但没有引文、记录组成覆盖不全等输出得到有界纠正；仍不合规的声明不入图，预算不被重置。
- 比较受控案例的模型调用数、候选及最终事实，而不只统计空队列。实际真实模型质量、耗时与部署结果分别报告。

## 当前实现

- `executor.py` 在实际调度前检查关系的合法对象类型。缺少端点时保存 `waiting_endpoints` 工作项，保持未尝试/依赖阻塞状态，不消耗识别任务预算；合法端点出现后由既有依赖签名变化唤醒。仅有缺端点状态不触发已检查原文的重扫，补发现须有已定位的原文缺口。
- `record_search.py` 优先已有明确缺口，普通候选按章节和类型的已调度次数轮转，再按组内次数、相似度和原文顺序选择。即使所有组首选相同类型，也给已入选的次选类型及时处理的机会；候选数量不变，计数保存在既有当前工作状态。
- `record_discovery.py` 默认 `table_reading=bounded-table-rows-v2`、`max_table_rows_per_group=4`。`table_reading.py` 只组合满足结构和容量边界的数据行；纵向合并单元格继续按单行处理，避免共用物理单元格归属不明确。
- `record_model_adapter.py` 明确桥接 ID 和各核验项的原文支持要求。发现与核验分别最多进入一次语义纠正流程，纠正携带完整前次回答及具体错误；既有 JSON/Schema 格式重试仍可能产生额外请求，但发现阶段为独立核验预留至少一次调用，所有请求仍使用原任务预算。发现纠正若清空全部候选，则原回答作为待冻结候选继续接受独立核验，不能直接入图；核验明确否定时仍拒绝。暂停继续复用已付回答。提示直接阅读已给原文，并移除 Schema 中的 `title` 元数据以减少输入开销。
- 纠正入口复用实际请求的完整容量检查，含回答输出预留。纠正输入放不下时不保存纠正状态或消耗模型调用，沿用原回答进行冻结/核验；不截断证据，不掩盖计数错误。
